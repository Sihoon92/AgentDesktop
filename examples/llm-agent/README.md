# LLM 에이전트 예제

OpenAI Responses API와 `agent-desktop` CLI로 관찰-동작 루프를 돌립니다. 작업 파일에 적은 목표를 LLM이 수행하고, 하니스가 성공 조건을 직접 읽어 판정합니다. 확신이 없는 클릭 앞에서는 사람에게 묻고, 승인받은 답을 시스템별 지식으로 저장해 다음 실행에서 다시 묻지 않습니다.

`agent-desktop`은 LLM을 내장하지 않으므로 이 루프는 호출하는 쪽인 Python에 있습니다.

## 준비

Windows PowerShell 기준입니다. 저장소 루트에서 CLI를 빌드합니다.

```powershell
cargo build -p agent-desktop
Set-Location examples\llm-agent
conda activate AgentDesktop
pip install -r requirements.txt
```

API 키는 환경변수나 `examples\llm-agent\.env`에 넣습니다. `.env`는 Git에서 제외되어 있습니다. `.env.example`을 `.env`로 복사해 필요한 줄만 채웁니다.

```powershell
$env:OPENAI_API_KEY = '<키>'
```

| env | 뜻 |
| --- | --- |
| `OPENAI_API_KEY` | 텍스트 모델의 키(모델 실행에 필수) |
| `OPENAI_BASE_URL` | 텍스트 모델의 주소. 없으면 OpenAI 기본 주소 |
| `OPENAI_MODEL` | 텍스트 모델 이름. 작업 파일과 설정 파일의 `model`이 앞섬 |
| `VISION_MODEL` | 비전 모델 이름. 있으면 [텍스트 모델과 비전 모델 나눠 쓰기](#텍스트-모델과-비전-모델-나눠-쓰기) |
| `VISION_API_KEY` | 비전 모델의 키. 없으면 `OPENAI_API_KEY` |
| `VISION_BASE_URL` | 비전 모델의 주소. 없으면 `OPENAI_BASE_URL` |

공백뿐인 값은 없는 것으로 봅니다. `VISION_API_KEY`나 `VISION_BASE_URL`만 있고 비전 모델 이름이 없으면 한 모델로 조용히 돌지 않고 실행을 거절합니다.

`AGENT_DESKTOP_BIN`, `AGENT_SETTINGS`, `AGENT_KNOWLEDGE_DIR`도 `.env`에 둘 수 있습니다. 비우면 바이너리는 `target\release`, `target\debug` 순으로, 설정 파일은 `settings.local.yaml`, 지식 폴더는 `knowledge\`를 씁니다.

### 프로필 (회사와 집)

한 PC에서 두 가지 연결(예: 집의 OpenAI, 회사의 사내 게이트웨이)을 오가려면 `.env.example`을 `.env.home`, `.env.company`처럼 복사해 각각 채우고 프로필로 고릅니다. 이 파일들도 Git에서 제외됩니다.

```powershell
python run.py --profile company --exe "C:\절대\경로\App.exe" --goal "..."
python view.py --profile company
python check.py --profile company --skip app
```

- 매번 붙이지 않으려면 `.env`나 Windows 환경변수에 `AGENT_PROFILE=company`를 적습니다. 순서는 `--profile` > 환경변수 `AGENT_PROFILE` > `.env`의 `AGENT_PROFILE`입니다.
- 프로필 파일을 먼저, `.env`를 나중에 읽습니다. 같은 이름이면 프로필 파일 값이 쓰이고, 이미 셸에 있는 환경변수가 둘보다 앞섭니다.
- 고른 프로필의 파일(`.env.<이름>`)이 없으면 `.env`로 조용히 돌지 않고 멈춥니다.
- 실행 시작과 `check.py`에는 `프로필: company`처럼 이름만 나오고 키, 주소, 모델 이름은 나오지 않습니다.

### 설정 파일

PC마다 다른 값은 `settings.local.yaml`에 둡니다. `settings.example.yaml`을 복사해 쓸 줄만 값을 적습니다. 이 파일은 Git에서 제외되어 있고, 없으면 코드의 기본값으로 동작합니다.

| 키 | 뜻 |
| --- | --- |
| `model` | Responses API에 보내는 텍스트 모델 이름. env `OPENAI_MODEL`보다 앞섬 |
| `reasoning_effort` | 추론 노력. `omit`이면 `reasoning` 인자를 보내지 않음(그 인자를 받지 않는 모델용) |
| `image_mode` | 화면 그림을 모델에 주는 방식: `off`, `user_message`, `tool_output` |
| `knowledge_dir` | 지식 폴더. 상대 경로는 설정 파일이 있는 폴더 기준 |
| `exe` | 대상 앱의 절대 경로. `run.py --goal`과 `view.py`에서 `--exe`가 없을 때 씀 |
| `system` | 지식의 시스템 이름 |
| `stage_call_limit` | 단계 하나에 쓸 수 있는 모델 호출 수(1 이상의 정수, 기본 8) |
| `plan_reasoning_effort` | 계획을 세우기 전 호출의 추론 노력(기본 `medium`, `omit` 가능) |
| `vision_model` | 비전 모델 이름. env `VISION_MODEL`보다 앞섬 |
| `vision_reasoning_effort` | 비전 호출의 추론 노력. 적을 때만 보냄 |
| `vision_max_side` | 비전 모델에 보내는 그림의 긴 변 최대 픽셀(1 이상의 정수, 기본 1280) |
| `vision_points` | 비전 모델이 내는 좌표의 방식: `pixel`(기본), `normalized_1000`. 점검의 `비전 좌표`가 권하는 값 |
| `systems` | 고를 수 있는 시스템. `이름: exe 절대 경로` 줄의 묶음. [시스템 골라 띄우기](#시스템-골라-띄우기) |
| `ready_text` | 준비 신호. 대상 앱의 창에 이름이 이 글과 똑같은 요소가 보이면 준비된 것 |
| `ready_timeout_s` | 준비를 기다리는 최대 시간(1 이상의 정수, 기본 180초) |
| `workflow_dir` | workflow 폴더. 상대 경로는 설정 파일이 있는 폴더 기준 |
| `profile_dir` | [시스템 프로파일](#시스템-프로파일) 폴더. 상대 경로는 설정 파일이 있는 폴더 기준. `.env`를 고르는 `--profile`과는 다른 것 |

우선순위는 명령줄 인자, 작업 파일의 키, 설정 파일, 코드의 기본값 순서입니다. 텍스트 모델 이름만은 설정 파일과 코드의 기본값 사이에 env `OPENAI_MODEL`이 들어갑니다. 다른 위치의 파일은 환경변수 `AGENT_SETTINGS`로 지정합니다. 모르는 키나 틀린 값이 있으면 실행하지 않고 오류로 멈춥니다. API 키와 주소는 설정 파일이 아니라 `.env`에 둡니다.

Windows 경로는 따옴표 없이 적습니다(`exe: C:\Example\App\Example.exe`). 큰따옴표 안에서는 역슬래시가 특수 문자라서 오류가 나거나 경로가 다른 글자로 바뀝니다. 감싸야 하면 작은따옴표를 씁니다.

### 점검

새 PC나 새 대상 앱에서는 실행 전에 점검부터 합니다.

```powershell
python check.py --exe "<절대경로>"     # 설정 파일에 exe가 있으면 --exe 없이
python check.py --system <이름>        # 설정 파일의 systems에서 고름. 없으면 기본 선택 하나
python check.py --skip app             # LLM까지만. 창을 띄우지 않음
python check.py --skip llm             # 모델을 부르지 않음
```

항목마다 `통과`, `실패(코드)`, `건너뜀` 한 줄이 나오고, 실패가 있으면 종료 코드가 1입니다.

| 항목 | 확인하는 것 |
| --- | --- |
| 바이너리 | `agent-desktop`을 찾은 곳과 버전 |
| 설정 | 설정 파일을 읽었는지, 어느 키가 거기서 왔는지. 아래 줄에 고른 시스템의 프로파일을 수로 냄(`시스템 프로파일: 준비 신호 2 · 등록 이름 14 · ID 고정 예 · 읽는 방식 snapshot`, 없으면 `없음`). 프로파일 파일이 깨졌으면 `실패(PROFILE_INVALID)`와 몇 번째 항목인지를 내고 앱은 띄우지 않음. 대상이 바로가기(`.lnk`)면 그 아래에 `바로가기: 대상 exe · 인자 2 · 시작 위치 있음`이나 `바로가기: 실패(코드)`를 냄([바로가기로 띄우기](#바로가기로-띄우기)) |
| LLM 호출 | Responses API 호출이 되는지 |
| LLM 도구 호출 | 모델이 strict 도구를 부르는지 |
| LLM 그림 입력 | 그림을 두 방식으로 보내 읽는지. 읽은 방식을 `image_mode` 권장값으로 냄. 비전 모델을 지정하면 `건너뜀 (나눈 방식)` |
| 비전 호출 | 비전 모델이 숫자 그림을 읽는지. 비전 모델을 지정했을 때만 나옴 |
| 비전 좌표 | 빨간 원 하나를 그린 그림에서 비전 모델이 낸 좌표가 픽셀인지 0~1000인지. `vision_points` 권장값을 냄 |
| 준비 신호 | 대상 앱을 띄워 준비 신호가 보일 때까지 기다린 결과(`찾음 · 12초 · 대상 바뀜`), 실패하면 `READY_TIMEOUT` 같은 코드. 아래 줄에 바퀴마다 걸린 시간과, 준비된 화면에서 두 읽는 방식을 잰 시간을 냄(아래). 준비 신호가 적용되는 앱에서만 나옴 |
| 앱 관찰 | 주 창의 요소를 종류별로 센 수, 잘림 여부, 걸린 시간, 캡처 크기. 준비 신호가 있으면 준비된 창을 읽음 |
| id 유지 | 앱을 껐다 켠 뒤에도 요소의 `AutomationId`가 같은지. 모두 같으면 "등록 화면에서 'ID는 다시 켜도 같음'을 켜도 됩니다"를 붙임 |

준비 신호 항목 아래의 줄은 준비 기다리기가 어디서 느린지 가르는 데 씁니다.

```
  준비 신호: 통과 (찾음 · 4초 · 대상 바뀜)
    1바퀴: 창 목록 120ms · 후보 1 · 창1 없음 2100ms
    2바퀴: 창 목록 120ms · 후보 2 · 창1 없음 2050ms · 창2 찾음 310ms
    읽는 방식: snapshot 4.2초 · find 0.3초 · 권장 find
```

- **바퀴 줄:** 창 목록을 읽은 시간, 후보 창 수, 창마다(`find` 방식은 신호마다) 찾았는지와 걸린 시간입니다. 읽기가 실패하면 `실패 <코드>`, `find`가 제한 시간에 걸리면 `시간 초과`가 나옵니다. 창과 신호는 번호로만 부릅니다. 20바퀴를 넘으면 처음 10바퀴와 마지막 10바퀴만 냅니다.
- **`읽는 방식:` 줄:** 준비된 화면에서 두 방식을 한 번씩 잰 시간과 빠른 쪽입니다. 한쪽이 신호를 다 찾지 못했으면 `신호 1/2`처럼 표시하고 `권장 없음`입니다. 권하는 값은 등록 화면의 "읽는 방식"이나 프로파일의 `ready_read`에 적습니다.

출력에는 수, 코드, 판정, 값의 출처(`설정 파일`, `env`, `기본값`)만 있고 화면의 글, 경로, 설정 값, 모델 이름, 주소, 키는 없습니다. LLM과 비전 항목이 보내는 것은 점검 명령이 만든 글, 숫자 그림, 빨간 원 그림뿐입니다. 앱 관찰은 앱이 떠 있으면 읽고 없으면 띄우며, 누르거나 입력하지 않고 닫지도 않습니다. 읽는 것은 그 순간 주 창에 보이는 것뿐입니다. 메뉴를 거쳐야 나오는 화면을 재려면 그 화면을 손으로 연 뒤 점검합니다.

앱 관찰의 수는 그 앱을 어떻게 다뤄야 하는지 알려 줍니다.

| 수 | 뜻 |
| --- | --- |
| 이름 있는 ref | 이름으로 찾아 누를 수 있는 요소 |
| 이름 없는 ref(id 있음 n) | 누를 수는 있지만 이름이 없어 캡처의 번호로 구분하는 요소. id가 있고 유지되면 다시 찾는 열쇠가 됨 |
| 글자 | ref 없이 글과 위치만 있는 요소. 위치를 눌러야 함 |
| 빈 영역(그림 후보) | 이름도 ref도 자식도 없는 영역. 그림으로만 그려진 곳일 수 있고, 장식용 요소도 섞여 셈 |
| ID만 있는 요소 | 이름도 ref도 없고 `AutomationId`와 자리가 있는 요소. 등록 화면에서 이름을 붙일 수 있는 것들. 자식이 없는 것은 빈 영역에도 세어짐 |

id 유지는 두 번 점검해야 나옵니다. 앱을 켠 직후에 한 번 점검하고, 앱을 닫았다 켠 뒤 같은 화면에서 다시 점검하면 `같은 id 37/40`처럼 나옵니다. 앱을 다시 켜지 않았으면 `건너뜀`입니다. 비교할 값은 `.check\`에 해시로 저장하며 Git에서 제외됩니다.

창 핸들인 ID는 세지 않습니다. 이름을 붙이지 않은 WinForms 컨트롤처럼 `AutomationId`가 그 컨트롤 자신의 창 핸들인 요소가 있고, 그 값은 앱을 켤 때마다 바뀝니다. 하니스는 CLI에서 화면을 받을 때 값이 그 앱의 창 핸들과 같은 ID를 떼어 내고, 그 요소를 ID가 없는 요소로 봅니다(`agent/handles.py`). 그래서 이런 ID는 관찰 글, 등록 화면의 표, workflow의 대상, 이 점검의 수에 나오지 않습니다. 다른 까닭으로 바뀌는 ID는 가리지 못하므로 이 항목의 수를 보고 판단합니다.

## 실행

```powershell
python run.py tasks\footprint_open_settings.yaml --baseline
python run.py tasks\footprint_open_settings.yaml
```

`--baseline`은 LLM 없이 고정 순서로 실행하므로 키가 필요 없습니다. 두 번째 명령은 LLM을 호출하고, 시작할 때 `텍스트 모델: env · 비전 모델: 없음`처럼 모델 이름을 어디서 가져왔는지 한 줄 출력합니다. 모델 이름은 출력하지 않습니다.

작업 파일 없이 지시를 바로 줄 수도 있습니다.

```powershell
python run.py --exe "C:\절대\경로\App.exe" --goal "5분봉으로 바꿔줘" [--level 0-3]
```

`--level`의 기본값은 `3`이고 스텝 한도는 60입니다. 이 방식에는 성공 조건이 없으므로, 모델이 성공을 주장하면 [완료 판정](#완료-판정)의 순서대로 지식의 완료 조건이나 사람의 확인으로 판정합니다. 둘 다 없으면(터미널이 아닌 실행 등) `claimed`로 끝나고, 결과는 출력된 마지막 관찰이나 앱 화면에서 직접 확인합니다. 작업 파일과 `--goal`을 함께 주면 작업 파일의 `goal`만 바뀌고 성공 조건은 그대로 씁니다. 대상 앱이 이미 떠 있으면 같은 경로의 프로세스에 붙습니다.

| 종료 코드 | 뜻 |
| --- | --- |
| `0` | 하니스가 성공 조건을 확인함(`verified`), 또는 사람이 결과를 확인함(`confirmed`) |
| `1` | 실행했지만 성공 조건을 확인하지 못함 |
| `2` | 앱을 건드리기 전에 설정 오류로 중단함 |
| `3` | 성공 조건도, 확인할 사람도 없이 모델이 성공을 주장함(`claimed`, 미검증) |

`--approve`를 붙이면 관찰이 아닌 동작마다 터미널에서 승인을 묻습니다. `y`면 실행하고, 그 밖의 답은 거부입니다. 거부한 동작은 앱에 보내지 않고 이유를 모델에 돌려줍니다.

```powershell
python run.py --exe "C:\절대\경로\App.exe" --goal "새 탭을 열어줘" --level 1 --approve
```

`--system <이름>`은 지식을 나누는 시스템 이름이고(기본값은 실행 파일 이름), `--knowledge-dir <폴더>`는 지식 폴더입니다. 둘 다 [묻기와 배우기](#묻기와-배우기)에서 설명합니다. `--system`이 설정 파일 `systems`의 이름이면 그 시스템의 exe도 고릅니다.

### 시스템 골라 띄우기

같은 종류의 앱이 사이트마다 따로 깔려 있으면(예: 공장마다 다른 MES) 설정 파일에 이름과 경로를 적어 두고 이름으로 고릅니다.

```yaml
systems:
  공장A: C:\Example\MES\A\MES.exe
  공장B: C:\Example\MES\B\MES.exe
ready_text: 생산운영
ready_timeout_s: 180
```

```powershell
python run.py --system 공장A --goal "..."
```

- **exe 고르는 순서:** `--exe` > `--system`의 항목 > 작업 파일의 exe > 설정 `system`의 항목 > 설정 `exe`. 뷰어에서는 "설정"의 시스템 목록에서 고릅니다(목록 끝 "직접 입력"은 지금처럼 경로를 적음).
- **바로가기로 띄우기:** exe 경로를 적는 곳(`--exe`, 설정의 `systems`와 `exe`, 작업 파일의 `exe`, 뷰어, 등록 화면, `check.py`)에는 바로가기(`.lnk`) 경로도 적을 수 있습니다. 아래 [바로가기로 띄우기](#바로가기로-띄우기)에서 설명합니다.
- **준비 기다리기:** `ready_text`가 있으면 하니스가 모델을 부르기 전에 앱을 띄우고, 이름이 `ready_text`와 똑같은 요소(예: 메인 화면의 메뉴)가 보이는 창을 찾을 때까지 다시 읽습니다(읽기 사이에 0.3초를 쉼). 그 시스템의 [프로파일](#시스템-프로파일)에 준비 신호가 있으면 `ready_text` 대신 그 신호들을 모두 찾습니다. 팝업이 메인 화면을 다른 프로세스로 띄워도 실행 전에 없던 창을 살펴 따라가고, 그 창의 프로세스가 대상이 됩니다. 모델 호출 수와 토큰은 쓰지 않고, 승인 모드에서도 묻지 않습니다. 기다리는 동안 뷰어에 "대상 앱 준비 중"이 보입니다.
- **준비 신호는 설정 파일에 적은 앱에만:** 실행의 exe가 `systems`의 경로나 설정 `exe`일 때만 적용됩니다. `--exe`나 "직접 입력"으로 띄운 다른 앱은 지금처럼 모델이 `launch_target`을 부릅니다. 작업 파일은 `ready_text`, `ready_timeout_s`를 직접 적을 수 있습니다.
- **멈추는 경우:** 모델을 부르지 않고 이유를 남깁니다.

| 코드 | 뜻 |
| --- | --- |
| `already_running` | 같은 경로의 앱이 이미 떠 있음. 건드리지 않으니 닫고 다시 실행 |
| `no_new_window` | 실행 뒤 30초 동안 새 창이 하나도 뜨지 않음. 이미 떠 있던 창에 준비 신호가 보이면 "이미 떠 있는 것 같습니다"를 붙임 |
| `timeout` | `ready_timeout_s` 안에 준비 신호가 보이지 않음 |
| `launch_failed` | 앱을 띄우지 못함 |

회사 MES처럼 처음 쓰는 앱은 `python check.py --system <이름>`의 `준비 신호` 줄로 신호가 실제로 잡히는지 먼저 확인합니다. 메뉴 이름 뒤에 단축키 같은 글이 붙어 있으면 똑같은 이름이 아니라서 `READY_TIMEOUT`이 됩니다.

실행이 끝나면 기록 폴더, 그 실행을 나중에 다시 여는 명령(`나중에 보기: python view.py --open <run_id>`), `trace export` 명령을 출력합니다. `trace export`로 CLI trace를 HTML로 내보낼 수 있습니다.

### 바로가기로 띄우기

exe를 직접 실행하지 않고 바로가기로 실행하는 시스템은 바로가기 경로를 그대로 적습니다.

```yaml
systems:
  GSCM-A: D:\Example\Links\GSCM A.lnk
```

`agent-desktop launch`는 실행 파일만 시작할 수 있어서(`CreateProcess`), 하니스가 띄울 때마다 바로가기에서 대상 exe, 인자, 시작 위치를 읽어 CLI에 넘깁니다(`agent/shortcut.py`). 띄운 뒤의 동작은 exe를 적었을 때와 같습니다: 준비 기다리기, "이미 떠 있음" 판정, 다시 띄우기, workflow 재실행.

- **이름과 기록은 바로가기 경로로 남습니다.** 시스템 이름의 기본값, `systems`와의 비교, `run.json`의 `exe`는 적은 `.lnk` 경로입니다. 대상 exe의 경로, 인자, 시작 위치는 요약, `check.py` 출력, `run.json`에 넣지 않습니다.
- **점검:** `check.py`가 설정 항목 아래에 `바로가기: 대상 exe · 인자 2 · 시작 위치 있음`을 냅니다. 읽지 못하면 `바로가기: 실패(코드)`를 내고 앱을 띄우지 않습니다.
- **띄우지 못하는 바로가기:** 앱을 건드리기 전에 코드로 알립니다.

| 코드 | 뜻 |
| --- | --- |
| `SHORTCUT_UNREADABLE` | 바로가기 파일을 읽지 못함(없음, 깨짐) |
| `SHORTCUT_NO_TARGET` | 대상 경로가 없음(스토어 앱, 제어판 항목 등) |
| `SHORTCUT_NOT_EXE` | 대상이 `.exe`가 아님(배치 파일, 문서, 웹 주소) |
| `SHORTCUT_TARGET_MISSING` | 대상 exe 파일이 없음 |

- **한계:** 같은 exe에 인자만 다른 바로가기가 여럿이면 한 번에 하나만 띄울 수 있습니다. 하나가 떠 있는 동안 다른 것을 실행하면 "같은 시스템이 이미 떠 있습니다"로 멈춥니다. "관리자 권한으로 실행", 창 크기, 단축키 같은 바로가기의 다른 설정은 따르지 않습니다. 인자를 나눠 넘기므로, 명령줄 전체를 글자 그대로 읽는 앱은 따옴표 위치가 달라 보일 수 있습니다.

설계는 [docs/specs/2026-11-19-shortcut-launch-design.md](docs/specs/2026-11-19-shortcut-launch-design.md)에 있습니다.

## 시스템 프로파일

시스템마다 다른 것을 관리자가 등록해 두는 파일입니다. 지금은 두 가지를 담습니다: 메인 화면이 다 떴다고 보는 **준비 신호**와, 글자가 그림으로만 그려져 이름이 없는 요소에 붙이는 **등록 이름**입니다. 설계는 [docs/specs/2026-11-19-system-profile-design.md](docs/specs/2026-11-19-system-profile-design.md)에 있습니다.

`profiles\<시스템>.yaml`에 둡니다. 화면의 글이 들어 있으므로 Git에서 제외되어 있습니다. 폴더는 `--profile-dir` > 설정의 `profile_dir` > 환경변수 `AGENT_PROFILE_DIR` > 기본 폴더 순서로 정하고, 시스템 이름은 지식 폴더에 쓰는 그 이름입니다. `.env`를 고르는 `--profile`과는 관계가 없습니다.

```yaml
format: 1
system: GSCM
stable_ids: true
ready_read: snapshot
ready:
  - {name: Order Management}
  - {id: '56', role: image, in: {role: toolbar, id: '12'}}
elements:
  - {id: '56', role: image, in: {role: toolbar, id: '12'}, name: Shipment Plan}
  - {id: '60', role: image, in: {role: toolbar, id: '12'}, name: Execution Plan}
```

| 키 | 뜻 |
| --- | --- |
| `ready` | 준비 신호. **모두** 보여야 준비입니다. 이름으로 적거나(`name`, 좁힐 때 `role`), ID로 적습니다(`id`, `role`, 있으면 `in`). 하나라도 있으면 설정의 `ready_text`보다 앞섭니다 |
| `elements` | 등록 이름. `id`, `role`, `name`, 있으면 `in`. `name`은 한 줄에 80자까지 |
| `in` | 담긴 영역: 그 요소의 조상 가운데 가장 가까운, ID나 이름이 있는 요소(`{role, id}`나 `{role, name}`). 등록 화면이 자동으로 적습니다 |
| `stable_ids` | 이 시스템의 ID가 앱을 다시 켜도 같다는 표시(기본 거짓). 참일 때만 workflow가 대상에 ID를 적습니다 |
| `ready_read` | 준비 확인이 화면을 읽는 방식: `snapshot`(기본, 트리를 통째로 읽음)이나 `find`(신호마다 CLI에 물음). `check.py`가 재서 권하는 값을 적습니다 |

- **ID는 추가 정보입니다.** 어디서도 ID 하나만으로 요소를 판정하지 않습니다. 역할과 ID, 적혀 있으면 담긴 영역이 함께 맞아야 하고, 이름이 있는 요소는 이름도 맞아야 합니다. 다른 화면의 다른 영역에 같은 ID가 있어도 같은 요소로 보지 않습니다.
- **모델이 보는 것:** 이름 없는 요소의 줄에 `id="60"`이 붙고, 등록 이름이 있으면 `alias="Execution Plan"`이 붙습니다. 모델은 `alias`를 그 요소의 이름으로 읽되, 화면과 어긋나 보이면 `look`으로 확인하거나 묻습니다. 한 화면에서 한 등록 이름에 맞는 요소가 둘 이상이면 어느 것에도 붙이지 않습니다. 누르는 것은 지금처럼 ref나 표시 번호이고, ref가 없는 요소는 `click_part`(실제 클릭, 권한 단계 2 이상)로 누릅니다.
- **요소의 범위:** 이름도 ref도 없고 ID만 있는 노드는 자식이 없거나 프로파일에 등록됐을 때 요소가 됩니다. 자식이 없는 경우는 프로파일이 없는 실행에도 적용됩니다.
- **깨진 파일:** 모르는 키, 빈 글, 겹친 항목, 파일 이름과 다른 `system`이 있으면 그 시스템의 실행을 시작하지 않고(종료 코드 2), 몇 번째 항목의 어느 키인지만 알립니다. 값은 출력하지 않습니다.
- **나가지 않는 것:** 준비 신호의 글, 등록 이름, ID는 `run.json`, 요약, `check.py` 출력에 들어가지 않습니다. `events.jsonl`과 프로파일 파일에만 있습니다.
- 손으로 고칠 때 ID는 따옴표로 감쌉니다(`id: '056'`). 따옴표 없이 0으로 시작하는 숫자를 적으면 YAML이 다른 수로 읽습니다.

### 등록 화면

파일을 손으로 고치지 않고 뷰어에서 등록합니다. `view.py`로 띄운 뷰어의 위쪽에서 "등록"을 고릅니다. 설정 파일의 `systems`에 적힌 시스템만 고를 수 있습니다.

1. **앱 띄우기.** 시스템을 고르고 누르면 그 앱을 띄우고(이미 하나 떠 있으면 거기에 붙고) 그 앱의 창 목록을 보여 줍니다. 창이 나오지 않으면 시스템을 닫고 다시 누릅니다.
2. **화면 읽기.** 창을 고르고 누르면 그 창의 캡처와 요소 박스가 나옵니다. 메뉴를 열어 둔 상태를 읽으려면 "3초 뒤 읽기"를 누르고 앱으로 가서 메뉴를 엽니다. 열린 메뉴 목록처럼 그 창 위에 겹친 같은 앱의 창도 캡처에 함께 그려집니다. 다시 읽어도 저장하지 않고 적어 둔 이름은 남습니다.
3. **준비 신호.** 박스를 눌러 "준비 신호로"를 누릅니다. 이름이 있는 요소는 이름으로, 이름이 없고 ID가 있는 요소는 역할·ID·담긴 영역으로 들어갑니다. ID 신호 하나만 두면 이름 신호나 다른 신호를 함께 두라는 안내가 나옵니다(저장은 됨).
4. **등록 이름.** 오른쪽 표에 이름이 없고 ID가 있는 요소가 모두 나옵니다. 줄마다 그 요소를 잘라 낸 그림, 역할, ID, 담긴 영역이 있고, 이름 칸에 적으면 등록됩니다. 비우면 등록하지 않습니다. 그림이 작게 보이는 줄은 마우스를 올리거나 이름 칸을 누르면 원래 크기로 뜹니다. 줄에 올리면 캡처에서 그 요소의 박스가 강조됩니다. 다른 화면에서 등록한 이름은 그대로 남습니다.
5. **지금 확인.** 지금 떠 있는 창에서 준비 신호가 실제로 잡히는지와, 두 읽는 방식에 걸린 시간과 권장 방식을 보여 줍니다. "읽는 방식"의 선택은 바꾸지 않으므로, 권장과 다르면 직접 고릅니다.
6. **저장.** 한 창에서 둘 이상의 요소와 맞는 등록 이름이나 ID 신호, 읽은 창에 없는 이름 신호가 있으면 저장하지 않고 그 줄에 이유를 보여 줍니다. 읽은 뒤 화면을 다시 읽지 않고 오래 두었으면 다시 읽으라고 합니다. 앞서 읽은 화면에서 적어 둔 이름도 함께 저장됩니다.

저장하지 않은 것(읽은 화면, 적어 둔 이름, 준비 신호, 선택)은 "실행"이나 "지식" 보기에 다녀와도 남습니다. 시스템을 바꾸면 저장된 값으로 돌아가고, "앱 띄우기"를 누르면 읽은 화면과 적어 둔 이름을 비웁니다.

등록 화면은 앱을 누르거나 입력하지 않고(띄우기, 창 목록, 트리 읽기, 스크린샷만), 모델을 부르지 않으며, 읽은 화면을 기록 폴더에 남기지 않습니다. 실행 중에는 화면을 읽을 수 없고, 화면을 읽는 동안에는 실행을 시작할 수 없습니다.

등록한 뒤에는 앱을 닫았다 켜서 한 번 더 확인합니다. 등록 화면에서 "앱 띄우기"와 "화면 읽기"를 다시 눌렀을 때 이름 칸에 등록한 이름이 채워져 있고 "지금 확인"이 신호를 모두 찾으면, 그 ID와 담긴 영역은 다시 켜도 같은 것입니다.

### 준비 기다리기가 느릴 때

`check.py`의 준비 신호 항목과 실행 요약의 `준비:` 줄로 까닭을 가릅니다.

| 보이는 것 | 뜻 |
| --- | --- |
| 읽기 하나가 오래 걸림(바퀴 줄의 ms, 요약의 `최대`) | 트리가 큼. `읽는 방식:` 줄이 `find`를 권하면 바꿔 봄 |
| 실패한 읽기가 많음 | 화면이 보인 직후 앱이 바빠 읽지 못함. 읽는 방식을 바꿔도 덜 빨라짐 |
| 후보 창이 많음 | 관계없는 새 창까지 읽음 |
| `find`의 시간 초과가 많음 | 신호가 아직 없을 때 `find`가 트리를 끝까지 읽느라 제한 시간(3초)에 걸림. `snapshot`이 나을 수 있음 |

## 단계로 나눠 실행하기

모델은 첫 화면을 관찰한 뒤 지시를 단계로 나누고(`plan`), 단계를 하나씩 끝냅니다(`stage_done`). 단계는 화면에서 확인할 수 있는 결과 하나입니다. "화면이 열려 있다", "선택 칸에 두 값이 선택되어 있다", "조회 결과가 표에 나와 있다"가 각각 한 단계입니다.

- **계획:** 단계는 1개에서 12개까지이고, 단계마다 목표(`goal`)와 완료 기준(`done_when`)을 적습니다. 지시에서 온 값 가운데 다음 실행에서 바뀔 수 있는 것은 `params`에 이름과 함께 적습니다([workflow 만들기와 재실행](#workflow-만들기와-재실행)의 파라미터 후보). 계획이 없으면 앱을 바꾸는 도구는 `launch_target`을 빼고 모두 거절됩니다(`needs_plan`). 계획이 틀렸으면 모델이 `plan`을 다시 불러 고칩니다. 끝난 단계는 바꿀 수 없고, 3번 넘게 고치려 하면 사람에게 묻습니다.
- **단계 완료:** `stage_done`에는 근거가 필요합니다. 가장 최근 관찰의 표시 번호이거나, 그림으로만 확인되면 `look`으로 찍은 캡처입니다. 하니스는 번호가 지금 관찰에 있는지, 캡처가 지금 화면의 것인지만 확인합니다. 그 근거가 단계의 목표를 뜻하는지는 모델이 판단합니다. 끝나지 않은 단계가 있으면 성공으로 끝낼 수 없습니다(`stages_unfinished`). 포기는 언제든 할 수 있습니다.
- **호출 한도:** 단계마다 모델 호출 수를 셉니다(`stage_call_limit`, 기본 8번). 한도에 닿으면 다음 호출 전에 사람에게 묻습니다. "계속"이면 한도만큼 더 주고, 방법을 적어 주면 그 글을 모델에게 전하고 계속하며, "중단"이면 실행을 멈춥니다. 답이 없거나 물어볼 사람이 없으면(터미널이 아닌 곳의 `run.py`) 멈춥니다. 질문만 한 차례는 세지 않습니다. 계획을 고쳐도 진행 중이던 단계의 호출 수는 이어집니다.
- **전체 상한:** 모델 호출 수(`max_steps`)와 토큰(`token_budget`)의 상한은 모델을 부르기 전에 확인합니다. 닿으면 `finish`만 할 수 있는 호출을 한 번 더 주므로, 일을 다 하고 판정만 받지 못한 채 멈추지 않습니다. 이 한 번에서는 끝나지 않은 단계가 있어도 판정합니다.
- **모델에게 보내는 기록:** 가장 최근 관찰만 글과 그림을 온전히 보내고, 그 전의 관찰은 한 줄로 줄입니다. 끝난 단계의 호출과 결과는 요약 한 줄(단계의 목표, 모델의 메모, 전달된 동작의 이유)로 바꿉니다. 가장 최근 관찰은 단계가 끝나도 새 관찰이 나올 때까지 남습니다. 질문과 답, 계획은 줄이지 않습니다. 기록 폴더에는 모든 것이 그대로 남습니다.
- **추론 노력:** 계획을 세우기 전의 호출은 `plan_reasoning_effort`(기본 `medium`)로, 그 뒤는 `reasoning_effort`로 부릅니다.

`--baseline`은 모델을 부르지 않으므로 단계가 없습니다.

## 묻기와 배우기

에이전트는 잘못 누르는 것보다 묻는 쪽을 택합니다. 언제 묻는지는 모델의 판단에만 맡기지 않고 하니스가 강제합니다.

### 화면을 보는 방법

- **표시 번호:** 관찰의 모든 요소 줄 앞에 `[n]`이 붙습니다. ref가 없는 글자나 그림도 번호로 가리킬 수 있습니다. 번호는 그 관찰에서만 유효합니다.
- **부분 클릭(`click_part`):** 번호로 고른 요소의 가운데, 왼쪽, 오른쪽, 위, 아래를 누릅니다. 끝 부분은 가장자리에서 조금 안쪽입니다. 넓은 선택 칸의 오른쪽 끝은 화살표가 있는 자리입니다.
- **셀 찾기(`find_cells`):** 행 이름과 열 이름을 주면 두 이름이 만나는 자리를 돌려줍니다. 글자의 위치만으로 계산하고 이름의 뜻은 해석하지 않습니다. 맞는 자리가 여럿이면 모두 후보로 돌려줍니다.
- **캡처(`look`):** 창이나 요소 주변을 찍어 번호 박스를 그린 그림을 모델에게 줍니다. 그림에서 고른 지점은 `click_point`로 누릅니다.
- **기대와 변화:** 동작마다 모델이 기대하는 변화(`expect`: 창이 열림, 닫힘, 내용이 바뀜, 값이 바뀜, 아무 변화)를 적고, 하니스가 동작 전후의 창 목록과 요소를 비교해 실제 변화(`effects`)와 기대가 맞았는지(`expected_met`)를 돌려줍니다. 포커스만 옮겨진 것은 변화로 세지 않습니다. `click_part`와 `click_point`는 그림 속 팝업을 눌러도 다음 관찰을 그 그림의 출처 창에서 읽어 동작 전후를 같은 창으로 비교합니다. 그 창이 닫혀 다른 창을 관찰하게 되면 요소를 비교하지 않고 `effects.observed_window`로 알리며, 이때 채워지지 않은 내용·값 기대는 불일치가 아니라 확인 못 함(`unconfirmed`)으로 둡니다. 창이 열리거나 닫히면 내용이 바뀐 것으로도 봅니다(`content_changed` 충족). 기대가 창이 열림이나 닫힘이면 창 목록만으로 판정하고 그림은 보지 않습니다. 그 밖의 기대가 관찰 글과 창 목록으로 채워지지 않으면 하니스는 누른 창을 동작 직전과 직후에 찍어 누른 곳 주변(요소 사각형을 사방 64px 넓힌 곳)을 비교합니다. 거기서 20픽셀 이상 바뀌었으면 `expected_met`은 `null`, `verdict`는 `unconfirmed`(확인 못 함)이고 캡처를 붙여 모델이 눈으로 확인하게 합니다. 접근성 정보에 상태를 알리지 않는 체크 표시가 이 경우입니다. 이 판정은 연속 불일치로 세지 않고 지우지도 않습니다. 글도 그림도 바뀌지 않으면 `expected_met`은 `false`입니다. 마우스가 올라가 색이 진하게 바뀌는 것만으로도 "확인 못 함"이 될 수 있습니다. 창이 열리기를 기대한 클릭은 칸에 포커스 표시만 생겨도 불일치로 세므로, 눌러도 열리지 않는 칸에서 두 번 실패하면 사람에게 묻게 됩니다.

### 하니스가 묻게 하는 경우

| 경우 | 하니스가 하는 일 |
| --- | --- |
| 좌표를 직접 고른 클릭(`mouse_click`, `click_point`, `drag`) | 확인 질문에 답을 받기 전에는 보내지 않음(`needs_confirmation`) |
| `find_cells`의 후보가 둘 이상인 자리의 클릭 | 같음 |
| 기대와 다른 결과가 두 번 이어짐(`mismatch_limit`) | 질문에 답을 받을 때까지 앱을 바꾸는 도구를 모두 막음(`blocked_until_question`) |
| 지식을 따라 한 동작이 기대와 다름 | 같음. 그 지식 항목의 실패 횟수도 올림 |
| 단계의 호출 한도에 닿음(`stage_call_limit`) | 다음 모델 호출 전에 계속, 방법, 중단을 물음. 답 없이 계속하지 않음 |
| 계획을 3번 넘게 고치려 함 | 같은 방식으로 물음 |

답이 `2`, `2번`처럼 후보 번호 하나뿐이면 그 후보만, 위치를 찍었으면 그 지점만 한 번 누를 수 있습니다. 그 밖의 글이면 질문에 적은 후보 가운데 하나를 한 번 누를 수 있고, 어느 것인지는 모델이 답을 읽고 정합니다. 번호와 부분으로 누르는 `click_part`와 ref 동작은 위 표의 경우가 아니면 묻지 않습니다.

질문은 터미널에서 실행했으면 터미널에, 뷰어에서 시작했으면 뷰어의 대화 칸에 나옵니다. 뷰어의 질문에 30분(`ask_timeout_s`) 동안 답이 없으면 실행을 멈춥니다. 답하려고 뷰어를 누르면 앱이 포커스를 잃어 열려 있던 목록 같은 팝업이 닫힐 수 있습니다. 그래서 하니스는 답을 받은 뒤의 첫 동작을 질문 전의 관찰이 아니라 새로 읽은 화면과 비교하고, 그동안 창이 열리거나 닫혔으면 질문 전의 번호를 버리고 모델에게 다시 관찰하라고 알립니다. 터미널이 아닌 곳에서 `run.py`를 돌리면 물어볼 사람이 없으므로, 모델은 질문 대신 포기를 보고합니다.

### 지식 폴더

승인한 답은 `knowledge\<시스템>\<id>.yaml`에 항목 하나당 파일 하나로 저장됩니다. 시스템 이름은 `--system`, 작업 파일의 `system`, 실행 파일 이름(소문자, 확장자 제외) 순으로 정합니다. 폴더는 `--knowledge-dir`, 작업 파일의 `knowledge_dir`, 환경 변수 `AGENT_KNOWLEDGE_DIR`, `examples\llm-agent\knowledge` 순입니다. `knowledge\`는 Git에서 제외되어 있고, 예시는 `knowledge.example\`에 있습니다.

| 종류 | 내용 | 쓰임 |
| --- | --- | --- |
| 해결 기록(`r-...`) | 상황과 해결 | 실행을 시작할 때 사용 중인 항목을 모델에게 줌. 모델이 따를 때 `knowledge_id`로 밝히면 확인 질문 없이 진행 |
| 완료 조건(`c-...`) | 작업의 종류와 확인 방법(`file`, `element`, `human`) | 모델이 `finish`의 `completion_id`로 고르면 하니스가 그 확인을 실행 |

항목에는 화면 좌표를 넣을 수 없습니다. 좌표로 보이는 글은 저장할 때 거절됩니다. 요소는 역할, 이름, 부분, 상대 위치로 적습니다. 파일을 손으로 고쳐도 되고, 읽을 수 없는 파일은 건너뛰고 경고로 알립니다. `status: disabled`인 항목은 모델에게 주지 않습니다.

기록과 마찬가지로 지식에는 화면의 글과 사람의 답이 들어갑니다. 민감 정보로 다루세요.

### 완료 판정

모델이 성공을 주장하면 다음 순서로 판정합니다.

1. 작업 파일에 `success.require`가 있으면 하니스가 그 요소를 확인합니다(`verified`).
2. 모델이 완료 조건 항목을 골랐으면 그 확인 방법을 차례로 실행합니다. `file`은 저장한 파일이 있고, 비어 있지 않고, 이번 실행에서 쓰였는지를 파일 시스템에서 직접 봅니다. 모두 하니스가 확인했으면 `verified`, 사람의 확인이 들어 있으면 `confirmed`입니다.
3. 둘 다 없고 물어볼 사람이 있으면 "결과가 맞나요?"를 묻습니다. 맞다고 답하면 `confirmed`이고, 아니라고 답하면 그 말을 모델에게 돌려주고 계속합니다.
4. 물어볼 사람도 없으면 `claimed`입니다.

### 등록

`verified`나 `confirmed`로 끝난 실행에 질문과 답이 있었거나 헛걸음이 있었던 단계가 있으면, 모델이 그 내용을 지식 항목의 초안으로 정리하고 사람에게 보여 줍니다. 항목마다 승인, 고쳐서 승인, 거절을 고르고, 승인한 것만 저장됩니다. 답이 없으면 아무것도 저장하지 않습니다. 지식을 따른 동작이 실패한 뒤 새 답을 받았으면 그 항목을 고치는 안이 나옵니다.

헛걸음이 있었던 단계는 완료한 단계 가운데 다음 중 하나가 있었던 것입니다: 기대와 다른 결과, 창을 열었다가 그 안에서 아무것도 하지 않고 닫거나 떠남, 화면을 두 번 이상 살핌, 한도 질문. 이런 단계에서 나온 항목은 "스스로 알아냄"으로, 질문에서 나온 항목은 "질문에서"로 표시되고, 저장된 항목의 `source.origin`에 `discovered`나 `question`으로 남습니다. 질문도 헛걸음도 없던 실행은 초안을 만들지 않습니다. 항목에 업무 값이 들어가지 않게 하는 것은 모델에게 준 지시뿐이므로, 승인하는 사람이 글을 읽고 확인합니다.

### 그림 입력

캡처를 모델에게 주는 방법은 작업 파일의 `image_mode`로 정합니다. `user_message`(기본값)는 도구 결과 뒤에 그림이 든 사용자 메시지를 붙이고, `tool_output`은 도구 결과 안에 그림을 넣고, `off`는 그림을 보내지 않습니다. 엔드포인트가 그림을 받지 않으면 `off`로 두고 표시 번호, `find_cells`, `click_part`로 진행합니다. 캡처를 자르고 번호 박스를 그리는 데 Pillow를 쓰며, 없으면 창 캡처를 그대로 보냅니다.

### 텍스트 모델과 비전 모델 나눠 쓰기

`VISION_MODEL`(또는 설정 파일의 `vision_model`)을 넣으면 그림을 받지 않는 텍스트 모델로 실행하고, 그림이 필요한 곳에서만 하니스가 비전 모델에게 질문 하나와 그림 한 장을 보냅니다. 이때 `image_mode`는 무시하며, 기본값이 아니면 시작 줄에 `image_mode 무시(나눈 방식)`이 붙습니다.

- `look`은 `question`을 받습니다. 하니스가 캡처를 찍어 비전 모델에게 묻고, 결과의 `vision`에 답(`answer`), 가리킨 번호(`marks`), 번호 없는 대상의 캡처 픽셀(`points`), 확신 없음(`unsure`)을 넣습니다. 캡처에 그려지지 않은 번호와 캡처 밖의 점은 버립니다.
- 기대와 다른 결과나 확인할 수 없는 결과 뒤에는 동작 전 대상 주변을 잘라 찍고, 대상의 상태를 하니스가 정한 질문으로 묻습니다. 비전 모델에게는 상태를 말하게만 하고, 기대대로 됐는지는 텍스트 모델이 그 답과 기대를 비교해 판단합니다. 비전 호출이 실패해도 동작 결과는 그대로이고 `vision.error`만 붙습니다.
- 비전 모델은 추론이 약하므로 판단은 모두 텍스트 모델이 합니다. 텍스트 모델에게는 다시 관찰하기, `find_cells`, `[n]` 번호로 먼저 확인하고 그것으로 알 수 없는 것만 `look`으로 물으라고 안내합니다.
- 텍스트 모델은 `marks`로 `click_part`를, `points`로 `click_point`를 부릅니다. `points`로 고른 클릭도 지금처럼 사람의 확인을 받습니다.
- 비전 모델의 토큰은 실행의 토큰 예산에 더하고, 단계의 모델 호출 수에는 넣지 않습니다.
- 비전 호출은 Responses API의 사용자 메시지 하나(`input_text`와 `input_image`, `detail: high`)이고 도구를 주지 않습니다. 그림의 긴 변이 `vision_max_side`보다 크면 줄여 보내고, 받은 좌표를 원래 캡처의 픽셀로 되돌립니다.

비전 모델이 좌표를 어떤 방식으로 내는지는 모델마다 다르므로, 처음 쓸 때 `python check.py --skip app`의 `비전 좌표`가 권하는 값을 `vision_points`에 적습니다.

## workflow 만들기와 재실행

모델 실행이 `verified`나 `confirmed`로 끝나면 그 기록에서 workflow를 만들어 저장합니다. workflow는 모델 없이 다시 실행하는 단계 목록이고, 바뀌는 값은 파라미터로 받습니다. 설계는 [docs/specs/2026-11-19-workflow-design.md](docs/specs/2026-11-19-workflow-design.md)에 있습니다.

```powershell
python run.py --workflows [--system <이름>]                 # 이 시스템의 workflow 목록
python run.py --workflow w-20261119-001 --param shop=WA0,WA1 --param save_path=C:\out\a.xlsx
python run.py --make-workflow <run_id|latest>               # 지난 실행에서 다시 만들기(모델 호출)
```

### 만들기

- **언제:** 성공한 모델 실행의 끝에 자동으로 한 번 합니다. 사람에게 묻지 않고, 만들지 못해도 실행 결과는 바뀌지 않습니다. 끝의 출력에 `workflow: w-… (미확인, 단계 N, 파라미터 M)`이나 `workflow를 만들지 못했습니다: <코드>` 한 줄이 나옵니다.
- **파라미터 후보:** 모델이 `plan`을 낼 때 `params`에 지시에서 온 값 가운데 다음 실행에서 바뀔 수 있는 것을 이름과 함께 적습니다. 이름은 영문 소문자로 시작하는 `a-z`, `0-9`, `_`입니다.
- **모델이 하는 일:** 한 번 더 불려, 남길 동작과 묶을 동작, 파라미터의 자리를 기록의 번호로만 가리킵니다. 대상의 역할이나 이름을 글로 적는 자리가 없어 없는 대상을 지어낼 수 없습니다.
- **하니스가 하는 일:** 대상과 확인 조건을 기록에서 채우고, 만든 대상 적기를 그 동작 직전의 관찰에 다시 대 봅니다. 정확히 그 요소 하나가 나오지 않으면 저장하지 않습니다.
- **대상 적기:** 좌표, 표시 번호, ref, 창 id를 쓰지 않습니다. 범위(본 창이나 "N번 단계가 연 창"), 역할, 이름으로 적고, 이름이 없거나 같은 요소가 여럿이면 가까운 글자를 기준으로 "같은 줄의 n번째"처럼 적습니다. 실행 중에 바뀐 글(칸의 값)은 기준으로 쓰지 않습니다.
- **조작하지 않은 값:** 지시에는 있었지만 실행이 건드리지 않은 값은 파라미터로 받지 않고 "바꿀 수 없는 값"으로 남깁니다.
- **ID:** 그 시스템의 [프로파일](#시스템-프로파일)에 `stable_ids: true`가 있을 때만 대상에 ID를 적습니다. ID는 역할과 이름에 더해지는 조건이고(`id`, 담긴 영역 `in`), 이름을 대신하지 않습니다. 이름이 파라미터인 대상에는 적지 않고, 담긴 영역의 이름이 실행 중 바뀐 글이면 `in`을 적지 않습니다. 글자가 그림으로만 그려진 메뉴처럼 이름도 가까운 글자도 없는 대상은 ID가 있어야 workflow가 만들어집니다(없으면 `LOCATOR_NOT_UNIQUE`). 재실행은 `id`가 적힌 대로 찾고, ID가 달라졌으면 `TARGET_NOT_FOUND`로 멈춥니다.
- **그림뿐인 대상:** 캡처의 픽셀을 눌러야 했던 동작은 옮기지 못합니다. 그런 동작이 필요한 실행에서는 만들지 않습니다(`PICTURE_TARGET`).

만들지 못한 이유는 코드로 남습니다: `RUN_NOT_FOUND`, `RUN_NOT_SUCCESSFUL`, `NO_PLAN`, `RECORD_TOO_OLD`(표시 번호가 없는 옛 기록), `MODEL_NO_DRAFT`, `DRAFT_INVALID`, `LOCATOR_NOT_UNIQUE`, `PICTURE_TARGET`.

### 재실행

재실행은 모델을 부르지 않으므로 API 키가 필요 없습니다. 준비 신호가 있으면 준비 기다리기부터 하고, 항상 앱의 최초 화면에서 시작합니다.

- **단계마다:** 대상을 찾고, 기록된 도구로 동작하고, 확인 조건을 봅니다. 대상이 없으면 15초까지 다시 읽고, 둘 이상이면 바로 멈춥니다. 확인 조건도 15초까지 다시 읽습니다.
- **`select_only`(이것만 선택):** 목록에서 준 값만 선택된 상태로 맞춥니다. 체크 상태가 트리에 보이면 그것을 읽어 다른 것만 바꾸고, 보이지 않으면 "전체 선택"을 누른 뒤 값에 없는 줄을 하나씩 눌러 해제합니다. 뒤의 경우 최종 상태를 글로 다시 읽지 못하고, 누를 때마다 그 줄의 그림이 바뀌었는지만 확인합니다.
- **저절로 닫히는 창:** 조회의 진행 창처럼 원래 실행에서 저절로 닫힌 창이 있던 단계는, 그런 창이 떠 있는 동안 180초까지 기다린 뒤 내용이 바뀌었는지 봅니다.
- **멈춤:** 확인 조건이 깨지거나 모르는 창이 뜨면 그 단계에서 멈추고 코드를 남깁니다. 모델이 이어받지 않고, 대상 앱은 닫지 않습니다.
- **값:** `list`는 쉼표로 나눕니다. 주지 않은 파라미터는 원래 실행의 값을 씁니다. 저장 경로(`path`)만 다릅니다: 주지 않으면 원래 폴더에 실행 ID를 붙인 새 이름으로 저장하고, 준 경로는 절대 경로이고 폴더가 있어야 하며 이미 있는 파일이면 거절합니다. 값은 기록 폴더를 만들기 전에, 앱을 띄우기 전에 검사합니다(종료 코드 2).
- **결과:** 끝까지 통과하면 `verified`(종료 코드 0)이고 workflow의 상태가 "미확인"에서 "확인됨"으로 바뀝니다. 멈추면 `stopped`(종료 코드 1)이고 실패 횟수만 오릅니다. `run.json`의 `started_by`와 `model`은 `workflow`입니다.

| 때 | 코드 |
| --- | --- |
| 시작 전 | `WORKFLOW_NOT_FOUND`, `WORKFLOW_INVALID`, `SYSTEM_MISMATCH`, `PARAM_UNKNOWN`, `PARAM_INVALID`, `FILE_EXISTS`, 준비 기다리기의 `READY_*` |
| 실행 중 | `APP_GONE`, `TARGET_NOT_FOUND`, `TARGET_AMBIGUOUS`, `TARGET_OFFSCREEN`, `ACTION_FAILED`, `EXPECT_UNMET`, `UNEXPECTED_WINDOW`, `PARAM_VALUE_NOT_FOUND`, `WAIT_TIMEOUT`, `FILE_NOT_SAVED`, `STOPPED_BY_USER` |

재실행은 질문 정책과 반복 동작 가드를 쓰지 않습니다. 정해진 단계를 한 번 도는 실행이고, 목록마다 같은 이름의 요소를 누르기 때문입니다. 권한 단계와 대상 프로세스 고정은 그대로입니다.

### workflow 파일

`workflows\<시스템>\w-YYYYMMDD-NNN.yaml`에 저장합니다. 화면의 글이 들어 있으므로 Git에서 제외되어 있습니다. 폴더는 `--workflow-dir` > 설정의 `workflow_dir` > 환경변수 `AGENT_WORKFLOW_DIR` > 기본 폴더 순서로 정합니다. 읽을 때마다 형식을 검사해서, 모르는 키나 좌표, 표시 번호, ref, 창 id가 있으면 실행하지 않습니다(`WORKFLOW_INVALID`). 깨진 파일은 목록에서 빠집니다.

### 지금 못 하는 것

- 트리에 요소가 없는 그림뿐인 대상(우클릭 원형 메뉴, 트리에 보이지 않는 아이콘).
- 스크롤해야 보이는 대상과 긴 목록.
- 조건 분기와 반복, 지난 workflow 고치기.
- 조회 단계에서 닫히지 않는 알림 창이 뜨면 "모르는 창"으로 바로 멈추지 않고 180초 뒤 `WAIT_TIMEOUT`으로 멈춥니다.

## 실행 기록

실행마다 `runs\<YYYYMMDD-HHMMSS>\`에 기록이 남습니다.

| 파일 | 내용 |
| --- | --- |
| `run.json` | 지시, 실행 파일, 모델, 권한 단계, 시작 방법, 최대 스텝, 실행할 때의 코드 버전, 상태(`running`에서 최종 상태로), 시작·끝 시각, 기록하는 프로세스와 10초마다 갱신하는 살아 있음 표시, 끝난 실행의 단계 수(`stages`: 단계 수, 완료 수, 단계별 호출 수, 한도 질문 수, 계획을 고친 수, 호출당 토큰의 최댓값), 비전 모델을 썼는지(`vision`, 참·거짓)와 나눈 방식의 비전 호출 수·토큰(`vision_calls`, `vision_tokens`), 준비 기다리기의 결과(`ready`: 상태 코드, 기다린 초, 대상 프로세스가 바뀌었는지, 읽는 방식, 확인한 바퀴 수, 읽기 수와 실패 수, `find`의 시간 초과 수, 가장 긴 읽기의 ms. 준비 신호의 글과 ID는 없음), workflow를 만든 결과(`workflow`: 만들었는지, ID, 코드), 재실행의 결과(`workflow_run`: ID, 단계 수, 끝낸 단계 수, 코드) |
| `summary.txt` | 화면 내용이 없는 실행 요약(아래 "실행 요약") |
| `events.jsonl` | 관찰(요소 종류별 수 포함), 동작(기대와 실제 변화 포함), 모델 호출(호출의 토큰, 그때의 단계와 호출 수), 계획과 단계의 시작·완료·한도·중단, 승인 제안·결정, 질문과 답, 캡처, 비전 모델의 질문과 답, 쓴 지식, 완료 판정, 등록 결과, 준비 기다리기의 시작과 끝(`ready`), 저장한 경로(`finish_note`), workflow를 만든 결과(`workflow`), 재실행의 단계별 결과(`workflow_step`: 단계 번호, 종류, 통과 여부, 코드, 걸린 시간, 목표), 종료를 한 줄에 하나씩. 관찰의 요소마다 표시 번호(`mark`)와 속한 팝업 창(`scope`)이 있고, ID가 있는 요소에는 ID(`native_id`)와 담긴 영역(`in`), 등록 이름(`alias`)이 있음 |
| `frames\NNNN.png` | 관찰마다 찍은 대상 창 스크린샷(겹친 팝업 창을 붙임, 아래 박스 좌표 참고) |
| `captures\cN.png` | 모델에게 보낸 캡처(`look`, 기대와 다른 결과, 질문이 필요한 거절). 나눈 방식에서는 비전 모델에게 보낸 캡처 |

관찰마다 창 스크린샷을 한 장 찍으므로 스텝마다 약 1초가 더 걸립니다. 기록에는 화면 내용과 UI 텍스트, 질문과 답이 그대로 들어가므로 민감 정보로 다루세요. `run.json`에는 질문, 답, 지식의 글, 단계의 글(목표, 완료 기준, 메모)을 넣지 않지만, 지시와 모델이 쓴 완료 문장(`reason`)은 들어가고 그 문장에 화면의 글이 섞일 수 있습니다. 기록 폴더 밖으로 전할 때는 아래의 실행 요약만 씁니다. `runs\`는 Git에서 제외되어 있습니다. 관찰한 창 제목과 UI 텍스트, 캡처, 지식 항목, 질문과 답은 모델 API로도 전송됩니다.

### 실행 요약

실행이 끝나면 화면 내용이 없는 요약이 출력되고 `runs\<id>\summary.txt`로도 남습니다. 뷰어에서 시작한 실행도 같습니다. 기록을 가져올 수 없는 PC의 결과를 전할 때 이 요약을 씁니다.

```
요약 (화면 내용 없음)
  코드: 284f163
  판정: gave_up · 스텝 14/60 · 토큰 31200
  준비: ready · 12초 · snapshot · 확인 9바퀴 · 읽기 14회(실패 2, 시간 초과 0, 최대 2.1초) · 대상 바뀜
  마지막 동작: [14] click_point → needs_confirmation
  동작: 12회 · 기대 지정 9 · 일치 5 · 불일치 3 · 확인 못 함 1
  거절: needs_confirmation 2 · blocked_until_question 1
  오류 코드: STALE_REF 1 · TIMEOUT 2
  질문: 3 · 답 2 · 무응답 1
  단계: 4 · 완료 2 · 단계별 호출 3/9/2/0 · 한도 질문 1 · 계획 고침 0
  호출당 토큰 최대: 9120
  비전 호출 5 · 비전 토큰 4100
  workflow: 못 만듦 · LOCATOR_NOT_UNIQUE
  지식: 불러옴 4 · 참고 2 · 참고 뒤 실패 1
  마지막 관찰: 이름 있는 ref 12 · 이름 없는 ref 3(id 있음 2) · 글자 40 · 빈 영역 2 · 잘림 없음
```

요약에는 수, 도구 이름, 코드, 판정만 들어갑니다. 지시, 화면의 글, 요소 이름, 질문과 답, 지식 내용, 경로는 들어가지 않습니다. 코드나 도구 이름 모양이 아닌 값은 `기타`로 나옵니다. `코드`는 실행할 때의 커밋이고, 커밋하지 않은 수정이 있으면 `+수정`이 붙습니다. 기록에 없는 값은 `알 수 없음`으로 나오거나 줄이 빠집니다. `단계` 줄은 계획을 세운 실행에만 나오고, 단계의 수는 실행이 끝날 때 기록되므로 끊긴 실행에는 `단계`와 `호출당 토큰 최대` 줄이 없습니다. `비전 호출` 줄은 비전 모델을 쓴 실행이 끝났을 때만 나옵니다. `준비` 줄은 준비 신호를 기다린 실행에만 나오고, 읽는 방식, 확인한 바퀴 수, 읽기 수(실패한 수, `find`가 제한 시간에 걸린 수, 가장 오래 걸린 읽기)를 함께 냅니다. 이 수를 남기기 전의 기록은 `ready · 12초 · 대상 바뀜`으로 나옵니다. `workflow` 줄은 workflow 만들기를 시도한 모델 실행에 나오고(`만듦 w-… · 단계 N · 파라미터 M` 또는 `못 만듦 · <코드>`), 재실행에는 `재실행: w-… · 단계 5/12 · EXPECT_UNMET` 줄이 나옵니다(통과하면 코드 자리에 `통과`). 단계의 목표, 파라미터의 이름과 값, 저장 경로는 요약에 들어가지 않습니다.

```powershell
python view.py --summary latest          # 지난 실행의 요약을 기록에서 다시 만듦
python view.py --summary <run_id>
```

뷰어에서는 실행 화면의 "실행 요약 보기"로 같은 글을 보고 "요약 복사"로 복사합니다.

## 스텝 뷰어

`run.py`에 `--view`를 붙이면 실행할 때마다 뷰어가 브라우저로 열리고 그 실행을 실시간으로 따라갑니다. 실행이 끝나도 Enter를 누를 때까지 뷰어가 남아 있어 스텝을 돌려 볼 수 있습니다.

```powershell
python run.py --exe "C:\절대\경로\App.exe" --goal "5분봉으로 바꿔줘" --view
```

기록을 보거나 브라우저에서 새 실행을 시작하려면 뷰어만 띄웁니다.

```powershell
python view.py --exe "C:\절대\경로\App.exe"
```

브라우저에 뷰어가 열립니다. 주소에 실행할 때마다 새로 만든 토큰이 붙고, 서버는 `127.0.0.1`에서만 받습니다. 주소를 다른 사람과 공유하지 마세요.

- **패널:** 왼쪽부터 실행 목록, 대화, 캡처, 스텝 정보입니다. 패널마다 제목 줄의 버튼으로 접고 펴며, 접으면 좁은 띠가 되고 캡처가 그만큼 넓어집니다. 실행 목록은 실행을 지정해 열면 접힌 채로 시작합니다. 접은 상태는 그 브라우저에 저장됩니다.
- **재생:** 실행 목록에서 실행을 고르면 스텝마다 스크린샷 위에 박스를 그립니다. 스텝은 타임라인의 한 칸으로, 동작이나 질문 하나입니다. 파란 테두리는 에이전트가 조작할 수 있다고 인식한 요소, 회색 점선은 모델이 읽은 텍스트(ref 없음, 관찰 하나에 400개까지), 빨간 테두리는 조작한 대상입니다. 박스에 마우스를 올리면 역할, 이름, 설명이 나오고, ID와 등록 이름이 있으면 그것도 나옵니다. 오른쪽 스텝 정보에 모델이 적은 동작 이유(`intent`), 도구와 인자, 전달 결과, 기대한 변화와 일어난 변화, 기대 판정(기대대로, 기대와 다름, 확인 못 함), 모델이 받은 관찰 텍스트가 나옵니다. 관찰하는 창이 바뀐 동작은 그 사실이 함께 나옵니다. 나눈 방식의 실행에서는 "비전 모델의 답" 카드에 비전 모델에게 보낸 캡처와 질문, 답, 가리킨 점이 나옵니다. 비전 모델을 쓴 스텝은 타임라인 칸과 스텝 정보 제목에 파란 `비전` 표시가 붙고(마우스를 올리면 `look 질문`, `동작 뒤 불일치` 같은 이유), 실행 정보 줄에 `비전 N회`가 나오며, `V`로 다음 비전 스텝으로 갑니다. 모델이 부른 `look`도 타임라인의 한 칸입니다.
- **키:** `←` `→`로 스텝을 옮기고, `B`로 동작 전·후 화면을, `A`로 전체 요소·대상만을, `T`로 텍스트 박스 표시를 바꾸고, `V`로 다음 비전 스텝으로 갑니다.
- **새 실행:** 위쪽에 지시를 넣고 실행합니다. 실행 파일, 권한 단계, 시스템(비우면 실행 파일 이름), 단계별 호출 한도(비우면 기본값), 동작 전 승인은 "설정" 버튼을 눌러 펴서 정하고, 접혀 있을 때는 지금 값이 옆에 요약으로 보입니다. 설정 파일에 `systems`가 있으면 실행 파일 칸 자리에 시스템 목록이 나오고(경로는 브라우저로 보내지 않음), 목록 끝 "직접 입력"을 고르면 지금의 실행 파일·시스템 칸이 나옵니다. 실행하면 진행 중인 스텝이 1초마다 붙습니다. 준비 신호를 기다리는 동안에는 "대상 앱 준비 중"과 지난 초가 보입니다. 한 번에 하나만 실행할 수 있습니다. 뷰어에서 시작한 실행은 터미널 확인을 받을 수 없으므로 `restart_target`이 항상 거부됩니다.
- **단계 줄:** 계획을 세운 실행은 캡처 위에 단계가 한 줄로 나옵니다. 칸마다 번호, 목표, 상태(대기, 진행 중, 질문 중, 완료, 중단), 쓴 호출 수와 한도(`3/8`)가 있고, 완료한 단계에는 체크 표시가 붙습니다. 지난 스텝을 보면 그 시점의 상태로 바뀝니다. 칸을 누르면 그 단계의 첫 스텝으로 옮기고, 아래 줄에 목표, 완료 기준, 완료한 단계의 근거와 메모가 나옵니다. 타임라인에는 단계가 바뀌는 자리에 "단계 n" 표시가 붙고, 계획을 고치면 대화 칸에 "계획을 고침"이 남습니다. 계획이 없는 기록에는 단계 줄이 없습니다.
- **승인:** 승인 모드로 시작하면 동작마다 대상을 노란 박스로 보여 주고 승인이나 거부를 기다립니다. 600초 동안 답이 없으면 실행을 멈춥니다.
- **질문과 답:** 에이전트가 물으면 캡처 왼쪽의 대화 칸에 질문이 뜨고(접혀 있으면 펴짐), 칸 바닥에 답 양식이 나옵니다. 스크린샷에 후보가 번호 박스로 나옵니다. 제안한 후보는 빨간 실선, 다른 후보는 점선, 판단의 근거는 노란 채움입니다. 번호나 글로 답하거나, 스크린샷을 눌러 위치를 찍어 답합니다. 완료 확인은 맞음·아님으로, 등록은 항목마다 승인·고쳐서 승인·거절로 답하고, 항목에는 출처(질문에서, 스스로 알아냄)가 표시됩니다. 단계의 호출 한도나 계획 고치기 횟수에 닿아 묻는 질문에는 "계속", "방법 보내기"(적은 글을 모델에게 전하고 계속), "중단"으로 답합니다. `run.py --view`로 띄운 뷰어에서는 질문을 보기만 하고 답은 터미널에서 합니다.
- **지식:** 위쪽의 "실행 | 지식"에서 지식을 고르면 시스템별 항목이 나옵니다. 글을 고치고, 사용을 멈추거나 다시 쓰고, 지울 수 있습니다. 완료 조건의 확인 방법은 파일에서 고칩니다. `--knowledge-dir`로 다른 지식 폴더를 봅니다.
- **workflow:** 위쪽에서 "workflow"를 고르면 고른 시스템의 workflow가 카드로 나옵니다. 카드에는 ID, 상태(미확인, 확인됨), 통과와 실패 횟수, 지시, 파라미터 칸(이름, 종류, 원래 값), "바꿀 수 없는 값"이 있습니다. 값을 넣고 "재실행"을 누르면 모델 없이 실행하고 그 실행의 화면으로 넘어갑니다. 값이 틀리면 실행하지 않고 코드와 이유를 보여 줍니다. 재실행한 기록은 타임라인의 칸에 workflow 단계 번호(`W3`)가 붙고, 스텝 정보에 단계의 목표와 통과 여부, 멈춘 코드가 나옵니다. 모델 실행이 끝나면 실행 정보 줄에 만든 workflow의 ID나 만들지 못한 코드가 나옵니다. 횟수는 "새로고침"을 눌러야 바뀝니다. `--workflow-dir`로 다른 workflow 폴더를 봅니다.
- **등록:** 위쪽에서 "등록"을 고르면 시스템의 준비 신호와 요소의 등록 이름을 화면에서 골라 프로파일로 저장합니다. [등록 화면](#등록-화면)에서 설명합니다. `view.py`로 띄운 뷰어에만 있고, `--profile-dir`로 다른 프로파일 폴더를 씁니다.
- **경고 띠:** 스크린샷을 찍지 못했거나 찍는 사이 창이 움직였으면 박스가 어긋날 수 있다고 표시합니다.

`--runs`로 다른 기록 폴더를 볼 수 있고, `--no-browser`는 주소만 출력합니다. `agent-desktop` 바이너리가 없으면 기록 보기만 합니다.

### 멈추기와 끄기

- **실행 멈춤:** 위쪽 오른쪽 버튼입니다. 화면 안 띠에서 확인하면 실행이 다음 안전한 자리(모델 호출 전, 도구 실행 전, 질문·승인·준비 대기 중)에서 멈춥니다. 진행 중인 모델 호출이나 CLI 명령은 끊지 않고 끝난 직후에 멈추며, 그동안 버튼에 "멈추는 중…"이 보입니다. 기록은 `stopped`와 "사용자가 실행을 멈췄습니다"로 끝나고 요약도 남습니다. 대상 앱은 닫지 않으므로, 같은 시스템을 다시 실행하기 전에 직접 닫습니다.
- **뷰어 종료:** 실행 중이면 띠에서 "멈추고 종료"를 확인받고, 실행을 마무리한 뒤(최대 120초) 서버를 닫습니다. 화면에는 "뷰어를 종료했습니다"가 남습니다. `view.py`로 띄운 뷰어에만 있습니다.
- **Ctrl+C:** 종료 버튼과 같이 정리합니다. 실행 중이면 마무리를 기다리고, 한 번 더 누르면 기다리지 않고 바로 끕니다. Ctrl+Break도 같습니다.
- **다시 열기:** 포트는 다른 프로세스와 겹쳐 열지 않습니다. 같은 포트에 이 저장소의 옛 뷰어가 남아 있으면(기록 폴더의 `.viewer.json`으로 알아봄) 쉬는 중일 때 끄고 그 포트로 엽니다. 옛 뷰어가 실행 중이거나 다른 프로그램이 포트를 쓰면 다음 빈 포트(최대 20개)로 열고 알립니다.
- **남은 뷰어 끄기:** `python view.py --stop`은 기록 폴더의 표시 파일이 가리키는 뷰어에 실행을 멈추고 종료하라고 요청합니다. 터미널 창을 그냥 닫아 뷰어가 남았을 때 씁니다.

### 지난 실행 보기

뷰어는 `run.py`가 돌고 있지 않아도 `runs\`의 기록을 모두 보여 줍니다. 실행 하나를 바로 열려면 `--open`에 실행 ID나 `latest`를 줍니다.

```powershell
python view.py --open latest
python view.py --open 20261107-132854
```

- **찾기:** 목록은 날짜별로 묶이고, 위쪽에서 지시나 실행 파일 이름으로 검색하거나 상태와 날짜로 거를 수 있습니다. 항목마다 판정, 스텝, 토큰, 걸린 시간, 시작 방법이 나옵니다.
- **중단됨:** `running`으로 남은 기록 중 기록하던 프로세스가 없거나, 같은 PID가 다른 프로세스에 쓰였거나, 살아 있음 표시가 60초 넘게 멈춘 것은 "중단됨"으로 보입니다. 강제 종료, Ctrl+C, PC 재시작으로 끊긴 실행입니다. 뷰어는 기록 파일을 고치지 않습니다.
- **바뀐 점:** 동작 스텝에 동작 전후 화면에서 생긴 요소, 사라진 요소, 상태(`checked` 등)나 값이 바뀐 요소가 나옵니다. 동작 후 화면에서는 바뀐 요소를 초록 박스로, 동작 전 화면에서는 사라진 요소를 빨간 점선으로 표시합니다. 요소 상태가 기록되기 전의 기록은 생김과 사라짐만 보입니다.
- **실행 요약:** 타임라인 위에 지시, 판정과 판정 방식(하니스가 확인, 모델 주장만 등), 걸린 시간, 스텝, 토큰, 승인·거부 수가 나옵니다.
- **옛 로그:** 기록 형식이 생기기 전의 `runs\<id>.jsonl`은 "옛 로그"로 보이고, 스크린샷 없이 스텝별 도구, 인자, 결과만 나옵니다.

### 기록 정리

오래된 기록은 자동으로 지우지 않습니다. `--prune`은 지울 기록과 용량을 출력만 하고, `--yes`를 붙여야 지웁니다. 지운 기록은 휴지통을 거치지 않으므로 되돌릴 수 없습니다.

```powershell
python view.py --prune --older-than 30d     # 30일보다 오래된 기록을 보여 주기만 함
python view.py --prune --keep 100 --yes     # 최신 100개만 남기고 영구 삭제
```

`--older-than`과 `--keep` 중 하나만 줍니다. 뷰어 목록이나 실행 요약에서 ☆를 눌러 보관한 기록(기록 폴더에 `keep` 파일이 생김), 실행 중인 기록, 읽을 수 없는 기록, 링크나 정션은 지우지 않고 이유와 함께 건너뜁니다. 상태 필터의 "보관"으로 보관한 기록만 볼 수 있습니다.

### 한 파일로 내보내기

```powershell
python view.py --export latest C:\공유\run.html
```

실행 하나를 스크린샷까지 HTML 파일 하나로 묶습니다. 서버 없이 브라우저에서 열리고 그 실행만 재생합니다. 토큰과 서버 주소는 들어가지 않지만 앱 화면, UI 텍스트, 실행 파일 경로는 그대로 들어가므로 보내기 전에 확인하세요. 이미 있는 파일은 덮어쓰지 않습니다.

### 박스 좌표

UIA 요소 영역과 `list-windows` 창 영역은 물리 화면 픽셀이고, 창 영역에는 보이지 않는 테두리가 포함됩니다. 창 스크린샷은 보이는 부분만 찍으므로, 스크린샷 왼쪽 위의 화면 좌표를 다음처럼 구합니다.

```text
border = (창 너비 - 이미지 너비) / 2
원점   = (창 x + border, 창 y + (창 높이 - 이미지 높이) - border)
```

요소 박스는 화면 좌표에서 원점을 빼서 이미지 좌표로 바꾸고, 이미지 밖은 잘라냅니다. 175% 주 모니터의 일반 창(테두리 10px)과 최대화 창(테두리 12px, 원점 0,0), 125% 보조 모니터의 창(테두리 8px)에서 FootprintChart와 메모장으로 확인했습니다.

팝업 메뉴나 선택 칸의 목록은 같은 프로세스의 다른 최상위 창이라 관찰한 창의 스크린샷에 나오지 않습니다. 그래서 관찰 그림(`frames`)과 모델 캡처(`captures`)는 그런 창을 하나씩 `screenshot --window-id`로 찍어 위 원점 계산대로 화면 위치에 붙인 한 장입니다. 화면 전체는 찍지 않으므로 다른 앱은 들어가지 않고, 창이 없는 자리는 짙은 회색입니다. 붙이는 창은 보이고 최소화되지 않은 같은 pid·프로세스 인스턴스의 창 가운데, 관찰한 창이나 이미 붙인 창과 겹친 넓이가 둘 중 작은 창 넓이의 25% 이상이거나, 왼쪽 위 모서리가 그 창 안쪽으로 가장자리에서 24px 이상 들어와 있는 창입니다. 그래서 창 아래쪽 칸에서 열려 대부분이 창 밖으로 넘친 목록도 들어오고, 팝업 위의 팝업도 따라 들어옵니다. 옆 모니터에 최대화한 창은 보이지 않는 테두리로 몇 픽셀만 겹치므로 들어오지 않습니다. `list-windows`는 최상위 창을 화면의 위에서 아래 순서로 주므로(Windows의 `EnumWindows` 순서), 관찰한 창도 그 순서의 제자리에 두고 아래부터 붙입니다. 관찰한 창이 팝업이어도 아래의 본 창이 팝업을 덮지 않습니다. `click_point`와 `click_part`는 누를 지점에서 그림의 맨 위에 그려진 창을 대상으로 누르고(창 밖으로 넘친 팝업의 요소도 팝업 창으로 누름), 캡처 뒤 그림 속 창 하나라도 움직이거나 닫히면 그 캡처의 지점을 누르지 않습니다.

한계: 관찰한 창과 겹치지 않는 곳에 뜬 같은 앱의 창(화면 가운데에 뜨는 대화 상자 등)은 그림에 들어가지 않습니다. 그 창을 관찰하면 그 창이 중심이 됩니다. 붙인 창의 스크린샷이 실패하면 그 창만 빼고 관찰 이벤트의 경고(캡처는 `look` 결과의 `windows_left_out`)에 수를 적습니다.

## 작업 파일

```yaml
goal: 에이전트에게 줄 목표
exe: C:\절대\경로\App.exe
permission_level: 3
success:
  require:
    - {role: switch, description_contains: 설정 패널, states: [checked]}
    - {role: statictext, name: 지표}
baseline_target: {role: switch, description_contains: 설정 패널}
```

대상 프로세스의 창 하나에 `require`의 요소가 모두 있어야 성공입니다. 요소 조건은 `role`, `name`, `name_contains`, `description_contains`, `states`를 쓸 수 있습니다. `success`는 생략할 수 있고, 그러면 [완료 판정](#완료-판정)의 2번부터 적용됩니다. 선택 항목의 기본값은 `max_steps: 12`, `token_budget: 600000`, `model: gpt-6.1-terra`, `reasoning_effort: low`, `plan_reasoning_effort: medium`, `stage_call_limit: 8`, `image_mode: user_message`, `ask_timeout_s: 1800`, `mismatch_limit: 2`입니다. `plan`과 `stage_done`도 `max_steps`에 세므로, 단계가 여럿인 작업은 `max_steps`를 넉넉히 둡니다. `system`과 `knowledge_dir`로 지식의 시스템 이름과 폴더를 정할 수 있습니다. 질문만 한 모델 차례는 `max_steps`에 세지 않습니다.

## 권한 단계

| 단계 | 추가되는 도구 | 앱에 미치는 영향 |
| --- | --- | --- |
| 0 | `launch_target`, `list_windows`, `observe`, `wait_for_text`, `look`, `find_cells`, `ask`, `plan`, `stage_done`, `restore_window`, `click`, `toggle`, `expand`, `collapse`, `finish` | 커서와 포커스를 가져가지 않음 |
| 1 | `set_value`, `select`, `check`, `uncheck`, `scroll`, `press` | `press`를 뺀 도구는 같음 |
| 2 | `type`, `double_click`, `right_click`, `mouse_click`, `mouse_wheel`, `drag`, `click_part`, `click_point` | 실제 커서와 포커스를 사용하며, 2단계부터 `press`도 포커스를 가져감 |
| 3 | `restart_target` | 실행 전 터미널에서 확인을 받고, 강제 종료는 하지 않음 |

## 하니스가 막는 동작

- `exe`와 경로가 같은 프로세스의 창만 다룹니다. 같은 이름의 다른 버전은 대상이 아닙니다.
- 다른 프로세스를 띄우고 끝나는 실행기는 대상으로 쓸 수 없습니다. 예를 들어 Windows 11의 `C:\Windows\System32\notepad.exe`는 WindowsApps의 `Notepad.exe`를 띄우므로, 에이전트가 창을 찾지 못하고 포기합니다. 실제 앱의 경로(`Get-Process Notepad | Select-Object Path`)를 지정하세요.
- 앱이 이전 세션을 복원하면(메모장의 지난 탭 등) 그 내용도 관찰에 포함되어 모델 API로 전송되고 기록에 남습니다.
- 최신 관찰에 없는 ref는 앱에 보내지 않습니다.
- 전달된 `toggle`은 같은 컨트롤에 다시 보내지 않습니다. `disposition.retry`가 `safe`가 아닌 실패도 반복하지 않습니다.
- 같은 동작이 3번 실행된 뒤 다시 요청되면 실행을 중단합니다.
- 좌표 입력은 점이 대상 창 안에 있고 그 창이 포커스를 얻었을 때만 보냅니다.
- 좌표를 직접 고른 클릭과, 표에서 후보가 여럿인 자리의 클릭은 사람의 답이나 지식 항목 없이는 보내지 않습니다. 기대와 다른 결과가 이어지면 질문에 답을 받을 때까지 앱을 바꾸는 도구를 막습니다([하니스가 묻게 하는 경우](#하니스가-묻게-하는-경우)).
- 화면 밖(`offscreen`)이거나 넓이가 없는 요소, 캡처한 뒤 창이 움직이거나 크기가 바뀐 캡처의 지점은 누르지 않습니다.
- 질문에 답이 없으면 추측하지 않고 실행을 멈춥니다.
- 계획(`plan`)이 없으면 앱을 바꾸는 도구를 보내지 않습니다(`launch_target` 제외). 끝나지 않은 단계가 있으면 성공으로 끝내지 않습니다. 단계의 호출 한도에 닿으면 사람의 답 없이 계속하지 않습니다([단계로 나눠 실행하기](#단계로-나눠-실행하기)).
- `press`에 `--force`를 붙이지 않으므로 CLI가 막는 단축키는 계속 막힙니다.

## 가상 MES 앱

`virtual-mes\`는 회사 MES의 화면과 조작 흐름을 흉내 낸 연습용 앱입니다. 컨트롤이 접근성 트리에 보이는 방식(ref, 글자만, 그림만)과 선택 칸이 열리는 방식(어디를 눌러도, 화살표로만)을 실행 옵션으로 바꿀 수 있어, 에이전트가 ref 없는 화면과 가운데 클릭이 통하지 않는 칸을 다루는지 시험할 수 있습니다. 묶음 헤더와 소계 행이 있는 표 화면도 있습니다. 회사 MES처럼 작은 팝업 뒤에 메인 화면이 뜨는 시작 과정도 옵션(`--splash-ms`, `--launcher`, `--menu-delay-ms`, `--single-instance`)으로 흉내 내어 [시스템 골라 띄우기](#시스템-골라-띄우기)를 시험할 수 있습니다. 빌드, 옵션, 이벤트 기록은 [`virtual-mes/README.md`](virtual-mes/README.md)에 있습니다.

```powershell
powershell -NoProfile -File virtual-mes\build.ps1
```

글자가 그림으로만 그려지고 ID만 있는 메뉴는 `--expose menu=idonly`(이름도 ref도 없음)나 `--expose menu=bare`(이름 없는 버튼)로 만듭니다. [시스템 프로파일](#시스템-프로파일)의 등록 화면과 등록 이름을 집에서 시험할 때 씁니다. 옵션과 메뉴의 ID 표는 `virtual-mes\README.md`에 있습니다.
