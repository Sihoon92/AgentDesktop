# CUA 배경과 설계 기준

이 예제(`examples/llm-agent`)를 사내 computer-use agent(CUA)로 키우는 작업의 배경입니다. 설계, 기능 추가, 회사에서 전해 온 현상을 해석할 때 이 문서를 기준으로 삼습니다. 확인되지 않은 내용은 "미확인"에 모아 두었고, 확인되면 그 자리에서 고칩니다.

## 왜 만드는가

회사에는 MES 데이터를 자동 조회하는 RPA 기반 API가 이미 있습니다. 관리자가 요청마다 workflow(예: `click '전공정 생산현황'` → `click ...`)를 플랜으로 기록해 두면, 사용자는 그 플랜 ID로 API를 호출해 데이터를 받습니다.

한계는 플랜 작성 공수입니다. 시스템마다 RPA를 새로 세우고 요청마다 사람이 플랜을 만들어야 해서, 전 임직원과 사내의 많은 시스템으로 넓힐 수 없습니다. CUA는 이 플랜 작성을 자연어 지시와 에이전트 실행으로 대체합니다.

기존 RPA의 workflow 형식과 등록 API에는 맞추지 않습니다. workflow 형식, 저장, 등록, 재실행기는 이 프로젝트에서 새로 설계합니다.

대상 MES는 Windows 설치형 앱입니다. 사내에는 브라우저로 쓰는 시스템도 있습니다(아래 "브라우저 앱").

## 서비스 흐름

1. **지시:** 사용자가 웹 브라우저에서 자연어로 지시합니다. 예: "전공정 생산현황 들어가서 Shop은 조립, 기간은 전일로 놓고 조회 누른 뒤 엑셀로 다운로드해 줘."
2. **관찰 표시:** 에이전트가 현재 화면을 캡처하고, 인식한 요소 박스를 화면 위에 그려 보여 줍니다.
3. **대상 표시:** 이번 단계의 대상(예: "전공정 생산현황")을 찾아 하이라이트 박스로 표시합니다.
4. **동작과 재관찰:** 동작(클릭 등)을 하고 다시 관찰합니다. 단계마다 캡처를 남겨 사용자가 진행 상황을 눈으로 따라갑니다.
5. **정정:** 동작이 의도와 다르면 사용자가 자연어로 고칩니다(예: "기간은 달력이 아니라 드롭다운에서 골라야 해"). 에이전트는 그 정정을 반영해 이어서 수행합니다.
6. **workflow 생성:** 작업을 끝내면 LLM 없이 재실행되는 RPA workflow를 자동으로 만들어 등록하고 ID를 돌려줍니다.
7. **반복 실행:** 이후에는 그 ID로 RPA가 빠르게 반복합니다. 바뀌는 값(Shop, 기간 등)은 파라미터로 넘길 수 있어야 합니다.

## 지금 코드와의 거리

| 흐름 | 지금 있는 것 | 없는 것 |

| 1 지시 | `run.py --goal`, 뷰어의 새 실행 입력 | 여러 사용자가 접속하는 웹 서비스, 인증 |
| 2–4 관찰·대상·재관찰 | `agent/loop.py`, `agent/recorder.py`, 뷰어의 요소·대상 박스와 단계 재생 | — |
| 5 정정 | 동작별 승인·거부(`--approve`, 뷰어 승인) | 실행 중 자연어 정정을 받아 계획을 고치는 경로 |
| 6 workflow 생성 | 실행 기록(`events.jsonl`, 프레임) | workflow 형식, 기록을 workflow로 바꾸는 변환, 등록 |
| 7 반복 실행 | `--baseline`(고정 순서, 작업 파일의 대상 하나) | 파라미터화한 workflow 실행, 실패 시 복구 |

## 일반화 기준

지금 대상은 MES지만 다른 사내 시스템으로 빠르게 넓히는 것이 목표입니다. 새 시스템마다 설정은 필요하다고 가정하되, 그 설정이 어디에 모이는지를 처음부터 정해 둡니다.

- **공통부와 시스템 프로파일을 나눕니다.** 관찰-동작 루프, 기록, 뷰어, 정정, workflow 변환은 시스템을 모르는 공통부입니다. 실행 방법, 로그인, 대상 창이나 URL, 메뉴 구조 힌트, 용어집(예: "전공정" ↔ 화면 표기), 성공 확인 조건 같은 시스템 고유 값은 시스템 프로파일 파일에 둡니다. 코드에 MES 이름이나 화면 배치를 분기로 넣지 않습니다. 저장소 전체의 같은 원칙이 `AGENTS.md`의 "fixes must be application-agnostic"입니다.
- **MES 전용인 것은 표시합니다.** MES에서만 통하는 가정(특정 그리드, 팝업 달력, 다운로드 경로 등)을 만들면 그 자리에서 "MES 프로파일 소관"으로 적고 프로파일로 옮길 수 있게 만듭니다.
- **관찰이 부족하면 에이전트가 스스로 압니다.** 접근성 트리에 대상이 없거나 이름이 비어 있으면(직접 그린 그리드, 캔버스, 이미지 버튼), 에이전트는 추측으로 누르지 않고 관찰 부족으로 판단해 관찰을 넓힙니다: 다른 표면이나 하위 트리 스냅샷, 스크롤 후 재관찰, 스크린샷 기반 판단. 어떤 수단으로도 대상을 특정하지 못하면 사용자에게 묻습니다. 관찰 부족 사례는 새 시스템을 붙일 때 프로파일에 무엇을 더 적어야 하는지 알려 주는 신호이므로 기록에 남깁니다.
- **workflow는 좌표가 아니라 요소로 기록합니다.** 단계마다 대상의 역할, 이름, 위치 경로와 그 단계의 확인 조건(다음 화면에 무엇이 보여야 하는지)을 저장합니다. 화면 해상도나 DPI가 달라도 재실행되어야 하고, 확인 조건이 깨지면 그 단계에서 멈추거나 LLM 복구로 넘깁니다.
- **파라미터는 기록 시점에 구분합니다.** 사용자 지시에서 바뀔 수 있는 값(Shop, 기간)과 고정 절차를 실행 중에 구분해 두어야 workflow에서 파라미터로 뺄 수 있습니다.
- **앱 조작 계층은 갈아 끼울 수 있게 둡니다.** 루프와 workflow는 "요소를 찾고, 동작하고, 확인한다"는 계약에만 의존하고, 그 계약을 `agent-desktop`(접근성 트리)로 채우는 구현을 기본으로 둡니다. 브라우저용 구현(아래)을 나중에 같은 계약 뒤에 붙일 수 있어야 하며, 어떤 구현을 쓸지는 시스템 프로파일이 정합니다.

## 브라우저 앱

`agent-desktop`은 브라우저 앱에도 쓸 수 있습니다. 웹 페이지 자동화 도구(DOM 조작, 페이지 이동 API)는 아니지만, Windows에서 Chrome과 Edge가 내보내는 UIA 트리를 읽으므로 웹 페이지 안의 버튼, 입력란, 링크도 ref로 관찰하고 조작합니다. 근거와 세부는 `skills/agent-desktop-windows/references/chromium-and-electron.md`입니다.

- **플래그 없이 보입니다.** Chromium 138 이상은 UIA 클라이언트가 붙으면 전체 트리를 만듭니다.
- **처음 읽으면 얇습니다.** 콜드 실행 후 트리가 다 차기까지 10~25초가 걸리므로 첫 스냅샷에 `--timeout-ms`를 넉넉히 주고, 얇으면 새 스냅샷을 찍습니다.
- **깊이가 깊습니다.** 이름 없는 그룹이 길게 중첩되어 기본 깊이에서 컨트롤이 안 보일 수 있습니다. `--max-depth`를 올리거나 경계 ref에서 `snapshot --root`로 내려갑니다.
- **이름 없는 요소가 많습니다.** 역할·AutomationId·설명이 같은 요소가 여럿이면 `AMBIGUOUS_TARGET`이 됩니다. 사내 웹 시스템은 아이콘 버튼과 그리드 셀에서 이런 경우가 흔할 것으로 예상합니다.
- **가려진 창은 다 안 찹니다.** 대상 브라우저 창을 다른 창이 덮고 있으면 트리가 처음 상태에 머물 수 있습니다.

접근성 경로로 부족하면 CDP(Chrome DevTools Protocol)로 DOM을 직접 다루는 경로가 있습니다. `agent-desktop launch --cdp`로 브라우저를 디버깅 포트와 함께 새로 띄우고, Playwright 같은 CDP 클라이언트가 그 포트에 붙습니다. DOM 선택자를 쓰므로 웹에서는 더 안정적이지만 제약이 있습니다:

- 이미 떠 있는 브라우저에는 붙지 못하고 새로 띄워야 합니다.
- 포트가 열린 동안 같은 사용자의 다른 프로세스도 그 브라우저를 조작할 수 있습니다.
- 회사 브라우저 정책이 원격 디버깅을 막았을 수 있습니다(미확인).

그래서 브라우저 앱도 처음에는 `agent-desktop` 접근성 경로로 시도하고, 관찰 부족이 반복되는 시스템에서만 CDP 구현을 시스템 프로파일로 켭니다. 파일 저장 대화상자, 다운로드 알림 같은 브라우저 밖 창은 CDP를 쓰더라도 `agent-desktop`이 맡습니다.

## 개발 방식

집 PC에서는 MES를 실행할 수 없습니다. 그래서 두 가지로 개발합니다.

1. **가상 앱:** MES와 비슷한 구조(메뉴 → 조회 조건 → 조회 → 그리드 → 엑셀 다운로드)의 연습용 Windows 앱을 직접 만들어, 공통 기능(관찰, 정정, workflow 생성, 파라미터 재실행)을 이 앱으로 개발하고 테스트합니다.
2. **상용 앱으로 일반화 검증:** 집 PC에 설치된 상용 앱(데스크톱 앱과 브라우저)을 실행하고 조작하면서, 가상 앱에서 만든 기능이 앱별 코드 없이 통하는지 확인합니다. 한 앱에서 통한 것은 일반화의 증거가 아닙니다. UI 툴킷이 다른 여러 앱에서 확인합니다.

사용자가 PC를 쓰는 중에는 앱을 띄우거나 포커스를 옮기는 실행을 하지 않습니다(`CLAUDE.md`의 "실제 동작 확인").

## 집–회사 제약

- 개발은 집 PC에서 합니다. 코드는 GitHub(이 비공개 저장소)로 회사에 가져가 실행합니다.
- 회사에서 나온 실행 결과(기록, 스크린샷, 로그)는 집으로 가져올 수 없습니다. 사용자가 현상을 말로 전하는 것이 유일한 경로입니다.
- LLM은 양쪽 모두 OpenAI SDK로 호출합니다. 집에서는 OpenAI API, 회사에서는 내부 LLM(`OPENAI_BASE_URL`)이며, 내부 LLM도 이 예제가 쓰는 Responses API, 도구 호출, 이미지 입력을 지원합니다(사용자 확인). 그래서 LLM 호출 코드는 하나로 유지하고 엔드포인트와 모델 이름만 설정으로 바꿉니다.

이 제약에서 나오는 작업 기준:

- **집에서 재현할 수 있게 만듭니다.** 회사에서 전해 온 현상은 먼저 가상 앱이나 비슷한 상용 앱에서 재현한 뒤 고칩니다. 재현하지 못한 수정은 추측이라고 밝힙니다.
- **회사 실행 결과는 사람이 옮겨 적을 수 있는 형태로 요약합니다.** 실행 끝에 짧은 요약(커밋 해시, 단계 번호, 오류 코드, 관찰 요소 수, 판정)을 출력해 사용자가 그대로 불러 줄 수 있게 합니다. 화면 내용이나 업무 데이터는 요약에 넣지 않습니다.
- **사내 값은 코드 밖에 둡니다.** URL, 계정, 시스템 프로파일의 실제 값은 커밋하지 않는 설정 파일로 받고, 저장소에는 예시만 둡니다.
- **회사에서 환경부터 점검할 수 있게 합니다.** 바이너리, LLM 엔드포인트(Responses API 지원), 대상 앱 관찰 가능 여부를 한 번에 확인하는 점검 명령을 둡니다.
- **현상을 받으면 질문으로 좁힙니다.** 사용자가 현상을 전하면, 위 요약의 어느 값을 확인하면 원인이 갈리는지 구체적으로 묻습니다.

위 도구(가상 앱, 실행 요약, 설정 분리, 점검 명령)는 후보이며 아직 만들지 않았습니다.

## 미확인

- **MES의 UI 툴킷과 접근성 트리:** 설치형 앱이라는 것만 확인했습니다. WinForms, WPF, 그리드 컴포넌트, 자체 렌더링 툴킷 중 무엇이냐에 따라 UIA로 보이는 범위가 크게 다릅니다. 특히 그리드와 달력 컨트롤은 트리에 셀이나 날짜가 안 나올 수 있습니다. 회사에서 MES 화면에 `snapshot`을 찍어 ref 수와 그리드 내부가 보이는지를 확인하는 것이 첫 점검입니다.
- **실행 위치:** 사용자 요청을 받아 어느 PC(또는 세션)에서 앱을 조작하는지, 동시 요청을 어떻게 나누는지.
- **회사 브라우저 정책:** 원격 디버깅(CDP) 허용 여부, Edge IE 모드로 도는 사내 웹 시스템이 있는지.
- **보안:** 화면 내용이 내부 LLM과 기록에 남는 범위, 다운로드 파일의 처리.
