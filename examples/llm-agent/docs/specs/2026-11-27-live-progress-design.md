# 실시간 진행 표시 설계

- 날짜: 2026-11-27
- 상태: 구현됨

## 왜

회사에서 `view.py`로 실행하면 지금 무엇을 하는지 눈으로 알 수 없다. 기록은 모두 일이 끝난 뒤에 남는다. 모델 응답이 오면 `model`, 도구가 끝나면 `tool`/`action`, 화면을 다 읽으면 `observation`이 남고, "시작했다"는 기록은 없다. 그래서 모델이 20초를 생각하거나 CLI 명령 하나가 오래 걸리면 그동안 웹 화면은 그대로이고, `view.py`의 터미널은 실행 중 아무것도 찍지 않는다. 이번 포커스 문제처럼 어느 명령에서 막혔는지도 실행이 끝난 뒤 기록을 뒤져야 안다.

## 목표

- 실행 중에 지금 하는 일이 터미널과 웹 화면에 바로 보인다. 단위는 세 겹이다(사용자 선택 B).
  1. 모델 호출: "모델 생각 중 · 14초"
  2. 도구 호출: `click_part` + 모델이 적은 intent
  3. 그 도구가 보낸 CLI 명령: `focus-window`, `mouse-click`, `snapshot`, `screenshot` …
- 각 항목에 걸린 시간과 성공 여부(실패면 코드)가 붙는다. 진행 중인 항목은 흐른 시간이 계속 늘어난다.
- 지난 실행을 다시 열거나 HTML로 내보내도 같은 기록과 시간을 볼 수 있다.
- `run.py`와 `view.py`, 모델 실행과 workflow 재실행에 모두 적용된다.

## 하지 않는 것

- `events.jsonl`과 그것을 읽는 쪽(요약, 뷰어 타임라인 항목, workflow 만들기, 테스트)은 바꾸지 않는다.
- 터미널 화면을 제자리에서 다시 그리지 않는다(curses 같은 것). 줄을 추가로만 찍는다.
- 웹 갱신 방식은 지금의 1초 폴링을 그대로 쓴다. SSE나 WebSocket은 쓰지 않는다.
- 요약(`summary.py`)과 `run.json`에는 아무것도 더하지 않는다.

## 안티 목표

- 진행 표시 때문에 실행이 느려지거나 멈추면 실패다. 파일 쓰기나 터미널 출력이 실패해도 실행은 계속돼야 한다.
- 0.5초마다 반복되는 읽기(준비 대기, `wait_for_text`)가 화면을 수백 줄로 덮으면 실패다.

## 제약

- 회사 반입 규칙: 진행 기록에는 모델의 intent 글이 들어가므로 `events.jsonl`처럼 회사 PC 전용 기록이다. 요약, `check.py` 출력, `run.json`에는 넣지 않는다. CLI 명령은 **명령 이름만** 적고 인자(입력한 글, 경로, 좌표, 창 id)는 적지 않는다.
- `agent/`와 `viewer/` 코드에 앱 이름이나 화면 글을 넣지 않는다(`tests/test_application_agnostic.py`).
- 터미널은 cp949 콘솔에서도 깨지거나 멈추지 않아야 한다. `run.py`처럼 `errors="replace"`로 맞추고, 표시 기호는 cp949에 있는 것만 쓴다.
- 기존 실행 폴더(진행 기록이 없음)도 뷰어에서 지금처럼 열린다.

## 접근 방법

- 1. `events.jsonl`에 함께 쓰기: 가장 간단하지만 그 파일을 순서대로 읽는 곳이 많아 영향 범위가 넓다(포커스 작업에서 이벤트 하나로 기록기 테스트 9개가 깨졌다). 반복 읽기로 수백 줄이 쌓인다.
- 2. 메모리에만 두기: 가볍지만 실행이 끝나면 사라져 지난 실행과 내보내기에서 시간을 볼 수 없다.
- **3. 별도 파일 `progress.jsonl` (사용자 선택).** 기존 기록을 건드리지 않고, 기록이 남는다.

## 설계

### 진행 기록 파일 `runs/<id>/progress.jsonl`

한 줄에 한 레코드다. 모든 레코드는 다음 필드를 가진다.

| 필드 | 뜻 |
|---|---|
| `id` | 실행 안에서 1부터 늘어나는 항목 번호 |
| `phase` | `start` 또는 `end` |
| `kind` | `model`, `tool`, `cli`, `ready` |
| `t_ms` | 실행 시작(기록기 생성)부터 흐른 밀리초, 단조 시계 |
| `parent` | 이 항목을 품은 항목의 `id`, 없으면 생략 |

`start`에만 붙는 것:
- `model`: `step`(모델 호출 번호)
- `tool`: `step`, `name`(도구 이름), `intent`(있을 때)
- `cli`: `name`(명령 이름 한 단어, 예: `snapshot`), `headed`(참일 때만)
- `ready`: 없음

`end`에만 붙는 것: `ok`(참/거짓), 실패면 `code`(CLI의 `error.code`, 도구 결과의 `refused_code`나 `code`, 모델 오류면 예외 종류 이름). `model`의 끝에는 `tokens`(그 호출의 토큰)도 붙는다.

`tool`의 `start`와 `end`에는 `events_seen`도 붙는다. 그 순간까지 `events.jsonl`에 쓴 줄 수다. 기록기가 센다.

반복 읽기도 파일에는 하나씩 다 쓴다. 한 줄이 짧아 준비 대기 수백 번도 수십 KB이다. 묶기는 보여 주는 쪽(터미널, 웹)이 한다. 규칙은 같은 부모 아래 연달아 끝난 같은 이름의 항목을 하나로 묶는 것이다. 대상은 `cli` 항목과, 읽기만 하는 도구(`READ_ONLY_TOOLS`, 예: workflow 재실행이 0.5초마다 부르는 `list_windows`, `observe`)의 `tool` 항목이다. 묶인 도구의 자식 CLI는 따로 보여 주지 않는다. 결과는 `snapshot ×24 · 12.0초 · 실패 2`처럼 보인다.

**성공 표시 규칙:** `ok`는 "전달됐는가"이다. CLI 오류, 하니스 실패, 거절(`refused`)이면 `ok: false`이고 `×`로 보인다. 전달됐지만 기대와 다르면(`expected_met: false`) `ok: true`에 `mismatch: true`를 붙이고 `△`로 보인다. 확인하지 못함(`verdict: unconfirmed`)은 `○`로 둔다.

### 신호를 내는 곳

진행 기록은 `ProgressLog` 하나가 맡는다(새 모듈 `agent/progress.py`). 기록기(`RunRecorder`)가 만들 때 함께 만들어 `recorder.progress`로 내준다. `ProgressLog`는 열린 항목의 스택을 들고 있어, 새 항목의 `parent`를 스택 맨 위로 정한다. 기록 하나마다 받는 쪽(sink) 목록에 넘긴다. 파일 쓰기가 기본 sink이고, 터미널 출력은 켤 때만 붙는다. sink에서 예외가 나면 삼키고 그 sink만 끈다(안티 목표). 진행 기록이 없는 곳(survey 세션, `check.py`, 테스트)에서는 아무것도 하지 않는 객체를 쓴다.

- **CLI:** `DesktopClient.run`이 명령마다 `cli` 항목을 열고 닫는다. 명령 이름은 `args[0]`이다. 결과의 `ok`와 `error.code`, 그리고 하니스 자체 실패(`HARNESS_TIMEOUT`, `HARNESS_SPAWN`, `SHORTCUT_*`)를 끝에 적는다. `DesktopClient`는 기록기보다 먼저 만들어지므로, 진행 기록을 나중에 붙이는 방법(`set_progress`)으로 받는다. 기록기는 이미 `desktop`을 받으므로 생성자에서 붙인다.
- **도구:** 모델 실행에서는 `loop.py`의 `_execute`가 도구 호출 하나를 `tool` 항목으로 감싼다. 그래서 `finish`의 성공 판정, 사람 승인 대기, 계획 없음 거절처럼 `Toolbox.call` 밖에서 처리되는 호출도 항목이 된다. 승인을 기다리는 동안에는 패널에 그 도구가 열린 채로 보인다. workflow 재실행처럼 `_execute`를 거치지 않는 호출은 `Toolbox.call`이 감싼다. 이미 같은 이름의 `tool` 항목이 맨 안쪽에 열려 있으면 `Toolbox.call`은 새로 열지 않는다. 그 안에서 보낸 CLI 명령과 동작 뒤 다시 관찰하는 읽기, 비전 질문이 모두 자식이 된다. 거절도 끝으로 적는다(`ok: false`, `code`는 `refused_code`).
- **모델:** `loop.py`의 `_respond`가 모델 호출을 `model` 항목으로 감싼다. 비전 모델 호출(`agent/vision.py`)은 그 시점의 열린 항목(보통 도구) 아래 `model` 항목이 된다. workflow 만들기의 모델 호출도 같은 방식으로 적는다.
- **준비 대기:** `Toolbox.launch_ready`가 `ready` 항목을 열고, 대기 중의 `launch`, `list-windows`, `snapshot`, `find`가 자식이 된다. 시작 직후 올리기의 `focus-window`도 이 안에 들어간다.
- 단계(`plan`, `stage`)는 진행 기록에 따로 적지 않는다. 화면은 `events.jsonl`의 단계 이벤트로 현재 단계를 안다.

### 터미널

`ProgressPrinter`(같은 모듈)가 sink로 붙어 줄을 찍는다. `run.py`는 늘 붙이고, `view.py`는 뷰어로 시작한 실행에 붙인다. `run.py`가 지금 도구마다 찍던 한 줄(`make_logger`)은 이 출력으로 대신한다.

```
[단계 2/4] 스텝 7
▶ 모델 생각 중
○ 모델 응답 · 14.2초 · 토큰 3,120
▶ click_part · 생산분석 메뉴를 연다
   ○ focus-window · 0.3초
   ○ mouse-click · 0.4초
   ○ list-windows · 0.1초
   ○ snapshot · 1.1초
○ click_part · 2.8초
▶ 모델 생각 중
```

- 모델과 도구는 시작할 때 `▶` 줄, 끝날 때 `○`(성공), `△`(전달됐지만 기대와 다름), `×`(실패, 코드 포함) 줄을 찍는다. CLI 명령은 끝날 때 한 줄만 찍고 부모보다 3칸 들여 쓴다.
- 연달아 같은 이름의 CLI가 끝나면 줄을 새로 찍지 않고 묶어 두었다가, 다른 기록이 오면 `○ snapshot ×24 · 12.0초` 한 줄로 찍는다.
- 단계가 바뀌면 `[단계 n/m] 스텝 k` 줄을 찍는다. 단계 정보는 같은 실행의 `stage`/`plan` 이벤트를 받아서 안다. `ProgressPrinter`는 기록기의 `on_event`도 받는다.
- intent는 한 줄 60자에서 자르고 `…`을 붙인다. 줄바꿈은 공백으로 바꾼다.

### 웹 뷰어

- 서버에 `GET /api/runs/<id>/progress?since=N`을 더한다. 인증과 응답 모양(`{"records": [...], "next": N}`)은 `events`와 같다. 파일이 없으면 빈 목록을 준다.
- 실행 중인 실행을 보는 동안 이벤트 폴링과 같은 주기로 진행 기록도 받는다.
- **"지금" 패널:** 타임라인 위에 둔다. 실행 중일 때만 보인다.
  - 맨 위 줄은 `단계 2/4 · 스텝 7`이다.
  - 그 아래에 열린 항목을 바깥부터 안쪽 순서로 보여 준다(예: `click_part · 생산분석 메뉴를 연다 · 2.1초`, 그 아래 `mouse-click · 0.4초`).
  - 흐른 시간은 1초마다 늘어난다. 진행 기록에서 받은 마지막 `t_ms`와 그것을 받은 브라우저 시각으로 계산한다.
  - 그 아래에 방금 끝난 항목 5개를 묶기 규칙에 따라 보여 준다.
- **스텝 상세:** 타임라인에서 동작이나 관찰을 고르면, 상세 칸에 그 도구의 걸린 시간과 CLI 명령 목록(묶기 적용, 기본은 접힘)을 보여 준다. 짝은 줄 번호로 맞춘다. 타임라인 항목을 만든 이벤트가 `events.jsonl`의 k번째 줄이면, `start.events_seen < k ≤ end.events_seen`인 가장 안쪽 `tool` 항목이 그 짝이다. 재실행에는 `step`이 없고 한 응답에 같은 도구가 여럿 올 수 있어, `step`과 이름으로는 짝을 정할 수 없기 때문이다. 맞는 것이 없으면 이 부분을 보여 주지 않는다.
- HTML 내보내기(`viewer/export.py`)는 `progress.jsonl`도 담아, 내보낸 파일에서도 스텝 상세의 시간이 보인다.
- 글은 모두 `textContent`로 넣는다(기존 규칙).

## 사용자가 정한 것

- 단위: 모델 호출, 도구 호출, 도구 안의 CLI 명령까지(B).
- 저장: 별도 파일 `progress.jsonl`(3).

## 구현자에게 맡기는 것

- `ProgressLog`를 기록기에 둘지, 기록기 옆의 별도 객체로 만들어 각 생성 지점에서 넘길지. 위의 "기록기가 만들고 `desktop`에 붙인다"는 내 판단이다. 기록기가 이미 실행마다 하나씩 있고 `desktop`을 받기 때문이다.
- 실행이 멈추거나 예외로 끝날 때 열린 항목을 어떻게 닫을지(예: `ok: false`, `code: "STOPPED"`).
- 터미널 기호(`▶`, `○`, `△`, `×`)가 cp949에 없으면 cp949에 있는 다른 기호로 바꾼다.
- 웹 "지금" 패널의 모양과 위치, 묶인 줄을 펼치는 방식.
- 파일 쓰기 버퍼링과 잠금. 실행 스레드 하나가 쓰는 것이 기본이지만, 하트비트 스레드와 겹치지 않게 한다.
