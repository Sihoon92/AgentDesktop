# 새 시스템 조사(`survey.py`)와 회사 GLM 실행 전용 장치

- 날짜: 2026-11-25
- 상태: 대체됨(2026-11-27). [회사 시스템 캡처 세션과 회사 GLM 정리 절차](2026-11-27-company-capture-session-design.md)가 이 문서를 대체합니다. 이 문서의 가설, 계열 판별, 이름 공개 범위, `company/` 훅은 그 문서로 옮겨졌습니다.
- 원래 상태: 설계. 방법은 사용자가 고름(2026-11-25, 이름 공개 범위 "A", 조사 방식 A와 실행 전용 장치 "응 맞아")
- 대상: `examples/llm-agent`의 새 진입점 `survey.py`, 새 모듈(가설 목록, 구조 조사), 생성되는 가설 문서, 새 폴더 `company/`(회사 Claude Code용 규칙과 훅). `agent-desktop` CLI(Rust)는 고치지 않습니다.
- 앞선 설계: [CUA 배경](../cua-background.md)의 "집–회사 제약", [시스템 프로파일](2026-11-19-system-profile-design.md)의 6장(점검), [바로가기로 띄우기](2026-11-19-shortcut-launch-design.md)

## 왜 하는가

회사의 MES와 GSCM은 집 PC에 없습니다. 집에서 만든 기능은 기억으로 만든 가상 MES에서만 확인되고, 회사에서 집으로 돌아오는 정보는 사용자가 말로 옮겨 적는 몇 줄뿐입니다. 2026-11-25 기준으로 지금까지 만든 기능은 회사 시스템에서 한 번도 돌지 않았습니다.

그래서 회사에 한 번 다녀올 때마다 얻는 정보를 최대로 늘려야 합니다. 가장 값진 정보는 "이 시스템이 무엇으로 만들어졌나"입니다. UI 툴킷이 같으면 접근성 트리의 모양도 같으므로, 그것을 알면 가상 MES를 같은 툴킷으로 다시 만들거나 같은 툴킷의 상용 앱으로 집에서 검증할 수 있습니다. 지금의 `check.py`는 요소 종류의 수까지만 알려 주고 툴킷은 알려 주지 않으며, 숫자가 무엇을 뜻하고 집에서 무엇을 해야 하는지는 기록되어 있지 않습니다.

사용자가 정한 운영 방식은 다음과 같습니다.

- 알고 싶은 정보마다 스크립트를 따로 두지 않습니다. 회사에서는 **하나만** 실행합니다.
- 설계자(집의 에이전트)가 가설을 md로 써 두고, 회사에서 그 md에 결과를 채웁니다.
- 회사 PC의 Claude Code(GLM 연결)는 **실행하고 결과를 확인하는 데만** 씁니다. 회사에서 고친 코드는 집으로 가져올 방법이 없기 때문입니다.

## 용어

- **가설:** 회사 시스템에 대해 집에서 알고 싶은 질문 하나. 번호(`H01`), 질문, 판정 규칙, 판정별로 집에서 할 일을 가집니다.
- **조사:** `survey.py` 한 번의 실행. 대상 앱을 읽기만 하고 가설마다 판정을 냅니다.
- **사실(facts):** 조사가 모은 수와 계열 이름. 가설의 판정은 사실에서만 나옵니다.
- **결과 문서:** 조사가 회사 PC에 남기는 md. 자동 판정이 채워져 있고 사람이 답할 칸이 비어 있습니다.
- **전달 블록:** 조사 끝에 콘솔에 찍히는 몇 줄. 사용자가 집에 옮겨 적는 부분입니다.

## 목표와 하지 않는 것

**목표**

- `python survey.py --system <이름>`(또는 `--exe <경로>`) 하나로 다음을 모두 합니다: `check.py`의 점검 전부, 툴킷·그리드 부품·창 구조·웹 내장 판별, UIA FrameworkId와 지원 패턴 세기, 가설 판정, 결과 문서와 오버레이 그림 저장, 전달 블록 출력.
- 가설은 코드 한 곳에만 정의합니다. 저장소의 가설 문서(`docs/company-survey/hypotheses.md`)와 결과 문서는 그 정의에서 만들어지며, 둘이 어긋나면 테스트가 실패합니다.
- 결과 문서에는 사람이 답할 칸과 답하는 방법이 함께 있고, 사람은 오버레이 그림을 보고 답할 수 있습니다.
- 회사 Claude Code가 `company/` 폴더에서 시작되면, 저장소의 추적 파일을 고치거나 저장소 상태를 바꾸는 git 명령을 하네스(훅)가 막습니다.
- 조사는 코드가 바뀐 상태에서 돌았는지를 스스로 기록합니다.

**하지 않는 것**

- 앱을 클릭하거나 입력하지 않습니다. 메뉴를 열어 다른 화면을 조사하지 않습니다. 조사는 띄운 직후의 창(또는 이미 떠 있는 창)만 읽습니다.
- 앱을 끄고 다시 켜지 않습니다. ID 유지 여부는 `check.py`처럼 앱을 껐다 켠 뒤 다음 조사에서 판정합니다.
- OCR을 하지 않습니다. 그림으로만 그려진 글자는 사람이 오버레이를 보고 답합니다.
- 회사 결과를 집으로 보내는 자동 경로(업로드, 메일)를 만들지 않습니다.
- 셸 명령으로 파일을 우회해 고치는 경우까지 훅이 완벽하게 막지는 않습니다. 그 경우는 조사의 코드 변경 기록으로 잡습니다.

**실패로 보는 것**

- 전달 블록, 콘솔 출력, 기본 결과 문서에 화면의 글자, 요소 이름, 메뉴 이름, 경로, 원래의 창 클래스 이름이나 DLL 이름이 들어감.
- 가설 문서와 코드의 가설 정의가 어긋남.
- 조사가 앱에 클릭, 키 입력, 포커스 변경 외의 상태 변화를 일으킴(띄우기는 예외).
- 회사 Claude Code가 추적 파일을 고쳤는데 조사가 "코드 변경 없음"이라고 적음.

## 사용자가 정한 것

- **이름 공개 범위 (A):** 기본 출력에는 알려진 계열 이름만 넣고, 모르는 이름은 개수만 셉니다. `--show-names`를 줄 때만 원래의 창 클래스 이름과 DLL 이름을 **결과 문서에만** 적습니다(콘솔과 전달 블록에는 그때도 넣지 않음). 무엇을 옮겨 적을지는 사용자가 판단합니다.
- **조사 방식 (A):** 가설 목록을 코드 한 곳에 두고, 조사 스크립트와 md가 모두 그 목록을 따릅니다.
- **회사 GLM 실행 전용:** 회사 Claude Code(GLM 연결)는 실행과 결과 확인만 합니다. `company/` 폴더의 규칙과 훅으로 강제합니다.

## 1. 회사에서의 흐름

1. 사용자가 `git pull`.
2. `python survey.py --system GSCM`. 앱이 뜨고(설정의 준비 신호가 있으면 기다림) 읽은 뒤 끝납니다. 앱은 띄운 채로 둡니다.
3. 회사 PC에 생기는 것:
   - `survey-results/<날짜-시각>-<시스템>/survey.md`: 결과 문서
   - `survey-results/<날짜-시각>-<시스템>/overlay.png`: 창 캡처 위에 요소 박스를 종류별 색으로 그린 그림
   - `survey-results/<날짜-시각>-<시스템>/facts.json`: 판정에 쓴 사실(같은 공개 범위 규칙을 따름)
4. 사용자가 `survey.md`의 "사람이 답함" 칸을 `overlay.png`를 보며 채웁니다. 회사 Claude Code에게 도움을 받을 수 있습니다.
5. 콘솔의 전달 블록과 사람이 답한 칸을 집에 옮겨 적습니다.

`survey-results/`는 Git에서 제외합니다(`.gitignore`에 추가).

## 2. 가설 목록

가설은 Python 모듈 하나(`agent/hypotheses.py`)에 데이터로 정의합니다. 가설마다 다음을 가집니다.

| 칸 | 뜻 |
| --- | --- |
| `id` | `H01`처럼 바뀌지 않는 번호. 닫힌 가설의 번호는 다시 쓰지 않습니다 |
| `title` | 한 줄 질문 |
| `why` | 답이 왜 중요한지 한두 문장 |
| `kind` | `auto`(사실로 판정) 또는 `manual`(사람이 답함) |
| `judge` | `auto`일 때: 사실 → (판정 코드, 근거 한 줄). 근거는 수와 계열 이름만 |
| `how_to_answer` | `manual`일 때: 오버레이에서 무엇을 보고 어떻게 답하는지 |
| `next` | 판정 코드별로 집에서 할 일 |
| `status` | `open` 또는 `closed`(닫힌 이유와 날짜). 닫힌 가설은 조사하지만 전달 블록에서 뺍니다 |

판정 코드는 짧은 영문·숫자(`WINFORMS`, `DELPHI`, `LOW`, `STABLE`)입니다. 전달 블록에 그대로 나가므로 화면 내용이 들어갈 자리가 없습니다.

### 처음 넣는 가설

판정 규칙의 세부 문턱값은 구현자에게 맡깁니다(아래 "구현자에게 맡기는 것"). 판정 코드의 집합과 그 뜻은 여기서 정합니다.

| ID | 질문 | 종류 | 판정 코드 | 집에서 할 일 |
| --- | --- | --- | --- | --- |
| H01 | 무엇으로 만들었나(UI 툴킷) | auto | `WINFORMS`, `WPF`, `WIN32`, `MFC`, `DELPHI`, `JAVA`, `QT`, `NEXACRO`(TOBESOFT 계열), `WEB`, `MIXED`, `UNKNOWN` | 같은 툴킷으로 가상 MES를 다시 만들지, 같은 툴킷의 상용 앱을 찾을지 정함. `UNKNOWN`이면 다음 조사에서 `--show-names` 요청 |
| H02 | 표는 어떤 부품인가 | auto | `DEVEXPRESS`, `INFRAGISTICS`, `FARPOINT`, `COMPONENTONE`, `SYNCFUSION`, `TELERIK`, `ACTIVEX_OTHER`, `NATIVE`, `NONE_SEEN` | 같은 부품의 체험판으로 가상 MES의 그리드를 다시 만듦 |
| H03 | 화면 요소가 트리에 얼마나 보이나 | auto | `RICH`, `PARTIAL`, `LOW` | `LOW`면 그림 인식(비전, 좌표) 쪽 우선, `RICH`면 ref 중심 유지 |
| H04 | 요소가 동작 패턴을 지원하나 | auto | `PATTERNS_OK`, `INVOKE_ONLY`, `NONE` | `NONE`이면 ref 동작 대신 실제 마우스 경로가 기본이 되도록 정책 조정 |
| H05 | 요소 ID가 껐다 켜도 같은가 | auto | `STABLE`, `CHANGES`, `NO_IDS`, `PENDING`(지난 기록 없음이나 같은 프로세스) | 프로파일의 `stable_ids`와 workflow 대상 적기 방침 |
| H06 | 어떻게 실행되나 | auto | `EXE`, `LNK_EXE`, `LNK_NOT_EXE`, `LAUNCHER`(띄운 프로세스와 창의 프로세스가 다름), `LAUNCHER_UNRESOLVED`, `ATTACHED`(3장 "대상 창 고르기") | `LNK_NOT_EXE`면 "탐색기처럼 열기"를 더함, `LAUNCHER`면 준비 확인의 프로세스 추적 점검, `LAUNCHER_UNRESOLVED`면 준비 신호를 적고 재조사 |
| H07 | 창 구조는 어떤가 | auto | `SINGLE`, `MDI`, `MULTI_TOP`(같은 프로세스의 보이는 최상위 창이 여럿) | `MDI`면 가상 MES를 MDI로 바꾸고 관찰 범위를 MDI 자식 창 기준으로 점검 |
| H08 | 안에 웹 화면이 있나 | auto | `NONE`, `WEBVIEW2`, `CEF`, `IE` | 웹이면 브라우저 경로(배경 문서 "브라우저 앱")를 먼저 시험 |
| H09 | 화면 크기와 배율 | auto | `<가로>x<세로>@<배율>`: 대상 창이 있는 모니터의 해상도와 배율(Win32 `MonitorFromWindow`, `GetDpiForMonitor`), 근거에 모니터 수와 창 캡처 크기 | 가상 MES 시험을 같은 배율로 맞춤 |
| H10 | 사내 LLM이 무엇을 하나 | auto | `TOOLS_IMAGE`, `TOOLS_ONLY`, `FAIL`, `SKIPPED` 와 비전 모델 여부 | `TOOLS_ONLY`면 나눈 방식(비전 모델) 설정 안내 |
| H11 | 화면 읽기가 얼마나 걸리나 | auto | 초(소수 한 자리)와 `COMPLETE`/`TRUNCATED` | 시간 한도, `--timeout-ms` 기본값 |
| H12 | 화면에 보이는 글자에 박스가 있나 | manual | `ALL`, `SOME`, `NONE` | `SOME`/`NONE`이면 글자 찾기를 비전으로 넘기는 비중을 올림 |
| H13 | 그림 버튼(아이콘)에 박스가 있나 | manual | `ALL`, `SOME`, `NONE`, `NO_ICONS` | 그림 대상(`PICTURE_TARGET`) 처리 우선순위 |
| H14 | 표의 칸마다 박스가 있나 | manual | `CELLS`, `TABLE_ONLY`, `NONE`, `NO_TABLE` | 표 찾기(`agent/table.py`)를 쓸 수 있는지 |

`manual` 가설의 기본 답은 `?`이고, 결과 문서에 답하는 방법이 함께 적힙니다. 예: "H12: overlay.png에서 필터 이름처럼 화면에 보이는 글자 위에 초록 박스(글자 요소)가 있는지 보세요. 전부 있으면 ALL, 일부만 있으면 SOME, 없으면 NONE."

## 3. 조사가 모으는 사실

조사는 대상 창 하나(준비 신호가 있으면 준비된 창, 없으면 띄운 프로세스의 주 창)에 대해 아래를 모읍니다. 모두 읽기만 합니다.

| 출처 | 모으는 것 | 쓰는 가설 |
| --- | --- | --- |
| `check.py`의 점검 함수(`run_checks`) | 바이너리, 설정, LLM과 비전, 준비 신호, 앱 관찰의 종류별 수, ID 유지 | H03, H05, H06, H10, H11 |
| `agent-desktop snapshot`(점검이 이미 하는 것) | 노드 수, 깊이, 잘림, 읽기 시간, 캡처 크기와 배율 | H03, H09, H11 |
| Win32(ctypes): 대상 프로세스와 그 자식 프로세스의 최상위·자식 창 | 창 클래스 이름 → 계열별 개수, `MDIClient` 유무, 보이는 최상위 창 수 | H01, H07, H08 |
| Win32(ctypes): 대상 프로세스와 자식 프로세스가 불러온 모듈 | DLL 이름 → 계열별 개수, 모르는 이름의 수, 프로세스 비트 수 | H01, H02, H08 |
| PowerShell의 Windows 기본 UIA(`UIAutomationClient`) | 요소별 `FrameworkId` 개수, 지원 패턴(Invoke, Value, Toggle, ExpandCollapse, Selection, Grid, Table, LegacyIAccessible) 개수 | H01, H04, H14 보조 |

- **계열 판별 표**는 `agent/toolkits.py` 한 곳에 둡니다. 창 클래스와 DLL 이름의 패턴 → 계열 이름(예: `WindowsForms10.*` → WinForms, `T[A-Z]*` 형태의 Delphi 클래스 → Delphi, `HwndWrapper*` → WPF, `Chrome_WidgetWin_*`·`msedgewebview2` → WebView2/Chromium, `Internet Explorer_Server` → IE, `SunAwt*` → Java, `Qt*QWindow*` → Qt, `Afx:*` → MFC, `DevExpress.*` → DevExpress, `FPSpread*`·`FarPoint.*` → FarPoint, `nexacro*`·`XPlatform*`·`MiPlatform*` → TOBESOFT 계열). 툴킷과 부품의 이름은 앱 이름이 아니므로 `tests/test_application_agnostic.py`의 금지 대상이 아닙니다.
- **Windows 시스템 DLL**(Windows 폴더 아래의 모듈)은 계열 판별에만 쓰고, "모르는 이름"으로 세지도 `--show-names`로 적지도 않습니다. 사내 DLL만 남기기 위해서입니다.
- **UIA 순회**는 노드 수와 시간에 상한을 둡니다(상한에 닿으면 `잘림` 표시). PowerShell 스크립트 파일은 저장소에 두고 Python이 실행하며, 이름이나 값은 PowerShell 밖으로 내보내지 않고 개수만 JSON으로 돌려받습니다.
- **조사 환경**: 커밋 해시, 코드 변경 수, 조사 버전(`SURVEY_VERSION`), Windows 빌드, Python 버전.
- **코드 변경 수**는 `examples/llm-agent/` 아래의 추적 파일 중 내용이 바뀐 것의 수입니다(`git diff --name-only HEAD -- <그 폴더>`, 새로 만든 추적 안 된 파일은 세지 않음). `git diff`는 줄바꿈 변환(`autocrlf`)을 거친 내용으로 비교하므로 줄바꿈만 다른 파일은 세지 않고, 파일 모드 차이도 `-c core.fileMode=false`로 무시합니다. 저장소 밖의 Rust 코드는 세지 않습니다(회사에서 고칠 이유가 없고, 집에서 받은 바이너리가 결과를 낼 뿐입니다). `변경있음`이면 결과를 버리지 않고 집에서 그 사실을 감안해 읽으며, 결과 문서에 바뀐 파일 이름을 적어 사람이 확인할 수 있게 합니다(콘솔과 전달 블록에는 수만).
- **ID 기록(H05)**은 `check.py`와 같은 저장소(`.check/<시스템>.json`)를 씁니다. 두 도구 모두 "같은 프로세스면 기록을 건드리지 않는다"는 규칙을 따르므로, 같은 앱에 `check.py`와 조사를 연달아 돌려도 서로의 기준을 덮지 않고, 앱을 껐다 켠 뒤라면 어느 도구로 돌리든 판정이 나옵니다.

`check.py`의 점검은 그대로 다시 쓰고, `check.py` 자체의 출력과 동작은 바꾸지 않습니다. 조사가 점검을 부를 수 있도록 점검의 결과를 사실로 넘기는 정도의 분리는 허용합니다. 앱 관찰 부분은 아래 "대상 창 고르기" 때문에 조사가 직접 하고, 바이너리·설정·LLM 점검만 `check.py`의 함수를 그대로 부릅니다.

### 대상 창 고르기

`check.py`는 앱이 이미 떠 있으면 실패하거나(준비 신호가 있을 때) 두 번째 사본을 띄웁니다(없을 때). 조사는 다시 돌리는 일이 잦으므로(`--show-names` 재조사, 껐다 켠 뒤 H05) 떠 있는 앱에 붙습니다.

1. **띄우기 전에 찾기:** 준비 신호가 있으면, 신호가 모두 보이는 기존 창(`agent/ready.py`가 "이미 떠 있음"을 판정할 때 쓰는 규칙). 없으면, 프로세스 실행 파일 경로가 대상 exe(바로가기면 그 대상)와 같은 프로세스의 보이는 최상위 창.
2. **하나면 붙습니다.** 띄우지 않고 그 창을 읽습니다. H06은 `ATTACHED`이고 준비 대기 시간은 재지 않습니다(H11은 읽기 시간만).
3. **둘 이상이면 멈춥니다.** `ATTACH_AMBIGUOUS` 코드로 앱 관련 가설을 모두 `SKIPPED`로 두고, 하나만 남기고 닫아 달라고 안내합니다.
4. **없으면 띄웁니다.** 준비 신호가 있으면 실행과 같은 방식(`wait_until_ready`)으로 기다립니다. 다른 프로세스로 넘어간 메인 화면도 따라가며, 이때 H06은 `LAUNCHER`입니다.
5. **준비 신호 없이 띄웠는데** 띄운 프로세스의 창이 나타나지 않으면, 나중에 나타난 아무 창이나 대상으로 삼지 **않습니다**. 다른 앱을 조사하면 H01·H02·H07·H08이 모두 틀린 답이 되기 때문입니다. H06을 `LAUNCHER_UNRESOLVED`로, 앱 관련 가설을 `SKIPPED`로 두고, 설정에 `ready_text`나 프로파일의 준비 신호를 적은 뒤 다시 조사하라고 안내합니다.

H06의 판정 코드는 `EXE`, `LNK_EXE`, `LNK_NOT_EXE`, `LAUNCHER`, `LAUNCHER_UNRESOLVED`, `ATTACHED`입니다(2장의 표도 이 집합을 따릅니다).

## 4. 결과물

### 결과 문서 (`survey.md`)

가설 정의에서 만들어집니다. 모양은 다음과 같습니다.

```markdown
# 시스템 조사: GSCM

- 시각 2026-11-27 10:12 · 조사 v1 · 커밋 6dbba10 · 코드 변경 없음
- 전달 블록 (그대로 옮겨 적으세요)

    [전달] survey v1 · 6dbba10 · 변경없음 · GSCM
    H01 DELPHI   H02 NONE_SEEN   H03 LOW(4/0/85)   H04 INVOKE_ONLY
    ...

## H01 무엇으로 만들었나 (자동)
- 판정: DELPHI
- 근거: 창 클래스 Delphi 14 · 모르는 이름 3 / DLL 모르는 이름 11
- 왜 중요한가: …
- 판정별 다음 할 일: …

## H12 화면에 보이는 글자에 박스가 있나 (사람이 답함)
- 답: ?
- 답하는 방법: …
```

- 시스템 이름은 사용자가 고른 `--system` 이름만 적습니다(exe 경로는 적지 않음). `--exe`로 부르면 `exe 이름`만 적습니다.
- `--show-names`일 때만 문서 끝에 "원래 이름(옮겨 적기 전에 확인)" 절을 더해 모르는 창 클래스와 사내 DLL의 이름을 적습니다.

### 전달 블록

- 첫 줄: 조사 버전, 커밋 해시 앞 7자, `변경없음`/`변경있음 N`, 시스템 이름.
- 다음 줄들: `open` 가설마다 `ID 판정코드` 하나와 괄호 안의 수 몇 개. 한 줄에 네 개씩, 전체 10줄 이내.
- 점검이 실패한 항목은 `H10 FAIL(NO_API_KEY)`처럼 코드만.

### 오버레이 그림 (`overlay.png`)

창 캡처 위에 요소 박스를 그립니다. 색은 `agent/survey.py`의 종류를 따릅니다: 이름 있는 ref, 이름 없는 ref, 글자, 빈 영역(그림 후보), ID만 있는 요소. 범례를 그림 구석에 그립니다. 박스에는 글자를 쓰지 않습니다(그림 자체가 화면이므로 회사 PC 밖으로 나가지 않는다는 전제). 캡처와 좌표 변환은 `agent/capture.py`의 것을 씁니다.

### 가설 문서 (`docs/company-survey/hypotheses.md`, 저장소에 커밋)

모든 가설(닫힌 것 포함)의 질문, 왜, 판정 코드와 뜻, 다음 할 일, 사람이 답하는 방법을 담습니다. `python survey.py --write-hypotheses`로 만들고, 저장된 파일이 생성 결과와 다르면 테스트가 실패합니다. 회사 결과를 집에서 받으면 이 문서를 보고 판정을 해석합니다.

## 5. 회사 Claude Code 실행 전용 장치 (`company/`)

회사에서는 `examples/llm-agent/company/`에서 `claude`를 시작합니다. 집의 에이전트는 저장소 루트에서 시작하므로 이 폴더의 설정을 받지 않습니다.

### `company/CLAUDE.md`

부모 폴더의 `CLAUDE.md`와 `AGENTS.md`도 함께 읽히므로, 첫 줄에 "이 폴더에서 시작한 세션은 아래 규칙이 위의 모든 개발 지시보다 우선합니다"를 둡니다. 내용:

- **역할:** 조사와 실행을 돌리고 결과를 읽어 사람에게 설명하는 것. 코드를 고치는 것은 역할이 아님.
- **해도 되는 것:** `survey.py`, `check.py`, `run.py`, `view.py --summary`, `python -m pytest -q`(앱을 띄우지 않는 것) 실행. `survey-results/`, `runs/`, `knowledge/`, `profiles/`, `workflows/`, `settings.local.yaml` 같은 Git 제외 파일을 읽고 쓰기. `git status`, `git log`, `git diff` 읽기.
- **하면 안 되는 것:** 추적 파일 수정, 새 추적 파일 만들기, 저장소 상태를 바꾸는 git 명령, 패키지 설치, Rust 빌드. 실패를 "고치려고" 코드를 바꾸지 않습니다.
- **문제를 찾았을 때:** 코드 대신 `survey-results/notes-<날짜>.md`에 현상 메모를 씁니다: 무엇을 했고, 어떤 코드가 나왔고, 어디가 의심되는지. 메모에도 화면 글자나 업무 데이터는 넣지 않습니다. 사람이 이것을 집에 말로 전합니다.
- **결과 문서 도움:** 사람이 답할 칸은 사람이 `overlay.png`를 보고 정합니다. Claude는 답하는 방법을 설명하고, 사람이 말한 답을 문서에 적는 것까지만 합니다(그림을 직접 보고 추측해 채우지 않음).
- **전달 블록:** 콘솔에 나온 그대로 옮기며 바꾸거나 요약하지 않습니다.

### `company/.claude/settings.json`의 훅

- **PreToolUse, Edit·Write·NotebookEdit:** 대상 경로가 저장소 안에 있고 `git check-ignore`로 제외되지 않은 파일이면 막습니다(종료 코드 2와 이유). 저장소 밖 경로는 허용합니다. **`company/` 아래는 제외 여부와 상관없이 항상 막습니다.** 그래야 Claude가 자기 규칙과 훅을 고치지 못합니다.
- **커밋되게 하기:** 저장소 루트 `.gitignore`가 `.claude/`를 제외하므로, 그대로면 `company/.claude/settings.json`이 커밋되지 않아 회사에 가지 않습니다. 루트 `.gitignore`에 `!examples/llm-agent/company/.claude/`와 `!examples/llm-agent/company/.claude/settings.json` 예외를 더하고, 이 파일이 추적되는지를 시험으로 확인합니다(`git ls-files`).
- **PreToolUse, Bash:** 저장소 상태를 바꾸는 git 하위 명령(`commit`, `push`, `checkout`, `switch`, `reset`, `restore`, `stash`, `apply`, `am`, `cherry-pick`, `rebase`, `merge`, `clean`, `rm`, `mv`, `add`), 패키지 설치(`pip install`, `conda install`, `npm install`), `cargo`를 막습니다. `git pull`, `status`, `log`, `diff`는 허용합니다.
- 같은 git 명령들을 `permissions.deny`에도 적어 두 겹으로 둡니다.
- 훅 스크립트는 표준 라이브러리만 쓰는 Python 파일(`company/hooks/guard.py`)이고 `$CLAUDE_PROJECT_DIR` 기준으로 부릅니다. 훅이 스스로 오류로 끝나면 Claude Code는 막지 않으므로, 훅은 판단할 수 없는 입력을 받으면 "막음"으로 끝냅니다.

### 탐지

훅을 피해 셸로 파일을 고친 경우(`sed -i`, 리다이렉션)는 조사의 `코드 변경 있음 N`이 드러냅니다. 집에서는 `변경있음`인 전달 블록을 그 코드의 결과로 보지 않습니다.

## 6. 시험

모두 앱을 띄우지 않는 시험입니다.

- **공개 범위:** 가짜 CLI 응답, 가짜 창 목록, 가짜 모듈 목록, 가짜 UIA 결과에 눈에 띄는 표지 문자열(요소 이름, 사내풍 DLL 이름, 폼 클래스 이름, 경로)을 넣고, 콘솔·전달 블록·기본 결과 문서·`facts.json`에 표지가 하나도 없는지 확인합니다. `--show-names`일 때는 결과 문서의 지정된 절에만 나오고 콘솔에는 없는지 확인합니다.
- **판정:** 가설마다 사실 → 판정 코드의 표 시험. 계열 판별 표의 패턴마다 하나 이상.
- **가설 문서 동기화:** 저장된 `hypotheses.md` = 생성 결과.
- **가설 목록 규칙:** 번호가 겹치지 않음, `auto`는 `judge`가, `manual`은 `how_to_answer`가 있음, `next`가 모든 판정 코드를 덮음.
- **전달 블록 크기:** 가설이 늘어도 10줄 이내.
- **훅:** 추적 파일 Edit 막음, 제외 파일 Edit 허용, `company/` 아래는 제외 파일이라도 막음, 저장소 밖 허용, 금지 git 명령 막음, `git pull`·`status` 허용, 깨진 입력 막음. `company/.claude/settings.json`이 Git에 추적됨.
- **대상 창 고르기:** 기존 창 하나면 띄우지 않고 붙음, 둘 이상이면 `ATTACH_AMBIGUOUS`, 준비 신호 없이 띄운 프로세스의 창이 없으면 다른 창을 고르지 않고 `LAUNCHER_UNRESOLVED`.
- **코드 변경 수:** 줄바꿈만 다른 파일은 세지 않음, `examples/llm-agent/` 밖은 세지 않음.
- **앱에 쓰는 명령 없음:** 조사가 CLI에 보내는 명령이 `launch`, `snapshot`, `screenshot`, `list-windows`와 점검이 쓰는 읽기 명령뿐인지 가짜 CLI로 확인.

실제 창 확인(가상 MES와 상용 앱 몇 개로 H01·H02·H07이 맞게 나오는지)은 사용자에게 확인받은 뒤 합니다. 가상 MES는 WinForms이므로 H01 `WINFORMS`가 나와야 합니다.

## 설계자가 정한 것 (사용자가 말한 것이 아님)

- 진입점은 `check.py`의 선택지가 아니라 새 `survey.py`입니다. 점검은 그대로 두고 조사가 감쌉니다.
- FrameworkId와 패턴은 `agent-desktop`(Rust)을 고치지 않고 PowerShell의 Windows 기본 UIA로 읽습니다. 회사에서 바이너리를 다시 빌드하지 않아도 되도록. 관리형 UIA는 `agent-desktop`의 UIA3와 일부 값이 다를 수 있지만 FrameworkId와 패턴 개수에는 충분하다고 봅니다.
- 오버레이는 HTML이 아니라 PNG 한 장입니다(Pillow는 이미 의존성).
- 결과 폴더는 `survey-results/`이고 실행마다 하위 폴더를 만듭니다.
- 사람이 답하는 가설의 답은 회사 Claude가 그림을 보고 추측해 채우지 않습니다.
- 처음 가설은 위 14개입니다.
- 조사는 떠 있는 앱에 붙고, 둘 이상이면 멈추며, 준비 신호 없이 띄운 런처의 창을 짐작으로 고르지 않습니다(3장 "대상 창 고르기").
- 코드 변경 수는 `examples/llm-agent/`의 추적 파일만, 줄바꿈과 모드 차이를 빼고 셉니다.
- H05의 ID 기록은 `check.py`와 같은 저장소를 씁니다.
- H09는 창이 있는 모니터의 해상도와 배율입니다.
- `company/`는 훅이 항상 보호하고, 그 설정 파일은 루트 `.gitignore` 예외로 커밋합니다.

## 구현자에게 맡기는 것

- 판정 문턱값(예: H03의 `RICH`/`PARTIAL`/`LOW` 경계, H01에서 `MIXED`로 보는 비율).
- 계열 판별 표의 정확한 패턴 목록(위 예시가 최소).
- UIA 순회의 노드·시간 상한 값.
- `check.py`의 점검 결과를 조사가 받는 방식.
- 오버레이의 색과 범례 배치.

## 확인이 필요한 것

- 회사 Claude Code가 프로젝트의 `.claude/settings.json` 훅을 따르는지(사내 배포판이 프로젝트 설정을 막았을 수 있음). 첫 조사 때 `company/`에서 시작해 추적 파일 하나에 Edit를 시켜 막히는지 보면 확인됩니다.
- 회사 PC에서 PowerShell 실행 정책이 저장소의 `.ps1` 실행을 막는지. 막히면 `-ExecutionPolicy Bypass`로 부르거나 스크립트를 명령 문자열로 넘깁니다(구현 때 둘 중 회사에서 통할 가능성이 높은 쪽을 기본으로).

## 방법 비교 (사용자가 고름)

1. **가설 목록 한 곳에서 스크립트와 md를 함께 만듦 (고름).** 가설을 더하면 조사, 결과 문서, 가설 문서에 동시에 반영되고 어긋나면 테스트가 잡습니다.
2. **md를 손으로 쓰고 스크립트가 자리표시를 채움.** 처음은 단순하지만 가설을 고칠 때마다 두 곳을 맞춰야 해서 번호가 어긋나기 쉽습니다.
3. **`agent-desktop` 스냅샷에 클래스 이름과 FrameworkId를 더함.** 모든 앱에 쓰이는 개선이지만 회사에서 바이너리를 다시 빌드해야 하고 Rust 계약과 테스트가 함께 바뀝니다. 조사 한 번을 위해 치르기에는 무겁습니다.

이름 공개 범위는 "계열 이름만, `--show-names`일 때만 원래 이름을 결과 문서에"(고름)와 "처음부터 원래 이름을 모두 출력" 중에서 골랐습니다.
