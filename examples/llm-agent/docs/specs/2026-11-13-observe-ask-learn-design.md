# 관찰 넓히기, 사람에게 묻기, 답에서 배우기 설계

- 날짜: 2026-11-13
- 상태: 구현했습니다(2026-11-13, 계획 [`../plans/2026-11-13-observe-ask-learn.md`](../plans/2026-11-13-observe-ask-learn.md)). 창 없는 테스트와, 가상 MES 앱의 실제 창에서 정해진 순서로 움직이는 가짜 모델의 장면 테스트(목표 1~7)가 통과합니다. 실제 모델로 하는 확인(모델이 알맞은 때에 묻는지, 등록 초안의 질)과 다른 앱에서의 일반화 확인(목표 8)은 아직 하지 않았습니다.
- 배경: [`../cua-background.md`](../cua-background.md)
- 앞 단계: [`2026-11-12-virtual-mes-app-design.md`](2026-11-12-virtual-mes-app-design.md)

이 문서에서 "사용자 결정"은 사용자가 대화에서 정한 것이고, "설계자 판단"은 설계자가 정한 기본값입니다. 설계자 판단은 사용자가 뒤집을 수 있습니다.

## 왜 만드는가

사용자가 회사의 다른 프로그램에서 CUA를 시도하며 겪은 장면 세 가지가 출발점입니다.

1. **화살표로만 열리는 선택 칸.** "선택 칸을 클릭해"라고 하면 에이전트가 칸의 가운데를 누릅니다. 가운데를 누르면 입력 커서만 깜빡이고 목록은 열리지 않습니다. 실제로는 칸 오른쪽 끝의 화살표를 눌러야 합니다. 에이전트는 이를 스스로 알아차려야 하고, 알아차리지 못하면 사람에게 무엇을 눌러야 하는지 물어야 합니다.
2. **표의 셀.** 조회 뒤 표에서 행과 열이 만나는 셀을 누르면 팝업이 뜹니다. "극판 양품수를 눌러서 들어가"라고 하면 사람은 보통 극판의 소계 행을 뜻합니다. 에이전트는 이를 짐작할 수 있어야 하고, 확실하지 않으면 이 셀이 맞는지 물어야 합니다.
3. **같은 이름의 칸 여러 개.** "라인" 칸이 3개인데 지시가 모호하면 되물어야 합니다.

지금 에이전트는 이 장면들을 처리하지 못합니다. 확인한 원인은 네 가지입니다.

- 모델은 접근성 트리를 글로 바꾼 것만 받습니다(`agent/loop.py`, `agent/observe.py`). 스크린샷은 뷰어용으로만 찍습니다.
- 사람이 할 수 있는 것은 동작 승인과 거부뿐입니다(`agent/approval.py`). 에이전트가 질문할 방법이 없습니다.
- 동작 뒤 무엇이 바뀌었는지 알려 주지 않습니다. 새 관찰 글만 돌려줍니다(`agent/tools.py`의 `call`).
- 실행이 끝나면 배운 것이 남지 않습니다.

사용자가 예전에 쓴 방법은 하니스 코드가 콤보 안에서 이름이 "Open"인 버튼을 찾아 그 위치를 누르는 것이었습니다. 이 방법은 그 프로그램에서만 통합니다. 다른 시스템으로 넓히려면 코드와 판단과 지식을 나눠야 합니다.

## 세 층 원칙 (사용자 결정)

| 층 | 무엇 | 어디에 둠 | 예 |
| --- | --- | --- | --- |
| 1. 공통 기계 동작 | 어느 앱에서나 참인 것 | 하니스 코드 | 요소의 역할과 위치, 좌표 계산, 화면이 바뀌었는지, 행 글자와 열 글자의 교차 지점 |
| 2. 판단 | 의미와 선택 | 모델(캡처를 봄) | "목록이 안 열렸다, 오른쪽에 화살표가 보인다", "극판이면 소계", 후보가 여럿임을 알아차림 |
| 3. 시스템 고유 지식 | 그 시스템에서만 참인 것 | 데이터(코드 아님) | "이 시스템의 선택 칸은 오른쪽 화살표로 연다" |

3층 지식은 사람이 탐침 스크립트를 돌려 코드로 옮기지 않습니다. 에이전트가 시도하고, 관찰하고, 물어서 얻습니다.

## 목표

확장한 가상 앱에서 아래 장면이 되면 이 단계가 끝난 것입니다(사용자 결정).

1. 화살표로만 열리는 선택 칸에서 가운데 클릭이 실패하면, 에이전트가 스스로 화살표를 찾아 엽니다.
2. 화살표가 요소로 잡히지 않는 설정에서는 질문하고, 번호나 찍은 위치로 답을 받아 성공합니다.
3. 활성 칸이 3개인데 지시가 모호하면 누르기 전에 확인 질문을 합니다.
4. 2단 헤더와 소계 행이 있는 표에서 "극판 양품수"를 지시하면, 확인 질문을 한 뒤 셀을 눌러 팝업을 엽니다.
5. 엑셀 저장까지 끝나면 파일로 성공을 판정하고, 등록할 내용을 보여 승인을 받습니다.
6. 같은 지시를 다시 실행하면 질문 없이 진행하고 "지난 답을 참고함"이라고 표시합니다.
7. 등록 내용이 틀리면 실패를 알아차려 다시 묻고 고칩니다.
8. 가상 앱이 아닌 다른 앱 두 개 이상에서, 앱별 코드 없이 1번과 변화 보고가 통합니다.

## 하지 않는 것

- 질문받지 않았을 때 사용자가 끼어들어 정정하는 것. 기존의 "거부 + 의견"(`--approve`)은 그대로 둡니다.
- 사람이 답하지 않은 실패에서 스스로 배우는 것, 여러 사례를 묶어 일반 규칙으로 만드는 것, 지식을 다른 시스템과 공유하는 것. 다음 단계("실패에서 스킬·가이드라인 남기기")입니다.
- workflow 생성.
- 여러 사용자가 접속하는 웹 서비스와 인증.
- 멈춘 실행을 이어서 다시 시작하는 것.
- `agent-desktop` CLI(Rust) 변경. 이 단계는 Python 예제와 가상 앱만 바꿉니다. CLI에 없는 기능이 꼭 필요하면 멈추고 사용자에게 알립니다.

## 이렇게 되면 실패

- 에이전트 실행 코드에 앱 이름, 창 제목, 화면 배치, 특정 버튼 이름("Open" 등)을 가정한 분기가 들어간다(`AGENTS.md`의 application-agnostic 규칙).
- 사용자 승인 없이 지식이 등록된다.
- 답이 없는데 에이전트가 임의로 진행한다.
- 등록된 지식이 화면 좌표로 저장되어 해상도나 DPI가 바뀌면 틀린 곳을 누른다.
- 같은 질문을 다음 실행에서 또 한다(지식이 등록되어 있는데도).
- 화면 내용이나 지식 내용이 실행 요약, 저장소, 외부 서비스로 나간다.

## 제약

- 모델 호출은 OpenAI Responses API 하나입니다(`agent/llm.py`). 회사의 내부 LLM도 Responses API, 도구 호출, 이미지 입력을 지원한다고 사용자가 확인했습니다.
- 회사 실행 결과(기록, 스크린샷, 지식 파일)는 집으로 가져올 수 없습니다. 지식은 회사에서 생기고 회사에 남습니다.
- 뷰어는 표준 라이브러리 서버이고 127.0.0.1에서만 받습니다(`viewer/server.py`). 이 구조를 유지합니다.
- 도구는 `permission_level`로 제한됩니다(`agent/tool_schemas.py`). 실제 커서를 움직이는 동작은 2단계입니다.
- 실제 창을 띄우고 커서를 움직이는 실행은 사용자 확인 뒤에만 합니다(`CLAUDE.md`).
- 의존성은 `openai`, `pyyaml`, `python-dotenv`, `pytest`뿐입니다. 추가하려면 이유를 적습니다.

## 사용자가 보는 흐름

사용자는 뷰어(웹 화면)를 보면서 채팅으로 답합니다(사용자 결정).

**누르기 전 확인.** 에이전트가 "이 셀이 맞나요?"라고 물으면 실행이 멈춥니다. 캡처 위에 누르려는 대상은 빨간 박스 ①로, 다른 후보는 점선 박스 ②③으로, 그 대상을 고른 근거(행 이름, 열 이름)는 노란색으로 표시합니다. 사용자는 채팅에 "맞아", "2번" 또는 말로 답합니다.

**막혔을 때.** 에이전트가 "여기서 무엇을 눌러야 하나요?"라고 물으면, 문제 부분 주변의 요소에 번호 박스를 붙입니다. 사용자는 번호로 답합니다. 번호가 없는 곳(요소로 잡히지 않는 그림)은 캡처를 한 번 클릭해 위치를 찍고, 그 표시를 채팅에 붙여 보냅니다. 어느 경우든 말로만 답해도 됩니다.

**끝났을 때.** 성공이 확인되면, 에이전트가 이번 실행의 질문과 답에서 등록할 내용을 한두 줄씩 채팅에 보여 줍니다. 사용자가 승인한 것만 등록합니다. 고쳐서 승인할 수도 있습니다.

**다음 실행.** 등록된 내용이 있으면 묻지 않고 진행하고, 그 단계에 "지난 답을 참고함"과 참고한 내용을 표시합니다.

## 언제 묻는가 (사용자 결정)

사용자는 "묻지 않고 잘못 누르는 것"이 "질문이 잦은 것"보다 더 곤란하다고 했습니다. 같은 질문을 며칠 뒤 또 받는 것도 곤란하다고 했습니다. 그래서 처음에는 묻고, 답이 등록된 뒤에는 묻지 않습니다.

| 상황 | 동작 | 누가 지키게 하는가 |
| --- | --- | --- |
| 후보가 하나이고 요소로 확인됨 | 묻지 않고 진행 | — |
| 후보가 둘 이상이고 해당 지식이 없음 | 누르기 전 확인 질문. 일반적인 해석이 뚜렷해 보여도 처음에는 묻습니다 | 모델(지침). 표 셀 찾기가 후보를 둘 이상 돌려준 경우는 하니스가 강제 |
| 요소가 아닌 그림 위 지점을 누르려 함(모델이 캡처에서 고른 좌표) | 누르기 전 확인 질문 | 하니스가 강제 |
| 해당 지식이 있음 | 묻지 않고 진행하고 참고했다고 표시 | 모델이 지식 id를 밝힘 |
| 동작 결과가 기대와 다른 일이 연속 두 번 | 막힘 질문 | 하니스가 강제 |
| 지식을 참고한 동작의 결과가 기대와 다름 | 다시 시도하지 않고 바로 질문 | 하니스가 강제 |
| 끝났는데 맞는 완료 조건이 없음 | "결과가 맞나요?" 확인 | 하니스가 강제 |

"하니스가 강제"는 조건이 만족될 때까지 앱을 바꾸는 도구 호출을 거절한다는 뜻입니다. 읽기 도구는 계속 쓸 수 있습니다. 누르기 전 확인이 강제되는 동작은 둘 중 하나일 때 통과합니다: 바로 앞에서 그 대상에 대한 확인 답을 받았거나, 동작이 지식 id를 밝혔습니다.

동작 전 승인(`--approve`)을 켠 실행에서는 확인 질문에 답한 동작도 승인을 한 번 더 거칩니다(설계자 판단). 두 기능을 서로 모르게 두는 편이 단순합니다.

## 설계

### 1. 표시 번호

관찰마다 화면에 보이는 요소 모두에 짧은 번호를 붙입니다. ref가 붙는 요소(버튼, 체크박스, 셀)와 ref가 없는 글자 요소 둘 다입니다. 지금 `agent/observe.py`의 `visible_elements`가 고르는 요소와 같은 집합입니다.

- 번호는 그 관찰에서만 유효합니다. ref와 같은 규칙입니다.
- 모델이 받는 관찰 글의 각 줄에 번호가 보입니다.
- ref는 그대로 둡니다. ref가 있는 요소를 통째로 누를 때는 지금처럼 ref 도구(`click` 등)를 씁니다.

사용자가 질문 화면에서 보는 ①②③은 이 번호가 아닙니다. 질문마다 후보에 새로 매긴 작은 번호입니다(아래 "5. 묻기").

### 2. 번호와 부분으로 누르기

새 도구 하나가 "번호가 가리키는 요소의 어느 부분"을 누릅니다.

- 입력: 표시 번호, 부분(가운데, 왼쪽 끝, 오른쪽 끝, 위쪽 끝, 아래쪽 끝), 누르는 방식(클릭, 더블클릭, 우클릭).
- 좌표는 하니스가 요소의 위치에서 계산합니다. 끝 부분은 가장자리에서 조금 안쪽입니다. 안쪽 거리는 요소의 짧은 변에 비례하게 잡습니다(설계자 판단).
- 실제 커서를 쓰므로 권한 2단계입니다. 대상 창 확인과 포커스는 지금의 `_physical`과 같은 절차를 따릅니다.

화살표 장면에서 화살표가 트리에 자식 버튼으로 있으면 그 버튼은 자기 번호와 ref를 가지므로 모델이 직접 고릅니다. 없으면 모델이 "이 칸의 오른쪽 끝"을 고릅니다. 어느 쪽인지는 모델이 캡처와 트리를 보고 판단합니다. 하니스는 버튼 이름을 찾지 않습니다.

### 3. 표의 셀 찾기

새 읽기 도구가 행 이름들과 열 이름들을 받아 교차 지점 후보를 돌려줍니다. 누르지는 않습니다.

- 입력: 행 이름 목록(예: `["극판", "소계"]`), 열 이름 목록(예: `["생산", "양품수"]`).
- 하니스는 현재 관찰의 글자 요소에서 이름이 일치하는 것을 찾습니다. 행 이름들은 세로 위치가 겹치는 한 줄에 있어야 하고, 열 이름들은 가로 위치가 겹쳐야 합니다(위 헤더가 아래 헤더를 덮음).
- 출력: 후보 목록. 후보마다 교차 지점, 그 지점에 있는 요소의 번호(있으면)와 값, 일치한 행 글자와 열 글자의 번호.
- 후보가 0개면 그 이유를 돌려줍니다(행 글자 없음, 열 글자 없음, 표의 글자가 요소로 보이지 않음).
- 후보가 둘 이상이면 모두 돌려주고, 이 가운데 하나를 누르려면 확인 질문이나 지식 참조가 먼저 있어야 합니다(하니스가 강제).

"극판이면 소계 행"이라는 해석은 모델의 몫입니다. 모델이 행 이름을 `["극판", "소계"]`로 넣어 부릅니다. 하니스는 글자 일치와 기하 계산만 합니다.

표가 그림으로만 그려진 경우 이 도구는 후보를 찾지 못합니다. 모델은 캡처를 보고 지점을 고르고, 그 지점은 누르기 전에 반드시 확인받습니다.

**이 기능의 한계(확인되지 않음).** 글자와 위치가 트리에 있으면 교차 지점 계산은 결정적입니다. 표가 그림뿐이면 모델이 캡처에서 좌표를 고르는 정확도에 달려 있고, 그 정확도는 재 보지 않았습니다. 그래서 누르기 전 확인을 안전장치로 둡니다.

### 4. 모델이 캡처를 본다

- 새 읽기 도구가 현재 창의 캡처를 모델에게 줍니다. 창 전체 또는 표시 번호 주변만 잘라서 줄 수 있습니다.
- 캡처에는 표시 번호 박스를 그려서 줍니다(설계자 판단). 번호가 그려진 이미지가 모델의 위치 판단을 돕는다고 보기 때문입니다. PNG에 그리려면 이미지 라이브러리가 필요하며, 추가 여부와 선택은 빌더가 정하고 이유를 적습니다.
- 하니스가 자동으로 캡처를 붙이는 경우: 동작 결과가 기대와 다를 때, 질문을 만들기 직전.
- 매 단계마다 붙이지는 않습니다(설계자 판단). 이미지는 토큰과 시간을 씁니다.
- 작업 설정으로 이미지 입력을 끌 수 있어야 합니다. 이미지를 받지 못하는 모델에서도 나머지 기능은 돌아야 합니다.
- 모델이 캡처에서 지점을 고르면 이미지 좌표로 말하고, 하니스가 화면 좌표로 바꿉니다. 지금의 `agent/frames.py`가 반대 방향 변환을 이미 합니다.
- 이미지를 모델에 넘기는 방식(도구 결과 안에 넣을지, 사용자 메시지로 덧붙일지)은 빌더가 정합니다. 내부 LLM에서 통하는 방식이 확인되지 않았으므로 설정으로 바꿀 수 있게 둡니다.

### 5. 기대와 변화 보고

- 앱을 바꾸는 도구는 모두 "기대하는 변화"를 인자로 받습니다. 종류는 닫힌 목록입니다: 새 창이 뜬다, 창이 닫힌다, 화면 내용이 바뀐다, 값이 바뀐다, 무엇이든.
- 하니스는 동작 전과 후의 관찰을 비교해 일어난 변화를 돌려줍니다: 새로 생긴 창과 사라진 창, 새로 생긴 요소와 사라진 요소(개수와 이름 일부), 값이 바뀐 요소, 포커스가 옮겨 간 요소, 변화 없음.
- 일어난 변화에 기대한 종류가 없으면 `기대와 다름`으로 표시해 돌려주고, 캡처를 자동으로 붙입니다.
- 기대와 다른 결과가 연속 두 번이면 하니스는 질문이 있을 때까지 앱을 바꾸는 도구를 거절합니다. 기대대로 된 동작이 나오면 횟수는 0으로 돌아갑니다.
- 트리에 나타나지 않는 변화(그림 영역 안의 변화)는 이 비교로 잡히지 않습니다. 캡처 비교를 보조 신호로 쓸지는 빌더가 정합니다. 입력 커서의 깜빡임이 "바뀜"으로 잡히지 않아야 합니다.

기존 `ActionGuard`(같은 동작 3회 금지)는 그대로 둡니다.

### 6. 묻기

새 도구 하나로 질문합니다. 앱은 건드리지 않습니다.

- 입력: 질문 종류(누르기 전 확인, 막힘), 질문 글, 후보 목록(각각 표시 번호 또는 지점과 짧은 설명), 누르려는 후보(확인 질문일 때), 근거 요소의 번호들.
- 후보에는 질문 안에서 1부터 번호를 매깁니다. 사용자가 보는 번호가 이것입니다.
- 실행은 답이 올 때까지 멈춥니다. 지금의 승인 대기(`ApprovalGate`)와 같은 방식으로 뷰어 서버가 답을 넘깁니다.
- 답: 글(필수)과 찍은 위치(선택). 하니스는 찍은 위치를 화면 좌표로 바꾸고, 그 위치를 포함하는 요소가 있으면 그 번호도 함께 모델에게 돌려줍니다.
- "맞아", "2번", "아니, 코팅 쪽"의 해석은 모델이 합니다.
- 질문, 후보, 답, 찍은 위치는 실행 기록(`events.jsonl`)에 남깁니다.

**답이 없을 때.** 정해 둔 시간이 지나면 실행을 멈춥니다. 진행하지 않습니다. 지금 승인 대기가 600초 뒤 실행을 멈추는 것과 같은 동작이며, 닫힌 뷰어가 실행을 영원히 붙잡지 않게 하려는 것입니다. 질문의 대기 시간은 승인보다 길게 잡고 설정으로 바꿀 수 있게 합니다(설계자 판단).

**뷰어 없이 실행할 때.** `run.py`만으로 실행하면 터미널에서 묻고 글로 답을 받습니다. 후보는 설명 글로 나열합니다. 위치 찍기는 없습니다.

### 7. 지식 창고

두 가지를 담습니다. 둘 다 사람이 읽고 고칠 수 있는 글 형식의 데이터입니다(사용자 결정).

**해결 기록.** 무엇이 문제였고 어떻게 풀었는가.

- 상황: 어느 화면에서, 무엇을 하려다, 무엇이 안 됐는가.
- 해결: 어떻게 해야 하는가. 자연어로 적습니다. 예: "선택 칸은 가운데가 아니라 오른쪽 끝의 화살표를 눌러 연다", "'극판 + 열 이름'은 극판·소계 행을 뜻한다".
- 근거: 실행 id, 질문, 답, 날짜.
- 상태와 횟수: 사용 중인지, 몇 번 참고했는지, 참고하고 실패한 횟수.

해결은 화면 좌표로 적지 않습니다. 요소의 역할, 이름, 부분, 상대 위치로 적습니다. 다음 실행에서 모델이 이 글을 읽고 현재 화면에 적용합니다. 지식은 2층(판단)에 주는 재료이고, 코드가 기계적으로 재생하지 않습니다.

**완료 조건.** 이런 작업은 무엇을 보고 성공으로 판단하는가.

- 어떤 작업에 해당하는지 자연어로 적은 설명. 예: "조회 결과를 엑셀로 저장하는 작업".
- 확인 방법 목록. 방법의 종류는 "8. 완료 판정"에 있습니다.

**어디에.** 시스템마다 폴더 하나입니다. 위치는 설정으로 바꿀 수 있고, 기본 위치는 git이 무시합니다. 저장소에는 예시만 둡니다. 어느 시스템인지는 작업 파일이나 실행 인자로 받는 시스템 이름으로 정하고, 없으면 실행 파일 이름을 씁니다(설계자 판단). 이것이 배경 문서가 말한 "시스템 프로파일"의 첫 조각입니다.

**찾기.** 실행을 시작할 때 그 시스템의 사용 중인 항목을 모두 모델에게 줍니다(설계자 판단). 항목이 수십 개일 때는 이것으로 충분합니다. 창고에서 꺼내는 일은 함수 하나(시스템, 지시, 현재 상황을 받아 관련 항목을 돌려줌) 뒤에 두어, 항목이 늘면 검색으로 바꿀 수 있게 합니다. 한 번에 주는 양에 상한을 두고, 넘으면 경고를 기록합니다.

**참고 표시.** 모델이 지식을 따라 동작할 때는 그 항목의 id를 동작 인자로 밝힙니다. 뷰어는 그 단계에 "지난 답을 참고함"과 항목 내용을 표시하고, 하니스는 참고 횟수를 셉니다.

**틀린 지식.** 지식을 참고한 동작의 결과가 기대와 다르면, 하니스는 실패 횟수를 올리고 질문을 강제합니다. 사용자의 새 답으로 성공하면, 끝날 때 그 항목의 수정안을 승인 대상으로 내놓습니다.

**등록.** 성공이 확인된 실행에서만 합니다(사용자 결정). 하니스가 확인한 실행과 사람이 맞다고 확인한 실행이 여기에 듭니다. 아무도 확인하지 않은 실행(`claimed`)은 들지 않습니다.

1. 하니스가 이번 실행의 질문, 답, 그 뒤 통한 동작을 모아 모델에게 등록 초안을 쓰게 합니다.
2. 초안을 항목마다 한두 줄로 채팅에 보여 줍니다.
3. 사용자가 항목마다 승인, 고쳐서 승인, 거절 중 하나를 고릅니다.
4. 승인된 것만 저장합니다.

실패하거나 멈춘 실행에서는 아무것도 등록하지 않습니다. 질문과 답은 실행 기록에 남아 다음 단계의 재료가 됩니다.

**보고 고치기.** 뷰어에서 시스템별 지식 목록을 보고, 글을 고치고, 사용을 멈추고, 지울 수 있습니다. 파일을 직접 고쳐도 됩니다.

### 8. 완료 판정

완료 조건을 하나로 고정하지 않습니다(사용자 결정). 지금 사용자의 주된 작업은 최종 파일(엑셀) 저장이 성공의 기준이지만, 입력 자동화 같은 작업은 기준이 다릅니다.

**확인 방법의 종류(공통 코드).**

| 종류 | 무엇을 보는가 | 상태 |
| --- | --- | --- |
| 화면 요소 | 지정한 역할, 이름, 상태의 요소가 화면에 있다 | 지금 있음(`agent/verify.py`) |
| 파일 | 지정한 위치에 파일이 있고, 실행 시작 뒤에 쓰였고, 비어 있지 않다 | 새로 만듦 |
| 사람 확인 | 채팅으로 "결과가 맞나요?"를 묻고 답을 받는다 | 새로 만듦 |

종류가 더 필요하면 코드로 추가합니다. 어떤 작업에 어떤 방법을 쓰는지는 데이터입니다.

**모델이 끝났다고 할 때의 순서.**

1. 작업 파일에 성공 조건이 있으면 그것으로 판정합니다. 지금과 같습니다.
2. 없으면 모델이 지식의 완료 조건 가운데 해당하는 것을 고르고, 하니스가 그 확인 방법을 실행합니다. 파일 확인의 경로는 완료 조건에 적힌 위치이거나 모델이 저장했다고 밝힌 경로이며, 어느 쪽이든 하니스가 파일을 직접 확인합니다.
3. 해당하는 것이 없으면 사람에게 확인받습니다. 맞다고 하면 성공이고, 이때 본 기준을 완료 조건으로 등록할지 승인 대상에 올립니다. 아니라고 하면 사용자의 말을 모델에게 넘겨 계속하게 합니다.

사람 확인으로 끝난 실행은 하니스가 확인한 실행과 구분되는 상태로 기록합니다. 지금 있는 `claimed`(아무도 확인하지 않음)는 물어볼 사람이 없는 실행에만 남습니다.

### 9. 뷰어

- 오른쪽에 채팅 영역을 둡니다. 질문, 답, 등록 승인, 완료 확인이 여기서 오갑니다.
- 질문이 떠 있는 동안 캡처 위에 후보 박스(빨강, 점선, 노랑)와 번호를 그립니다.
- 캡처를 클릭하면 위치 표시가 생기고 답에 붙습니다.
- 단계 정보에 기대한 변화, 일어난 변화, 기대와 다름, 참고한 지식을 표시합니다.
- 시스템별 지식 목록 화면을 둡니다.
- 서버 없이 여는 내보내기 HTML(`view.py --export`)에는 질문과 답을 읽기 전용으로 보여 줍니다.

화면 배치의 기준은 사용자가 본 목업입니다(2026-11-13 대화). 장면 1은 그대로, 장면 2는 "A 번호로 답하기"를 기본으로 하고 "C 캡처에서 직접 찍기"로 보완합니다. "B 눈금 칸"은 만들지 않습니다.

### 10. 가상 앱 확장

지금 가상 앱은 세 장면을 재현하지 못합니다. 필터 칸은 어디를 눌러도 열리고, 표는 헤더가 한 줄이며 소계 행이 없습니다.

- **선택 칸 여는 방식.** 실행 옵션으로 "어디를 눌러도 열림"(지금, 기본값)과 "화살표로만 열림"을 고릅니다. 화살표 방식에서 칸의 몸통을 누르면 입력 커서만 생기고 목록은 열리지 않습니다. 화살표의 노출은 필터 영역의 노출 방식을 따릅니다: ref면 칸 안의 버튼, text면 트리에 없음(칸의 글자와 위치만), pixel이면 아무것도 없음.
- **같은 이름의 칸 3개.** 지금 있는 3칸 필터(Shop)를 씁니다.
- **묶음 헤더 표.** 2단 헤더(위 헤더가 아래 열 여러 개를 덮음)와 행 계층(SHOP, 그룹공정, 공정), 소계 행이 있는 화면이 필요합니다. 그룹공정이 "소계"이고 공정이 비어 있는 행이 있어야 합니다. 배치의 기준은 사용자가 준 "전공정 생산현황 화면 예시"입니다. 셀을 누르면 팝업이 뜹니다. 새 화면으로 넣을지 기존 화면의 옵션으로 넣을지는 빌더가 정하되, 기존 테스트는 통과하거나 의도를 밝혀 고칩니다.
- **이벤트 기록.** 칸 몸통 클릭, 화살표 클릭, 셀 클릭(행과 열 포함)을 기록해 하니스가 장면의 성공을 화면 밖에서 판정할 수 있게 합니다.
- 앞 설계의 원칙은 그대로입니다. 같은 옵션이면 같은 화면이 나오고, 에이전트는 이벤트 기록을 읽지 않습니다.

## 테스트

- **앱을 띄우지 않는 테스트.** 표시 번호, 부분 좌표 계산, 셀 찾기(2단 헤더, 후보 여럿, 글자 없음), 변화 비교, 질문 대기와 답, 지식 창고의 저장·찾기·수정, 완료 확인(파일은 임시 폴더), 루프의 강제 규칙(연속 두 번, 그림 지점, 지식 참고 뒤 실패)을 캡처한 CLI 응답과 가짜 모델로 확인합니다.
- **가상 앱의 창 없는 테스트.** 새 옵션과 새 화면을 지금의 `tests/test_virtual_mes.py` 방식으로 확인합니다.
- **실제 창 테스트.** 목표 1~7의 기계 동작을 정해진 순서로 움직이는 가짜 모델로 확인합니다. `VIRTUAL_MES_LIVE=1`일 때만 돌고, 돌리기 전에 사용자에게 확인받습니다.
- **모델을 쓰는 확인.** 목표 1~7을 실제 모델로 뷰어에서 한 번씩 실행해 봅니다. 사용자가 직접 답하므로 자동화하지 않고 점검표로 남깁니다.
- **일반화 확인(목표 8).** 가상 앱이 아닌 앱 두 개 이상, UI 툴킷이 서로 다른 것으로 합니다. 어느 앱으로 할지는 빌더가 제안하고 사용자가 정합니다. 실제 창을 띄우므로 사용자 확인이 필요합니다.
- 요구사항마다 그것을 어기면 실패하는 테스트가 적어도 하나 있어야 합니다.

## 빌더에게 맡기는 것

- 도구 이름, 인자 이름, 모듈과 파일 배치.
- 지식 파일의 형식(YAML 등)과 항목 하나를 파일 하나로 둘지 여부. 조건은 사람이 읽고 고칠 수 있을 것, 항목 하나를 따로 고치고 지울 수 있을 것.
- 이미지 라이브러리를 쓸지와 무엇을 쓸지, 이미지를 모델에 넘기는 방식.
- 시스템 지침(프롬프트)의 문구.
- 대기 시간, 연속 실패 횟수 같은 수치의 기본값. 설정으로 바꿀 수 있어야 합니다.
- 질문, 캡처 보기, 등록 초안 작성이 단계 수 한도(`max_steps`, 지금 기본 12)와 토큰 한도에 어떻게 계산되는지. 질문과 답을 주고받다가 한도에 걸려 실행이 끊기지 않아야 합니다.
- 작업자 사이의 일 나누기. 관찰과 루프, 묻기와 뷰어, 지식 창고와 완료 판정, 가상 앱 확장의 네 묶음이 자연스러운 경계입니다. `agent/loop.py`와 `agent/tools.py`는 여러 묶음이 건드리므로 도구와 이벤트의 계약을 먼저 정합니다.

## 미확인

- 내부 LLM이 이미지를 어떤 형태로 받는지(도구 결과 안, 사용자 메시지), 이미지 한 장의 비용과 지연.
- 모델이 캡처에서 고른 좌표의 정확도. 재 보지 않았습니다.
- 실제 MES의 표가 글자 요소로 보이는지, 그림뿐인지. 배경 문서의 미확인 항목과 같습니다.
- 화살표 버튼의 이름이 시스템과 언어에 따라 어떻게 나오는지. 이 설계는 이름에 의존하지 않습니다.
- DPI 배율이 100%, 175%가 아닌 화면에서 이미지 좌표와 화면 좌표의 변환이 맞는지. 175%에서는 캡처에서 고른 지점이 맞는 셀에 닿는 것을 확인했습니다(`tests/test_scenes_live.py`의 `test_image_point_lands_on_the_cell_at_this_dpi`, 2026-11-13).
- 모델이 실제로 알맞은 때에 묻는지와 등록 초안의 질. 하니스가 강제하는 것(좌표 클릭, 후보가 여럿인 셀, 기대와 다른 결과의 반복, 좌표가 든 지식의 거절)만 테스트로 확인했습니다.
- 등록 글에 화면의 업무 값(수량, 날짜, 이름)이 들어가는 것은 지침으로만 막습니다. 승인할 때 사람이 봐야 합니다.
- 실행과 뷰어가 같은 지식 항목의 사용 횟수를 동시에 올리면 한쪽이 사라질 수 있습니다. 파일 잠금은 없습니다.
- 회사에서 여러 사람이 같은 지식 창고를 쓰게 될 때 누가 승인하는지. 지금은 한 사람이 쓴다고 가정합니다.
- 목표 8의 일반화 확인에 쓸 앱.
