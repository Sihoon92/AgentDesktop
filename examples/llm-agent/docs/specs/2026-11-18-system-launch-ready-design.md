# 시스템 골라 띄우고 준비될 때까지 기다리기 설계

- 날짜: 2026-11-18
- 상태: 사용자 승인(2026-11-18), 구현됨(커밋 전, 실제 창 확인 전). 구현 계획: [2026-11-18-system-launch-ready](../plans/2026-11-18-system-launch-ready.md)
- 대상: `examples/llm-agent`의 설정(`agent/settings.py`), 작업 만들기(`agent/task.py`), 대상 앱 띄우기(`agent/tools.py`), 루프 시작(`agent/loop.py`), 실행 시작(`run.py`, `viewer/run_manager.py`, `viewer/server.py`, `viewer/static/`), 점검(`check.py`), 기록과 요약, 가상 MES(`virtual-mes/`). `agent-desktop` CLI는 고치지 않습니다.
- 앞선 설계: [관찰, 묻기, 배우기](2026-11-13-observe-ask-learn-design.md), [단계로 나눠 실행하기](2026-11-14-staged-run-design.md), [텍스트 모델과 비전 모델 나눠 쓰기](2026-11-16-text-and-vision-models-design.md). 원칙은 그대로입니다.

## 왜 하는가

회사에는 MES가 여러 벌 있고(예: 울산, 천안소형, 천안중대형), 벌마다 실행 파일 경로가 다릅니다. 사용자가 원하는 것은 이렇습니다.

- 시스템마다 exe 경로를 설정 파일에 한 번 적어 둡니다.
- 뷰어에서 시스템을 고르고 지시를 넣어 실행하면, 그 MES가 열립니다.
- MES가 다 열릴 때까지 기다린 뒤에 첫 단계를 시작합니다.

사용자가 말한 회사 MES의 시작 과정은 이렇습니다.

1. exe를 실행하면 작은 팝업 창이 먼저 뜹니다.
2. 그다음 메인 화면이 뜹니다.
3. 메인 화면에 '생산준비', '생산운영', '생산분석', '설비운영', '품질운영', '기준정보' 같은 메뉴가 보이면 그것이 최초 화면입니다. 로그인은 없습니다.

지금 코드는 이렇습니다.

- 설정 파일에는 `exe`와 `system`이 하나씩만 있고, 뷰어는 실행 파일 경로를 글로 입력받습니다.
- 모델이 `launch_target`을 부르면 `agent-desktop launch <exe>`가 창이 하나라도 뜨는 순간 돌아옵니다. 그 창이 팝업이어도 "열렸다"가 됩니다.
- 대상 프로세스는 `launch`가 돌려준 pid와 `process_instance`로 고정됩니다(`Toolbox._rows`). 팝업을 띄운 프로세스가 메인 화면을 다른 프로세스로 띄우고 끝나면, 메인 화면은 대상의 창 목록에 나오지 않습니다. 회사 MES가 그런지는 모릅니다.
- 기다리는 장치로는 모델이 부르는 `wait_for_text`(트리를 다시 읽어 글자가 나올 때까지)와 baseline의 요소 기다리기가 있습니다.

## 용어

- **시스템:** 설정 파일에 이름과 exe 경로로 적어 둔 대상 앱 하나입니다. 이름은 지식 폴더 이름(`knowledge\<시스템>\`)으로도 씁니다.
- **준비 신호:** 대상 앱이 다 열렸다고 볼 수 있는 화면의 글자입니다. 설정 파일에 적습니다(예: `생산운영`).
- **준비 기다리기:** 하니스가 대상 앱을 띄운 뒤 준비 신호가 보일 때까지 창 목록과 화면을 다시 읽는 일입니다.
- **준비된 창:** 준비 신호가 처음 보인 창입니다. 그 창의 프로세스가 이후 실행의 대상이 됩니다.

## 목표와 하지 않는 것

목표:

1. 설정 파일에 시스템 여러 개를 이름과 exe 경로로 적을 수 있습니다.
2. 뷰어에서 시스템을 목록으로 고릅니다. 고른 시스템의 exe를 띄우고, 그 이름을 지식 폴더 이름으로 씁니다.
3. 준비 신호가 설정되어 있으면, 하니스가 모델의 첫 호출 전에 대상 앱을 띄우고 준비 신호가 보일 때까지 기다립니다. 모델 호출 수를 쓰지 않습니다.
4. 팝업과 메인 화면이 같은 프로세스든 다른 프로세스든 준비된 창을 찾아 대상으로 삼습니다.
5. 정한 시간 안에 준비 신호가 보이지 않으면 모델을 부르지 않고 이유를 남긴 채 멈춥니다.
6. 고른 시스템이 이미 떠 있으면 건드리지 않고, 닫고 다시 실행하라고 알리며 멈춥니다. 실행은 항상 최초 화면에서 시작합니다.
7. 집에서 이 흐름을 가상 MES로 재현하고 시험할 수 있습니다.

하지 않는 것:

- 로그인 처리. 회사 MES에는 로그인이 없다고 사용자가 말했습니다.
- "화면이 멈추면 준비" 같은 일반 판정. 사용자가 고른 방법(준비 신호)이 아니고, 팝업이 떠 있는 동안 멈춘 화면을 준비로 잘못 볼 수 있습니다.
- 시스템마다 다른 준비 신호. 지금 아는 MES들은 같은 메뉴를 쓰므로 공통 값 하나만 둡니다. 필요해지면 나중에 더합니다.
- 화면 글자가 접근성 트리에 나오지 않는 앱의 준비 판정(그림으로 판정). 회사 MES의 메뉴는 읽을 수 있는 형태라고 사용자가 확인했습니다. 그림으로만 된 시스템도 있어 나중에 따로 고도화합니다.
- 여러 시스템을 한 실행에서 함께 띄우기. 한 실행은 시스템 하나입니다.

## 1. 설정 파일

새 키 세 개를 더합니다.

```yaml
systems:
  울산: C:\MES\Ulsan\MES.exe
  천안소형: C:\MES\CheonanS\MES.exe
  천안중대형: C:\MES\CheonanL\MES.exe
ready_text: 생산운영
ready_timeout_s: 180
```

| 키 | 값 | 뜻 |
| --- | --- | --- |
| `systems` | 이름 → exe 절대 경로의 묶음 | 고를 수 있는 시스템. 이름은 지식의 시스템 이름 규칙(영문, 숫자, 한글, `.`, `_`, `-`, 64자)을 따름. 경로는 `exe`와 같은 규칙(절대 경로, 제어 문자 없음) |
| `ready_text` | 비어 있지 않은 글 | 준비 신호. 대상 앱의 창에 이 글이 보이면 준비된 것 |
| `ready_timeout_s` | 1 이상의 정수, 기본 180 | 준비 기다리기의 최대 시간(초) |

- `systems`는 지금 설정 파서가 받는 첫 묶음 값입니다. 값이 묶음이 아니거나, 이름이나 경로가 규칙에 맞지 않거나, 비어 있으면 실행하지 않고 오류로 멈춥니다. 오류 이유에는 시스템 이름과 경로를 넣지 않고 몇 번째 항목인지만 넣습니다(점검 출력에 경로를 넣지 않는 규칙).
- 기존 `exe`와 `system`은 그대로 둡니다. 시스템 하나만 쓰는 PC나 `run.py --exe`는 지금처럼 동작합니다.
- `ready_text`는 설정 파일에서 고른 앱에만 적용합니다. 실행의 exe가 `systems`의 한 항목이거나 설정의 `exe`일 때입니다. `run.py --exe`, 뷰어의 "직접 입력", 작업 파일의 exe로 띄운 다른 앱에는 적용하지 않습니다. 그 앱이 MES가 아니면 매번 시간 초과로 멈추기 때문입니다. 작업 파일은 `ready_text`와 `ready_timeout_s`를 직접 적어 켤 수 있습니다.
- `ready_text`가 없으면 준비 기다리기를 하지 않습니다. 지금처럼 모델이 `launch_target`을 부릅니다.
- 앱의 글(`생산운영`)은 설정 파일에만 있고 코드에는 넣지 않습니다(`tests\test_application_agnostic.py`).

## 2. 시스템 고르기

- **뷰어:** 설정의 `systems`가 있으면 "설정"의 실행 파일 칸 자리에 시스템 목록을 보여 줍니다. 목록 끝에 "직접 입력"을 두고, 고르면 지금의 실행 파일 칸과 시스템 칸이 나옵니다. `systems`가 없으면 지금 화면 그대로입니다.
- **뷰어 서버:** 상태 응답(`/api/status`)에 시스템 이름 목록을 더합니다. 경로는 보내지 않습니다. 실행 요청은 시스템 이름을 보내고, 서버(`RunManager`)가 설정에서 exe를 찾습니다. 모르는 이름이면 `InvalidRun`으로 거절합니다.
- **`run.py`:** `--system <이름>`이 `systems`에 있는 이름이면 그 시스템의 exe를 씁니다.
- **exe를 고르는 순서:** `--exe` > `--system`이 가리키는 `systems` 항목 > 작업 파일의 exe > 설정의 `system`이 가리키는 `systems` 항목 > 설정의 `exe`. 명령줄 인자가 작업 파일보다 앞서는 지금 규칙을 따릅니다. 뷰어 목록의 기본 선택은 설정의 `system`이 `systems`에 있으면 그것, 없으면 첫 항목입니다.
- 고른 시스템의 이름은 지식 폴더 이름이 됩니다. 실행 기록(`run.json`)의 `system`에도 지금처럼 남습니다.

## 3. 준비 기다리기

준비 신호가 있는 실행에서, 루프는 모델을 처음 부르기 전에 대상 앱을 띄우고 준비를 기다립니다(`_Run.run`의 첫 턴 전). 하니스가 하는 일이므로 단계의 호출 수와 토큰에 들어가지 않고, 승인 모드에서도 승인을 묻지 않습니다(사람이 실행을 누른 것이 곧 띄우라는 뜻).

순서:

1. `list-windows`로 지금 떠 있는 창을 기억합니다(실행 전 창).
2. `agent-desktop launch <exe>`를 부릅니다. 실패하면 지금처럼 멈춥니다.
   - **같은 시스템이 이미 떠 있으면 멈춥니다(사용자 결정).** Windows의 `launch`는 경로가 똑같은 exe가 이미 돌고 있으면 새로 띄우지 않고 그 프로세스를 돌려줍니다(`crates/windows/src/system/launch_attach.rs`). 돌려받은 프로세스(pid와 `process_instance`)가 1의 실행 전 창 목록에 있으면, 그 시스템이 이미 떠 있던 것입니다. 이때는 모델을 부르지 않고 "같은 시스템이 이미 떠 있습니다. 닫고 다시 실행해 주세요"라는 이유로 멈춥니다. 떠 있는 MES는 건드리지 않습니다.
   - 판정은 경로가 같은 exe로만 합니다. 다른 시스템(예: 울산을 켜 둔 채 천안 실행)은 경로가 달라 막지 않습니다. `launch --no-attach`는 쓰지 않습니다. 이 옵션은 exe 파일 이름만 비교해서, MES마다 파일 이름이 같으면 다른 시스템까지 막기 때문입니다.
   - 실행기가 메인 화면을 **다른 exe**로 띄우는 MES는 위 판정에 걸리지 않습니다. 사용자에 따르면 회사 MES는 이미 떠 있을 때 exe를 다시 누르면 새 화면이 뜨지 않습니다. 그래서 **실행 뒤 30초 동안 새 창이 하나도 뜨지 않으면** 준비 시간을 다 기다리지 않고 멈춥니다. 새 창은 실행 전 창 목록에 없던 창이고, 팝업도 새 창입니다. 이때 실행 전 창 가운데 준비 신호가 있는 창이 있으면 "같은 시스템이 이미 떠 있는 것 같습니다. 닫고 다시 실행해 주세요"를, 없으면 "실행했지만 창이 뜨지 않았습니다"를 이유로 남깁니다.
3. 약 1초마다 다음을 되풀이합니다.
   - 후보 창: `launch`가 돌려준 프로세스의 창, 그리고 실행 전 창에 없던 모든 창.
   - 후보 창마다 트리를 읽어 이름이 준비 신호와 **똑같은 요소**가 있는지 봅니다(앞뒤 공백만 무시). 글 전체에서 부분 문자열을 찾는 `wait_for_text`와 달리, 팝업의 제목이나 안내 글에 신호 글자가 섞여 있어도 팝업을 준비된 창으로 잡지 않기 위해서입니다.
   - 신호가 든 창이 나오면 그 창이 준비된 창입니다.
4. 준비된 창의 pid와 `process_instance`를 대상 프로세스로 삼고, 그 창을 지금 창으로 둡니다. 팝업을 띄운 프로세스와 다르면 바꿉니다.
5. `ready_timeout_s` 안에 신호가 보이지 않으면 모델을 부르지 않고 멈춥니다. 새 창이 30초 동안 하나도 뜨지 않으면 그보다 먼저 멈춥니다(2의 셋째 항목).

기다린 결과는 모델에게 주는 첫 메시지(지시와 브리핑)에 붙입니다. 대상 앱이 이미 떠서 준비되었고 창이 무엇인지 알려, 모델이 `launch_target`부터 부르지 않게 합니다.

준비가 끝난 뒤의 `launch_target`은 다시 띄우지 않고 지금 대상의 상태(pid, 창 목록)를 돌려줍니다. 팝업을 띄우는 실행기를 한 번 더 실행하지 않기 위해서입니다. `restart_target`은 대상 프로세스를 닫은 뒤 위 1~5를 다시 합니다.

baseline 실행(`--baseline`)도 준비 신호가 있으면 `launch_target` 대신 같은 준비 기다리기를 거칩니다.

## 4. 기록, 뷰어, 요약

- **이벤트:** 준비 기다리기를 시작할 때와 끝날 때 `events.jsonl`에 `ready` 이벤트를 남깁니다. 끝날 때는 찾았는지, 걸린 시간(ms), 읽은 횟수, 대상 프로세스가 바뀌었는지를 담습니다. 준비된 창의 관찰은 지금의 기다리기처럼 관찰 하나로 남겨 뷰어 타임라인에 보이게 합니다.
- **뷰어:** 시작 이벤트가 있고 끝 이벤트가 없는 동안 "대상 앱 준비 중"과 지난 초를 보여 줍니다. 끝나면 타임라인의 첫 칸이 준비된 창의 화면입니다.
- **`run.json`과 요약:** 준비 신호의 글은 넣지 않습니다. 수만 넣습니다: 기다린 초, 찾았는지, 대상 프로세스가 바뀌었는지. 준비 시간 초과로 멈춘 실행은 요약에서 그 이유가 코드로 구분됩니다.

## 5. 점검 (`check.py`)

- 설정 항목은 `systems`의 개수와 `ready_text`가 있는지만 출력합니다. 이름, 경로, 글은 출력하지 않습니다.
- 앱 관찰 항목(창을 띄움, `--skip app`으로 건너뜀)은 준비 신호가 있으면 같은 준비 기다리기를 해서 찾았는지와 걸린 초를 보여 줍니다. 회사에서 "메뉴 글자가 트리에 나오는가"를 먼저 확인하는 수단입니다. `--system <이름>`으로 점검할 시스템을 고르고, 없으면 뷰어의 기본 선택과 같은 시스템 하나만 점검합니다. 모든 시스템을 차례로 띄우지 않습니다.

## 6. 가상 MES

집에서 회사 MES의 시작 과정을 재현하는 옵션 세 개를 더합니다.

| 옵션 | 뜻 |
| --- | --- |
| `--splash-ms <N>` | 작은 팝업 창을 N밀리초 띄운 뒤 닫고 메인 화면을 띄움 |
| `--launcher` | `--splash-ms`와 함께. 팝업을 띄운 프로세스가 메인 화면을 다른 프로세스(같은 exe, 팝업 옵션 없이 나머지 인자 그대로)로 띄우고 끝남 |
| `--menu-delay-ms <N>` | 메인 화면이 뜬 뒤 N밀리초 지나서 메뉴를 채움. 창이 떴다고 준비된 것이 아님을 시험 |
| `--single-instance` | `--launcher`와 함께. 메인 화면이 이미 떠 있으면 실행기가 팝업도 새 창도 없이 끝남 |

회사 MES는 팝업과 메인 화면이 다른 프로세스일 가능성이 높다고 사용자가 말했으므로(확실하지는 않음), 기본 시험 조합은 `--splash-ms`와 `--launcher`를 함께 쓰고, 같은 프로세스 조합(`--launcher` 없이)도 시험합니다. 이미 떠 있는 경우는 가상 MES를 먼저 띄워 두고 실행해 시험합니다(멈춰야 함). `--launcher`의 실행기가 이미 떠 있는 메인 화면을 보면 새 창 없이 끝나게 하는 옵션(`--single-instance`)을 더해, 회사 MES처럼 "다시 눌러도 새 화면이 뜨지 않는" 경우와 30초 판정도 시험합니다. 다른 폴더에 복사한 가상 MES를 띄워 둔 채 실행하는 경우는 막지 않아야 합니다.

옵션 파일(`VirtualMes.args`)로도 줄 수 있습니다. `--launcher`가 띄우는 다른 프로세스는 옵션 파일을 읽지 않고 받은 인자만 씁니다. 팝업 창의 제목과 글은 메뉴의 글과 겹치지 않습니다. 이벤트 기록에 팝업이 뜨고 닫힌 것과 메뉴가 채워진 것을 남깁니다.

## 7. 바뀌지 않는 것

- 준비 신호가 없는 실행은 지금과 똑같습니다.
- 대상을 고정하는 방식(pid와 `process_instance`)은 그대로입니다. 바뀌는 것은 준비된 창을 찾은 순간 한 번 고정 대상을 옮기는 것뿐입니다.
- 지식, 질문, 단계, 비전 모델 동작은 그대로입니다.

## 설계자가 정한 것 (사용자가 말한 것이 아님)

1. 준비 신호는 모든 시스템 공통 값 하나입니다. 사용자가 말한 MES들이 같은 메뉴를 쓴다고 봤습니다.
2. `ready_timeout_s` 기본값은 180초입니다.
3. 다시 읽는 간격은 약 1초입니다. 큰 창은 트리 읽기에 1~2초가 걸릴 수 있으므로, 간격은 "읽기가 끝난 뒤 1초"입니다.
4. 후보 창에 "실행 전에 없던 모든 창"을 넣어 팝업과 메인 화면이 다른 프로세스여도 찾습니다. 관계없는 새 창은 준비 신호 판정이 걸러 냅니다.
5. 같은 시스템이 이미 떠 있는지는 `launch`가 돌려준 프로세스가 실행 전 창 목록에 있었는지로 판정합니다(멈추는 것 자체는 사용자 결정).
6. 뷰어는 시스템 경로를 받지 않고 이름만 주고받습니다.
7. 준비 기다리기는 승인 모드에서도 승인을 묻지 않습니다.
8. `ready_text`는 설정 파일에서 고른 앱(`systems` 항목, 설정의 `exe`)에만 적용합니다.
9. 준비 신호는 요소 이름이 똑같을 때만 찾은 것으로 봅니다.
10. exe를 고르는 순서는 2절의 순서입니다. `check.py`는 시스템 하나만 점검합니다.
11. 실행 뒤 30초 동안 새 창이 하나도 뜨지 않으면 멈춥니다(설정 키 없이 고정값). 사용자가 말한 "다시 눌러도 새 화면이 뜨지 않음"을 180초 기다리지 않고 알아보기 위해서입니다.

## 확인이 필요한 것

1. **준비 신호의 요소 이름이 정확히 `생산운영`인지.** 메뉴는 읽을 수 있는 형태라고 사용자가 확인했습니다. 요소 이름에 다른 글(예: 단축키 표시)이 붙어 있으면 똑같은 이름 판정에 걸리지 않으므로, 회사에서 `check.py`의 앱 관찰 항목으로 확인합니다.
2. **팝업과 메인 화면이 같은 프로세스인지.** 다른 프로세스 같다고 사용자가 말했지만 확실하지 않습니다. 설계는 어느 쪽이든 동작합니다. 뷰어의 `ready` 이벤트에 대상 프로세스가 바뀌었는지가 남으므로 첫 실행에서 알 수 있습니다.
3. **MES가 다 열리는 데 걸리는 시간.** 180초보다 길면 `ready_timeout_s`를 늘립니다. 팝업이 30초 안에 뜨지 않는 PC라면 새 창 판정의 30초도 늘려야 합니다.

## 방법 비교 (사용자가 고름)

1. **하니스가 준비 신호를 보고 기다림 (고름).** 설정에 시스템 목록과 준비 신호를 적고, 하니스가 띄운 뒤 신호가 보이는 창을 찾아 대상으로 삼습니다. 팝업과 메인 화면이 다른 프로세스여도 따라갑니다.
2. **화면이 멈추면 준비로 봄.** 설정할 것이 없지만 팝업이 떠 있는 동안 멈춘 화면을 준비로 잘못 볼 수 있고, 프로세스가 바뀌는 문제가 남습니다.
3. **모델에게 맡김.** 모델이 띄우고 `wait_for_text`로 기다립니다. 코드는 가장 적지만 기다리는 데 모델 호출을 쓰고, 모델이 팝업에서 먼저 움직일 수 있습니다.

이미 떠 있는 경우는 "그대로 씀", "멈추고 안내", "닫고 다시 띄움" 가운데 "멈추고 안내"를 골랐습니다. 매번 최초 화면에서 시작해야 실행 기록으로 워크플로를 만들 수 있고, 메뉴가 같은 다른 MES를 잘못 조작할 위험이 없기 때문입니다.
