# 회사 시스템 캡처 세션(`survey.py`)과 회사 GLM 정리 절차

- 날짜: 2026-11-27
- 상태: 구현됨, 실제 창 확인 끝(2026-11-27). 사용자 승인(2026-11-27). 사용자가 정한 것은 아래 "사용자가 정한 것"
- 대상: `examples/llm-agent`의 진입점 `survey.py`(새), 새 모듈(계열 판별, Win32 사실, UIA 개수, 세션 실행, 가설, 코드표, 전달 블록), 새 폴더 `company/`(회사 Claude Code용 규칙과 훅), 생성되는 문서(`docs/company-survey/`). `agent-desktop` CLI(Rust)는 고치지 않습니다.
- 대체: [새 시스템 조사와 회사 GLM 실행 전용 장치](2026-11-25-company-survey-design.md)(2026-11-25)를 대체합니다. 그 문서의 가설 목록, 계열 판별, 이름 공개 범위 "A", `company/` 훅은 이 문서에 옮겨 와 그대로 살리고, "띄운 직후 창 하나를 한 번 조사"하는 진입점과 "같은 앱이 둘이면 멈춤" 규칙은 버립니다.
- 앞선 설계: [CUA 배경](../cua-background.md)의 "집–회사 제약", [시스템 프로파일](2026-11-19-system-profile-design.md)

## 왜 하는가

집에서 만든 CUA는 기억으로 만든 가상 MES에서만 검증되었고, 회사의 MES/GSCM에서는 한 번도 돌지 않았습니다. 회사 정보는 집으로 가져올 수 없고, 사용자가 손으로 옮겨 적는 몇 줄만 돌아옵니다. 목적은 **그 몇 줄의 정보량을 최대로 늘리는 것**입니다. 알고 싶은 것은 두 가지입니다.

1. **회사 시스템이 무엇으로 만들어졌나**(UI 툴킷, 그리드 부품, 창 구조). 같으면 접근성 트리의 모양도 같으므로, 가상 MES를 같은 툴킷으로 다시 만들어 집에서 진짜에 가깝게 검증할 수 있습니다.
2. **실제로 무슨 일이 벌어지나**(켤 때 뜨는 팝업, 에러 창, 로그인 화면, 다른 프로세스가 띄우는 창, 응답 없음). CUA를 실제로 막을 것은 이런 예상 밖의 창입니다.

켜는 순간을 한 번 조사하면 1은 알 수 있어도 2는 거의 보지 못합니다. 그래서 사용자가 앱을 평소처럼 쓰는 동안 계속 떠 있다가, 사용자가 신호를 줄 때마다 그 순간을 저장하는 **캡처 세션**으로 바꿉니다.

## 용어

- **세션:** `survey.py` 한 번의 실행. 시작부터 종료까지 떠 있으며 여러 번 캡처합니다. 결과는 `captures/<세션>/`.
- **캡처:** 사용자가 단축키나 떠 있는 버튼으로 찍은 한 순간. `C01`, `C02`…
- **감시 기록:** 캡처 사이에도 세션이 남기는, 창이 생기고 사라진 기록. 글자 없음.
- **앱 프로세스:** 대상 시스템의 exe로 시작된 프로세스와 그 자손.
- **사실(facts):** 스크립트가 모은 수, 계열 이름, 코드. 판정은 사실에서만 나옵니다.
- **가설:** 집에서 알고 싶은 질문 하나(`H01`…). 판정 코드와 판정별로 집에서 할 일을 가집니다.
- **구조 코드:** 캡처마다 스크립트가 붙이는 코드(창 종류, 프로세스 관계, 상태).
- **장면 코드:** 캡처마다 회사 GLM이 정해진 목록에서 고르는 코드(`ERROR_DIALOG` 등).
- **전달 블록:** 사용자가 집에 옮겨 적는 15줄 이내의 글. 스크립트만 만듭니다.

## 목표와 하지 않는 것

**목표**

- `python survey.py --system <이름>` 하나로 세션을 시작하고, 앱을 쓰는 동안 단축키나 버튼으로 몇 번이든 캡처하고, 종료하면 세션 판정과 전달 블록이 나옵니다.
- 캡처마다 화면 전체 그림, 관련 창들의 접근성 트리, 창 목록과 구조 코드를 저장합니다. 캡처하는 동안 앱의 포커스와 상태를 바꾸지 않습니다.
- 캡처 사이에 생겼다 사라진 창(순식간에 닫힌 팝업 포함)도 감시 기록에 남습니다.
- 회사 GLM은 `company/`에서 시작해 캡처를 읽고 정리하며, 장면 코드와 사람의 답을 `labels.yaml`에 적습니다. 전달 블록은 스크립트가 `labels.yaml`을 검사한 뒤 만듭니다.
- 집에서는 옮겨 적은 블록을 `docs/company-survey/feedback/<날짜>.md`에 넣고, 스크립트가 오타를 잡고 코드를 뜻과 "다음 할 일"로 풀어 줍니다.
- 가설과 코드표는 코드 한 곳에만 정의하고, 저장소의 문서는 그 정의에서 생성합니다.

**하지 않는 것**

- 앱을 띄우거나 클릭하거나 입력하지 않습니다. 사용자가 평소처럼 켜고 씁니다.
- OCR을 하지 않습니다. 화면 글자의 뜻은 회사 PC 안에서 GLM과 사람이 트리와 그림을 보고 판단합니다.
- 회사 결과를 집으로 보내는 자동 경로(업로드, 메일)를 만들지 않습니다.
- 키 입력이나 마우스를 기록하지 않습니다(키로거로 보일 일을 하지 않음). 전역 단축키 등록(`RegisterHotKey`)만 씁니다.
- 셸 명령으로 파일을 우회해 고치는 경우까지 훅이 완벽하게 막지는 않습니다. 그 경우는 코드 변경 기록으로 드러납니다.

**실패로 보는 것**

- 전달 블록, 콘솔 출력, `session.json`, `facts.json`, `events.jsonl`에 화면 글자, 창 제목, 요소 이름, 경로, 원래의 창 클래스 이름이나 DLL 이름이 들어감.
- `labels.yaml`에 코드표에 없는 값이 있는데 전달 블록이 만들어짐.
- 캡처나 감시가 앱의 포커스를 옮기거나, 떠 있는 팝업을 닫히게 함.
- 가설 문서·코드 문서와 코드의 정의가 어긋남.
- 회사 Claude Code가 추적 파일을 고쳤는데 블록이 "변경없음"이라고 적음.

## 사용자가 정한 것

- **이름 공개 범위 "A"(2026-11-25에 정함, 유지):** 회사 밖으로 나갈 수 있는 출력(전달 블록, 콘솔)과 이름 없는 사실 파일에는 알려진 계열 이름과 수, 코드만 넣습니다. `--show-names`일 때만 모르는 창 클래스와 사내 DLL의 파일 이름을 회사 PC에만 남는 `summary.md`의 지정된 절에 적습니다.
- **가설 목록 한 곳(2026-11-25에 정함, 유지):** 가설을 코드 한 곳에 두고 판정, 결과 문서, 저장소 문서가 모두 그것을 따릅니다.
- **회사 GLM은 실행·읽기·정리만(2026-11-25에 정함, 유지):** `company/`의 규칙과 훅으로 강제합니다.
- **캡처 세션(2026-11-27):** "세션 시작 → 여러 번 캡처 → 종료 → GLM 정리"가 원래의 "한 번 조사"를 대신합니다.
- **캡처 방법(2026-11-27):** 전역 단축키와 떠 있는 버튼을 함께 씁니다.
- **한 번에 찍는 범위(2026-11-27):** 전경 창, 같은 앱의 창, 직전 캡처 이후 새로 뜬 창.
- **감시 기록(2026-11-27):** 단축키를 누르지 않은 순간에도 창이 생기고 사라진 것을 글자 없이 기록합니다.
- **전달 블록은 스크립트가 만듦(2026-11-27):** GLM은 정해진 코드 목록에서 고르기만 하고, 스크립트가 그 값을 검사한 뒤 블록을 만듭니다. 목록에 없는 값이 하나라도 있으면 블록을 만들지 않습니다. GLM의 자유로운 설명은 회사 PC에만 남는 `notes.md`에 씁니다.

## 1. 전체 흐름

```
[회사 PC]
 ① git pull
 ② python survey.py --system GSCM        (세션 시작: 점검 1회, 감시 시작, 버튼 표시)
 ③ 앱을 평소처럼 켜고 씀. 팝업·에러·새 화면이 뜨면 Ctrl+Alt+F9 또는 버튼 → 캡처
 ④ Ctrl+Alt+F10(또는 버튼 메뉴, Ctrl+C) → 세션 종료
      captures\<세션>\ 에 저장, 콘솔에 장면 코드 없는(?) 전달 블록과 다음 할 일 안내
 ⑤ cd company → claude → "정리해줘"
      GLM: 캡처마다 트리와 사실을 읽고 summary.md 옆 notes.md에 정리,
           장면 코드와 사람이 말한 답을 labels.yaml에,
           python ..\survey.py --block <세션> 실행 → 스크립트가 검사하고 블록 출력
 ⑥ 사용자가 블록을 손으로 옮겨 적음
[집 PC]
 ⑦ docs/company-survey/feedback/<날짜>.md 에 붙여 넣기
 ⑧ python survey.py --read-block docs/company-survey/feedback/<날짜>.md
      줄마다 확인 문자로 오타 검사, 코드를 뜻과 다음 할 일로 풀어 출력
 ⑨ 집의 에이전트가 가설 갱신, 가상 MES·에이전트 개선, 다음에 확인할 가설 추가 → 다음 방문 때 ①
```

GLM이 없거나 훅이 동작하지 않는 회사 환경에서도 ④의 블록(장면 코드가 `?`)은 그대로 옮겨 적을 수 있어야 합니다. GLM 정리는 정보를 더하는 단계이지 필수 단계가 아닙니다.

## 2. 세션 실행

### 2.1 시작

인자: `--system`, `--exe`, `--settings`, `--profile`, `--profile-dir`(뜻은 `check.py`와 같음), `--skip llm`, `--show-names`. 대상 exe는 `check.pick_target`과 같은 순서로 고르고, 바로가기면 `check._with_shortcut`(공개 함수 `with_shortcut`으로 바꿈)으로 대상 exe를 얻습니다.

시작할 때 한 번:

1. env 읽기(`load_env`), `check.run_checks(..., skip=["app", *skip])`로 바이너리·설정·LLM·비전 점검. 결과는 H10과 블록 머리에 씁니다.
2. 코드 상태(`git_state.code_state`: 커밋 앞 7자, `examples/llm-agent/` 아래 추적 파일 중 내용이 바뀐 파일; 줄바꿈과 파일 모드 차이는 세지 않음).
3. 프로세스 DPI 인식을 모니터별로 설정(`SetProcessDpiAwarenessContext(PER_MONITOR_AWARE_V2)`, 실패하면 그 아래 단계). 그래야 Win32 좌표, 화면 그림, `list-windows`의 좌표가 같은 물리 픽셀이 됩니다.
4. `agent-desktop session start`, `DesktopClient`(실제 실행이므로 `process_window_handles`, `read_shortcut`을 넘김).
5. 앱 프로세스 찾기(2.2). 이미 떠 있으면 기록합니다(H06 `ALREADY_RUNNING`). 없어도 기다립니다.
6. 전역 단축키 등록, 감시 스레드와 처리 스레드 시작, 떠 있는 버튼 표시. 콘솔에 "캡처: Ctrl+Alt+F9, 종료: Ctrl+Alt+F10"과 세션 폴더 이름(절대 경로 아님)을 찍습니다.

### 2.2 앱 프로세스 알아보기

앱 프로세스를 너무 넓게 잡으면 앱이 띄운 다른 제품(엑셀 내보내기, 도움말 브라우저, WerFault)을 앱으로 판정하고, 너무 좁게 잡으면 런처 뒤의 진짜 앱을 놓쳐 세션 전체가 `SKIPPED`가 됩니다. 그래서 아래 순서로 정합니다.

1. **설치 폴더:** 대상 exe가 있는 폴더(바로가기면 그 대상의 폴더)와 그 아래에 실행 파일이 있는 프로세스는 모두 `APP`입니다. 런처가 같은 폴더의 진짜 앱을 띄우거나, 업데이터·ShellExecute를 거쳐 부모 관계가 끊겨도 잡힙니다.
2. **추가 exe(선택):** `settings.local.yaml`의 `survey_app_exes`(절대 경로 목록)에 적은 실행 파일과 그 폴더도 1과 같이 봅니다. 진짜 앱이 런처와 다른 폴더(예: 사용자 폴더의 내려받은 사본)에 있을 때 씁니다. 설정 파일은 회사 PC에만 있습니다.
3. **자손:** 감시가 프로세스 목록(Toolhelp)을 읽을 때마다, 부모가 앱 프로세스인 새 프로세스를 봅니다. 실행 파일이 Windows 폴더 아래면 `SYSTEM`, 1·2의 폴더 밖이면 `CHILD_OTHER`이고, 둘 다 앱으로 세지 않습니다(H01·H03·H04·H07·H11의 대상이 아님). 앞의 규칙이 먼저입니다: Windows 폴더 → `SYSTEM`, 앱 폴더 → `APP`, 그 밖의 자손 → `CHILD_OTHER`, 나머지 → `OTHER`.
4. **캡처로 고르기(마지막 수단):** 세션이 끝날 때까지 `APP` 프로세스를 하나도 못 봤으면, 첫 캡처의 전경 창 프로세스(`SYSTEM`이 아닌 것)를 앱으로 삼아 판정하고 H06을 `PICKED_BY_CAPTURE`로 둡니다. 회사 방문 한 번이 통째로 버려지지 않게 하기 위해서이며, 블록에 그렇게 드러나므로 집에서 감안해 읽습니다.

- 프로세스는 (pid, 시작 시각) 쌍으로 구별합니다(`agent/process_identity.process_started_at`). pid 재사용으로 남의 프로세스를 앱으로 보지 않기 위해서입니다. CLI와 맞출 때는 `list-windows`의 `process_instance`를 씁니다.
- 실행 파일 경로를 읽지 못하는 프로세스(관리자 권한 등)는 `UNKNOWN`이고, 그 수를 `session.json`에 남깁니다.

### 2.3 감시 (`SURVEY_POLL_S = 0.5`)

감시 스레드는 0.5초마다 다음을 읽고, 바뀐 것만 `events.jsonl`에 한 줄씩 씁니다. 모두 ctypes Win32 읽기이며 앱에 메시지를 보내지 않습니다.

- 최상위 창 목록(`EnumWindows`): 보이는 창이 새로 생기거나 사라지면 `window_shown`/`window_hidden`.
- 앱 프로세스의 생성과 종료: `process_started`/`process_exited`.
- 앱 프로세스의 보이는 최상위 창마다 `IsHungAppWindow`: `hung_start`/`hung_end`.
- 전경 창(`GetForegroundWindow`): 바뀌면 `foreground`. 세션 자신의 창(버튼, 콘솔)은 "직전 전경 창"으로 기억하지 않습니다.

이벤트 한 줄의 칸(모두 코드와 수):

| 칸 | 뜻 |
| --- | --- |
| `t` | 세션 시작부터 초(소수 한 자리) |
| `event` | 위 이름 중 하나 |
| `win` | 세션 안의 창 번호(`W1`, `W2`…). hwnd는 회사 PC 안에서만 쓰므로 `trees/`의 매핑에만 남김 |
| `proc` | 세션 안의 프로세스 번호(`P1`…) |
| `rel` | `APP`, `CHILD_OTHER`, `SYSTEM`(실행 파일이 Windows 폴더 아래), `OTHER`, `UNKNOWN`(경로를 못 읽음). 정하는 순서는 2.2 |
| `kind` | `window_shown`에서: `DIALOG`(`#32770`), `OWNED`(소유 창 있음), `TOP`. `MAIN`은 캡처에서만 정함 |
| `fg_within` | `foreground` 이벤트에서: 새 전경 창이 뜬 지 `SURVEY_FOREGROUND_S = 2`초 안이면 그 직전 전경 창의 `rel`. 아니면 없음 |
| `family` | 창 클래스의 계열(`agent/toolkits.py`), 모르면 `?` |
| `owned` | 소유 창이 있으면 그 창의 `win`, 없으면 없음 |
| `modal` | 소유 창이 비활성(`IsWindowEnabled` 거짓)이면 참 |
| `bounds_class` | 작음/중간/전체 같은 크기 구분(`S`, `M`, `L`), 좌표는 남기지 않음 |

창 제목은 읽지도 남기지도 않습니다. 창 클래스 이름은 계열 판별에만 쓰고, 모르는 이름은 `--show-names`일 때만 세션 끝의 `summary.md` 절로 갑니다.

### 2.4 캡처 신호

- **전역 단축키(주):** `RegisterHotKey`. 기본은 캡처 `Ctrl+Alt+F9`, 종료 `Ctrl+Alt+F10`이며 `settings.local.yaml`의 `survey_capture_hotkey`, `survey_end_hotkey`로 바꿉니다. 등록에 실패하면(다른 프로그램이 이미 씀) 콘솔에 `HOTKEY_TAKEN`을 찍고 버튼만으로 계속합니다. PrintScreen은 회사 보안 프로그램이 가로챌 수 있어 기본으로 쓰지 않습니다.
- **떠 있는 버튼(보조):** tkinter의 작은 창. `WS_EX_NOACTIVATE | WS_EX_TOPMOST | WS_EX_TOOLWINDOW`를 주어 **눌러도 전경 창이 바뀌지 않게** 합니다(포커스를 잃으면 닫히는 팝업을 지키기 위해). 버튼에는 캡처 수와 처리 중 표시(색)를 보여 줍니다. 왼쪽 클릭은 캡처, 오른쪽 클릭은 "종료" 메뉴(이때는 포커스를 가져가도 됨). 끌어서 옮길 수 있습니다.
- 그래도 버튼을 누른 순간의 전경 창이 세션 자신의 창이면, 감시가 기억한 "직전 전경 창"을 그 캡처의 전경 창으로 씁니다.
- 캡처하면 짧은 소리(`MessageBeep`)로 알립니다.

### 2.5 캡처 한 번: 빠른 단계와 느린 단계

신호를 받은 스레드가 **빠른 단계**를 바로 하고(목표 0.5초 이내), 나머지는 처리 스레드의 대기열로 넘깁니다. 화면은 금방 바뀌므로 바뀌기 쉬운 것을 먼저 찍습니다.

**빠른 단계**

1. 캡처 번호(`C01`…)와 시각.
2. 화면 전체 그림(`PIL.ImageGrab.grab(all_screens=True)`) → `capture-NN/screen.png`. 그림이 거의 한 색이면 `SHOT_BLANK`(보안 프로그램이 캡처를 막는 경우).
3. 최상위 창 목록과 전경 창, 직전 캡처 이후 새로 뜬 창(감시 기록 기준), 앱 창마다 `IsHungAppWindow`.
4. 이 캡처의 **대상 창**을 정합니다. 순서대로 중복 없이 최대 `SURVEY_MAX_WINDOWS = 8`개:
   1. 전경 창(관계가 무엇이든)
   2. 직전 캡처 이후 새로 뜬, 아직 보이는 창(다른 프로세스 포함)
   3. 앱 프로세스의 보이는 최상위 창
   - 이 중 첫 번째를 캡처의 **주 창**이라 하고, 블록의 캡처 줄은 주 창의 구조 코드를 씁니다.

**느린 단계**(처리 스레드, 캡처 순서대로)

1. 대상 창마다 `list-windows`의 행을 hwnd로 맞추고(`agent/handles.window_number`) `snapshot`을 읽습니다(창마다 `SURVEY_SNAPSHOT_MS = 5000`). 결과 코드: `OK`, `TRUNCATED`, `TIMEOUT`, `UNRESPONSIVE`(`APP_UNRESPONSIVE`), `GONE`(이미 닫힘 또는 목록에 없음), `ERROR`. 트리는 `capture-NN/trees/W<k>.json`에 그대로 저장합니다(회사 PC 전용 원자료).
2. 대상 창마다 `agent.survey.kinds`로 종류별 수, `id_keys`로 ID 키.
3. 처음 보는 앱 프로세스(pid, 시작 시각)마다 한 번: 모듈 목록 → 계열별 수(Windows 폴더 아래 모듈은 계열 판별에만), 프로세스 비트 수. 앱 프로세스의 창 클래스 계열은 캡처마다 다시 셉니다(창이 바뀌므로).
4. 주 창이 앱 창이면(아니면 앱의 가장 큰 보이는 창) UIA FrameworkId와 패턴 개수(`agent/uia_count.ps1`, 노드 상한 `UIA_MAX_NODES = 3000`, 시간 상한 `UIA_TIMEOUT_S = 30`). UIA는 앱 프로세스마다 한 번만, 주 창이 그 프로세스의 `MAIN` 창인 첫 캡처에서 셉니다(H04에는 그것으로 충분하고, 느린 단계가 길어지지 않게). 다른 캡처의 `uia`는 비어 있습니다.
5. 주 창의 모니터 해상도와 배율, 모니터 수.
6. 주 창의 트리를 읽은 **바로 그때** 주 창 그림을 다시 찍어(`ImageGrab`으로 그 창의 사각형만) `window.png`로 두고, 그 위에 요소 박스를 종류별 색으로 그린 `overlay.png`를 만듭니다(박스에 글자 없음, 구석에 범례). 신호 순간의 화면은 `screen.png`에 그대로 남습니다. 그림과 박스가 다른 순간에서 오면 사람이 H12–H14를 틀리게 답하므로, 오버레이는 늘 트리와 같은 순간의 그림을 씁니다. 그때 주 창이 이미 닫혔으면 오버레이를 만들지 않습니다.
7. `capture-NN/facts.json`을 씁니다(3장).

- 대기열은 최대 `SURVEY_QUEUE_MAX = 5`개. 넘치면 느린 단계를 `QUEUE_FULL`로 건너뛰고 빠른 단계의 결과만 남깁니다.
- 느린 단계는 신호 순간이 아니라 처리 순간의 상태를 읽습니다. 그 사이 창이 닫혔으면 `GONE`이라는 사실로 남고, 화면 그림과 감시 기록은 이미 그 순간을 담고 있습니다.
- 느린 단계가 쓰는 CLI 명령은 `list-windows`, `snapshot`뿐이고, 앱에 쓰는 명령은 보내지 않습니다.

### 2.6 종료

종료 신호를 받으면: 단축키 해제 → 버튼 닫기 → 감시 중지 → 대기열이 빌 때까지 기다림(최대 60초, 넘으면 남은 캡처를 `QUEUE_ABANDONED`로) → 세션 판정(4장) → `session.json`, `summary.md`, 장면 코드가 `?`인 전달 블록 → 콘솔에 블록과 다음 할 일("`company` 폴더에서 claude를 시작해 '정리해줘'라고 하세요"). Ctrl+C와 콘솔 창 닫기도 같은 마무리를 합니다(가능한 범위에서).

### 2.7 스레드

tkinter는 주 스레드에서 돌고, 단축키 메시지 루프(`GetMessage`, 단축키는 등록한 스레드로 옴), 감시, 처리가 각각 스레드 하나입니다. 스레드 사이는 `queue.Queue`, tkinter 갱신은 `after()`로만 합니다. Win32 호출은 테스트에서 가짜로 바꿀 수 있도록 한 객체(`win32` 의존성) 뒤에 둡니다.

### `facts.json` (캡처 하나)

`id`, `t`, `shot`(`OK`/`SHOT_BLANK`), `main`(주 창의 `win`), `windows`: 대상 창마다 `win`, `proc`, `rel`, `family`, `kind`(아래 구조 코드), `owned`, `modal`, `hung`, `read`(스냅샷 결과 코드), `read_s`, `kinds`(종류별 수), `nodes`, `depth`; `uia`(개수 또는 실패 코드), `monitor`(`<가로>x<세로>@<배율>`, 모니터 수), `new_since_last`(새로 뜬 창 수), `slow`(`DONE`/`QUEUE_FULL`/`QUEUE_ABANDONED`).

### 구조 코드 (캡처의 주 창)

- **창 종류 `kind`:** `MAIN`(앱의 가장 큰 소유 없는 최상위 창), `DIALOG`(계열이 Win32 대화상자 `#32770`), `OWNED`(소유 창이 있는 다른 최상위 창), `TOP`(그 밖의 최상위 창). 대상 창은 모두 최상위 창이므로 MDI 자식 창은 종류가 아니라 H07에서 다룹니다.
- **관계 `rel`:** 2.3의 표(`APP`, `CHILD_OTHER`, `SYSTEM`, `OTHER`, `UNKNOWN`).
- **상태 `state`:** `OK`, `HUNG`(`IsHungAppWindow` 또는 `UNRESPONSIVE`), `TIMEOUT`, `GONE`, `BLANK`(`SHOT_BLANK`).

블록에서는 `kind/rel/state`로 씁니다(예: `DIALOG/SYSTEM/OK`).

## 4. 가설

### H05의 비교

로그인 직후 화면과 메인 화면처럼 **다른 화면**의 ID를 비교하면 ID가 바뀐 것으로 잘못 판정합니다. 집에서는 이 판정으로 프로파일의 `stable_ids`를 정하므로, 같은 화면끼리만 비교합니다.

- 비교 대상은 서로 다른 앱 프로세스(`process_instance`가 다름)에서 읽은 앱 창 트리 두 개입니다. 세션 안에서 앱이 다시 켜진 경우의 두 프로세스, 또는 이번 세션의 트리와 `.check/<시스템>.json`에 남은 기록입니다.
- **같은 화면으로 보는 조건:** 창 클래스 계열이 같고, 종류별 수(`named_ref`, `unnamed_ref`, `text`, `blank`)의 합이 서로 20% 안이고, 창 종류(`kind`)가 같아야 합니다. ID 자체는 조건에 쓰지 않습니다(ID가 바뀌는 앱을 "다른 화면"으로 잘못 거르지 않기 위해).
- 그런 짝이 있으면 ID 키를 비교합니다. 같으면 `STABLE`, 다르면 `CHANGES`, 양쪽 모두 키가 없으면 `NO_IDS`. 짝이 없으면 `PENDING`. 짧은 수: 비교한 짝 수.
- `.check/<시스템>.json`은 **읽기만** 하고 세션이 고쳐 쓰지 않습니다. `check.py`의 비교 기준을 바꾸지 않기 위해서입니다. 그 기록에는 종류별 수가 없으므로, 기록과의 비교는 이번 세션의 `MAIN` 창 중 처음 읽은 것과만 하고 같은 화면 조건은 확인하지 못한다고 근거에 적습니다(`check.py`가 띄운 직후 화면과 비교하는 것이므로).

### 팝업으로 세는 창

H15와 H16은 이번 세션 방식이 노리는 "예상 밖의 창"이므로, 잡음을 빼서 늘 같은 값이 나오지 않게 합니다.

- **앱이 띄운 팝업(`SAME_PROC`):** `APP` 프로세스의 창 중 앱 창에 소유되었거나(`owned`) 모달(`modal`)인 창. 소유 없는 앱 최상위 창(스플래시, 따로 뜨는 로그인 창, 메인 창)은 팝업으로 세지 않고 짧은 수에 `pre`로 따로 셉니다. 로그인인지는 GLM의 장면 코드가 알려 줍니다.
- **다른 프로세스가 띄운 팝업(`OTHER_PROC`, `SYSTEM`, `OTHER`):** `APP`이 아닌 프로세스의 창 중 앱 창에 소유되었거나, 뜬 뒤 2초 안에 전경이 되었는데 그 직전 전경이 앱 창이었던 것(`fg_within`이 `APP`). 사용자가 Alt+Tab으로 다른 앱에 간 것(이미 있던 창이 전경이 됨)과 전경을 가져가지 않는 알림 토스트는 세지 않습니다.
- **H15:** 첫 앱 창이 뜬 뒤 `SURVEY_STARTUP_S = 60`초 안의 위 팝업. 둘 다 있으면 `BOTH`. 세션이 앱의 시작을 보지 못했으면(`ALREADY_RUNNING`) `NOT_SEEN`. 짧은 수: `<앱 팝업>/<다른 팝업>/pre<수>`.
- **H16:** 그 60초 밖의 다른 프로세스 팝업. Windows 폴더 아래 프로세스면 `SYSTEM`, 아니면 `OTHER`. 짧은 수: 횟수.

`manual` 가설의 기본 답은 `?`입니다. `summary.md`에 답하는 방법(어느 캡처의 `overlay.png`에서 무엇을 볼지, 범례 색 이름으로)이 적힙니다.

판정 문턱값 중 앞 계획(2026-11-25)에서 정한 것은 그대로 씁니다: H01의 70%와 `Win32`는 다른 계열이 없을 때만 셈, H03의 0.6/0.2, H04의 패턴 묶음.

## 5. 장면 코드와 `labels.yaml`

### 코드표 (`agent/survey_codes.py`)

장면 코드, 구조 코드, 가설 판정 코드, 실패 코드를 모두 이 모듈 한 곳에 둡니다. 처음 장면 코드:

| 코드 | 뜻 |
| --- | --- |
| `STARTUP_POPUP` | 켤 때 뜨는 안내·공지·업데이트 창 |
| `LOGIN` | 로그인 화면 |
| `MAIN` | 메인 화면(메뉴와 작업 영역) |
| `GRID` | 표가 중심인 조회 화면 |
| `FORM` | 입력 칸이 중심인 등록 화면 |
| `ERROR_DIALOG` | 오류를 알리는 창 |
| `WARNING_DIALOG` | 경고 창 |
| `CONFIRM_DIALOG` | 예/아니오를 묻는 창 |
| `MESSAGE` | 단순 알림 창 |
| `LOADING` | 기다리는 중 표시 |
| `OTHER` | 위에 없음 |
| `?` | 판단하지 않음(기본) |

### `labels.yaml` 형식

```yaml
version: 1
captures:
  C01: STARTUP_POPUP
  C02: MAIN
manual:
  H12: SOME
  H14: CELLS
```

### 검사 규칙 (`python survey.py --block <세션>`)

- 최상위 키는 `version`, `captures`, `manual`만. `version`은 1.
- `captures`의 키는 그 세션에 있는 캡처 번호만, 값은 장면 코드표의 코드만.
- `manual`의 키는 `manual` 가설 번호만, 값은 그 가설의 코드만.
- 값은 YAML 문자열 하나. 목록, 사전, 주석 뒤의 글은 허용하지 않음(주석은 YAML 파서가 버리므로 문제 없음).
- 하나라도 어긋나면 블록을 만들지 않고 `LABEL_INVALID`와 어긋난 **줄 번호와 규칙 이름만** 찍습니다. 잘못 적힌 값 자체는 찍지 않습니다(값에 화면 글자가 있을 수 있으므로).
- `labels.yaml`이 없으면 모든 장면과 사람의 답을 `?`로 보고 블록을 만듭니다.

## 6. 전달 블록

스크립트만 만듭니다(`agent/survey_block.py`). 세션 종료 때와 `--block` 때 같은 함수가 같은 결과를 냅니다. 최대 15줄.

```
[전달] v2 · 6dbba10 · 변경없음 · GSCM · 캡처7 · 32분 ·K7
H01 DELPHI(14/16)   H02 FARPOINT   H03 LOW(4/0/85)   H04 INVOKE_ONLY ·3F
H05 PENDING   H06 LAUNCHER   H07 MDI   H08 NONE ·Q2
H09 1920x1080@1.25(1)   H10 TOOLS_ONLY   H11 COMPLETE(2.4s)   H12 SOME ·M8
H13 ?   H14 CELLS   H15 OTHER_PROC(2)   H16 SYSTEM(1) ·7A
H17 SEEN(1/12s)   H18 WIN32_DIALOG ·D4
C01 STARTUP_POPUP DIALOG/OTHER/OK ·9A
C02 LOGIN MAIN/APP/OK ·2C
C03~C05 GRID MAIN/APP/OK ·F1
C06 ERROR_DIALOG DIALOG/SYSTEM/OK ·88
C07 ? OWNED/APP/HUNG ·0B
```

- **머리 줄:** 버전, 커밋 앞 7자(모르면 `커밋?`), `변경없음`/`변경있음 N`, 시스템 이름, 캡처 수, 세션 길이(분).
- **코드 상태:** 커밋과 변경 수는 세션 시작 때 값입니다(그 코드가 캡처를 만들었으므로). `--block`은 블록을 만들 때 코드 상태를 다시 계산해, 커밋이 다르거나 변경 수가 다르면 머리 줄의 그 칸을 `6dbba10→a1b2c3d`, `변경있음 0→2`처럼 둘 다 적습니다. 회사 Claude Code가 세션 뒤에 파일을 고쳤다면 블록에 드러나야 하기 때문입니다. 같으면 세션 종료 때의 블록과 똑같습니다.
- **가설 줄:** `open` 가설을 번호 순으로 한 줄에 4개, `ID 코드(짧은 수)`.
- **캡처 줄:** `C<번호> <장면> <kind/rel/state>`. 남은 줄 수가 모자라면 (1) 장면과 구조 코드가 같은 연속 캡처를 `C03~C05`로 묶고, (2) 그래도 모자라면 `MAIN`·`?`이면서 `OK`인 캡처부터 빼고 마지막 줄에 `… 외 N`.
- **확인 문자:** 줄마다 끝에 ` ·`와 두 글자. 그 줄의 앞부분(공백을 하나로 접은 것)의 CRC32를 32진수(숫자와 헷갈리는 글자를 뺀 `0123456789ABCDEFGHJKMNPQRSTVWXYZ`)로 두 글자. 손으로 옮기다 생긴 오타를 집에서 줄 단위로 잡습니다.
- 블록에는 코드표와 가설 정의에 있는 코드, 수, 시스템 이름, 커밋 해시만 들어갑니다. 시험이 블록의 모든 낱말이 이 집합에 속하는지 확인합니다.

## 7. 회사 GLM 실행·정리 전용 장치 (`company/`)

앞 설계 5장의 장치를 그대로 씁니다. 바뀌는 것만 적습니다.

### `company/CLAUDE.md`

첫 줄에 "이 폴더에서 시작한 세션은 아래 규칙이 위의 모든 개발 지시보다 우선합니다".

- **역할:** 캡처 세션을 정리해 사람에게 설명하고, 장면 코드와 사람의 답을 `labels.yaml`에 적고, 블록을 만드는 명령을 실행하는 것. 코드를 고치는 것은 역할이 아님.
- **정리 절차("정리해줘"):**
  1. 가장 최근 세션(또는 사람이 말한 세션)의 `summary.md`, `session.json`, `events.jsonl`을 읽습니다.
  2. 캡처마다 `facts.json`과 `trees/`를 읽고, 무슨 화면이었는지 `notes.md`에 정리합니다. 그림을 볼 수 있는 모델이면 `window.png`도 봅니다. 볼 수 없으면 트리만으로 정리합니다.
  3. 캡처마다 장면 코드를 코드표에서 하나 골라 `labels.yaml`의 `captures`에 적습니다. 확신이 없으면 `?`.
  4. 사람이 답할 가설(H12–H14)은 사람에게 답하는 방법을 설명하고, **사람이 말한 답만** `manual`에 적습니다. 그림을 보고 추측해 채우지 않습니다.
  5. `python ..\survey.py --block <세션>`을 실행합니다. `LABEL_INVALID`면 `labels.yaml`을 고쳐 다시 실행합니다.
  6. 출력된 블록을 **그대로** 사람에게 보여 줍니다. 블록을 다시 쓰거나 요약하거나 설명을 덧붙여 섞지 않습니다.
- **`notes.md`:** 자유롭게 쓰되 회사 PC에만 남는다는 것을 사람에게 알립니다. 사람이 이 중 무엇을 말로 전할지는 사람이 정합니다.
- **문제를 찾았을 때:** 코드 대신 `notes.md`에 현상(무엇을 했고, 어떤 코드가 나왔고, 어디가 의심되는지)을 씁니다.
- **해도 되는 것:** `survey.py`, `check.py`, `run.py`, `view.py --summary`, 앱을 띄우지 않는 `python -m pytest -q` 실행. `captures/`, `runs/`, `knowledge/`, `profiles/`, `workflows/`, `settings.local.yaml` 같은 Git 제외 파일 읽고 쓰기. `git status`, `log`, `diff`, `pull`.
- **하면 안 되는 것:** 추적 파일 수정, 새 추적 파일, 저장소 상태를 바꾸는 git 명령, 패키지 설치, Rust 빌드.

### 훅 (`company/.claude/settings.json`, `company/hooks/guard.py`)

앞 설계·계획(2026-11-25 작업 10)의 규칙 그대로입니다. Edit·Write·MultiEdit·NotebookEdit는 저장소 안의 제외되지 않은 파일과 `company/` 아래를 막고, Bash는 저장소 상태를 바꾸는 git 하위 명령·패키지 설치·`cargo`를 막고, 판단할 수 없는 입력은 막습니다. `captures/`는 Git 제외이므로 쓰기가 허용됩니다. 루트 `.gitignore`에 `!examples/llm-agent/company/.claude/`와 `!examples/llm-agent/company/.claude/settings.json` 예외를 더합니다.

## 9. 시험

모두 앱을 띄우지 않고 실제 단축키·버튼·화면을 쓰지 않습니다. Win32, CLI, 화면 그림, UIA, git은 가짜 의존성으로 바꿉니다.

- **공개 범위:** 가짜 창 제목·요소 이름·클래스·DLL·경로에 표지 문자열을 넣고 세션을 돌려, 콘솔·블록·`session.json`·`facts.json`·`events.jsonl`에 표지가 없는지 확인. `--show-names`면 `summary.md`의 지정 절에만 나옴.
- **블록:** 15줄 상한, 묶기와 빼기 순서, 확인 문자 계산과 `--read-block`의 오타 검출(한 글자 바꾸면 그 줄만 `오타?`), 블록의 모든 낱말이 허용 집합에 속함.
- **`labels.yaml` 검사:** 모르는 키, 없는 캡처 번호, 코드표 밖 값, 한글 문장 값, 목록 값 → `LABEL_INVALID`이고 출력에 그 값이 없음. 파일 없음 → `?`로 블록.
- **감시:** 가짜 창 목록의 연속 상태로 생김/사라짐/응답 없음/전경 이벤트, 앱 자손 추적(런처가 끝난 뒤에도 자손 유지), pid 재사용 구별.
- **캡처:** 대상 창 고르기 순서와 상한, 버튼을 누른 순간 전경이 세션 창이면 직전 전경 창을 씀, 느린 단계의 결과 코드(`GONE`, `TIMEOUT`, `UNRESPONSIVE`), 대기열 넘침, `SHOT_BLANK`, UIA를 프로세스마다 한 번만 셈.
- **판정:** 가설마다 사실 → 판정 코드 표 시험, 문턱값 경계, 새 가설 H15–H18의 시간 창과 관계 규칙.
- **CLI 명령:** 세션이 CLI에 보내는 명령이 `session`, `list-windows`, `snapshot`, `version`뿐인지.
- **문서 동기화:** `hypotheses.md`, `codes.md`가 생성 결과와 같음.
- **훅:** 앞 계획 작업 10의 시험 그대로.
- **앱 이름 없음:** `survey.py`와 새 모듈이 `tests/test_application_agnostic.py`의 검사 대상에 들어감.

실제 창 확인(가상 MES로 세션을 열고, 앱을 켜서 팝업을 띄우고 캡처해 H01 `WINFORMS`, H15, 캡처 줄이 맞는지, 버튼을 눌러도 포커스가 안 옮겨지는지)은 사용자에게 확인받은 뒤에 합니다.

## 설계자가 정한 것 (사용자가 말한 것이 아님)

- 진입점 이름은 `survey.py`를 유지합니다(`agent/capture.py`가 이미 스크린샷 모듈이라 `capture.py`는 헷갈림). 세션 폴더는 `captures/`.
- 버튼은 `WS_EX_NOACTIVATE`로 포커스를 가져가지 않게 하고, 직전 전경 창 기억은 예비로 둡니다.
- 캡처를 빠른 단계와 느린 단계로 나누고, 화면 전체 그림은 Pillow `ImageGrab`으로 찍습니다.
- 앱은 세션이 띄우지 않습니다. 그래서 H06의 코드가 바뀌고 앞 계획의 "대상 창 고르기"(작업 7)는 필요 없습니다.
- 새 가설 H15–H18과 구조 코드, 장면 코드 목록.
- 블록 줄마다 확인 문자 두 글자.
- 기본 단축키 Ctrl+Alt+F9/F10, 감시 0.5초, 대상 창 최대 8개, 스냅샷 5초, UIA 3000노드·30초, 대기열 5, 시작 팝업 시간 창 60초.
- 키 입력·마우스는 기록하지 않습니다.
- `labels.yaml`이 틀렸을 때 값 자체를 찍지 않습니다.
- 앱 프로세스는 설치 폴더 기준으로 알아보고(2.2), 다른 폴더의 진짜 앱은 `survey_app_exes`로 더하며, 끝까지 못 보면 첫 캡처의 전경 창으로 고릅니다(`PICKED_BY_CAPTURE`).
- H05는 창 계열·종류·요소 수로 같은 화면인 짝만 비교하고, `.check/` 기록은 읽기만 합니다.
- H15·H16의 팝업은 소유·모달이거나 뜬 뒤 2초 안에 앱에게서 전경을 가져간 창만 셉니다.
- `--block`은 코드 상태를 다시 계산해 달라졌으면 두 값을 함께 적습니다.
- 오버레이는 트리를 읽은 순간 다시 찍은 창 그림 위에 그립니다.
- 앞 계획(2026-11-25)의 작업 1–6, 8, 10은 아직 구현되지 않았으므로 이번 계획에 함께 넣습니다.

## 구현자에게 맡기는 것

- 판정 문턱값 중 이 문서와 앞 계획이 정하지 않은 것.
- 계열 판별 표의 정확한 패턴(앞 계획 작업 1이 최소).

- 크기 구분(`S`/`M`/`L`)의 경계.

## 확인이 필요한 것

- `agent-desktop list-windows`가 다른 프로세스의 창(WerFault 등)까지 나열하는지, 그 `bounds`가 DPI 인식 프로세스의 Win32 좌표와 같은 픽셀인지. 구현 첫 단계에서 집 PC로 확인하고, 다르면 Win32 좌표를 기준으로 바꿉니다.
- 회사 Claude Code가 프로젝트의 훅을 따르는지(첫 정리 때 추적 파일 하나에 Edit를 시켜 막히는지 봄).
- 회사 PC의 PowerShell 실행 정책이 `.ps1`을 막는지(막히면 `-ExecutionPolicy Bypass` 또는 명령 문자열).
- 회사 보안 프로그램이 `RegisterHotKey`나 화면 캡처를 막는지. 막히면 각각 `HOTKEY_TAKEN`(버튼으로 계속), `SHOT_BLANK`로 드러납니다.

## 방법 비교 (사용자가 고름)

1. **상주 세션 (고름).** 한 프로세스가 떠 있으면서 단축키·버튼을 받고 감시 기록을 남깁니다. 순식간에 닫힌 팝업도 기록에 남고 캡처가 빠릅니다. 구현은 가장 큽니다.
2. **누를 때마다 실행.** 단축키마다 조사 스크립트를 새로 띄웁니다. 앞 계획을 가장 많이 다시 쓰지만 누를 때마다 몇 초가 걸리고, 누르기 전에 닫힌 창은 놓칩니다.
3. **완전 자동.** 새 창이 뜰 때마다 사람 없이 찍습니다. 잡음과 쓸데없는 그림이 많습니다. 1에 감시 기록을 넣어 장점을 대부분 얻습니다.

전달 블록은 "GLM이 양식대로 씀"과 "GLM은 코드만 고르고 스크립트가 검사해 만듦(고름)" 중에서 골랐습니다. 앞의 것은 화면 글자를 넣지 않기를 GLM이 지키기를 믿는 방식이고, 뒤의 것은 글자가 들어갈 자리가 없는 방식입니다.
