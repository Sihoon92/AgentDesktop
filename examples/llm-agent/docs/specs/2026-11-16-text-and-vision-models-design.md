# 텍스트 모델과 비전 모델 나눠 쓰기 설계

- 날짜: 2026-11-16
- 상태: 사용자 승인(2026-11-18), 구현됨(커밋 전, 실제 모델 확인 전). 구현 계획: [2026-11-18-text-and-vision-models](../plans/2026-11-18-text-and-vision-models.md)
- 대상: `examples/llm-agent`의 모델 연결(`agent/llm.py`), 화면 그림이 모델에게 가는 경로(`agent/screen_tools.py`, `agent/tools.py`, `agent/history.py`, `agent/images.py`), 실행 시작(`run.py`, `view.py`), 점검(`check.py`), 기록과 요약. `agent-desktop` CLI는 고치지 않습니다.
- 앞선 설계: [관찰, 묻기, 배우기](2026-11-13-observe-ask-learn-design.md), [단계로 나눠 실행하기](2026-11-14-staged-run-design.md). 두 설계의 원칙은 그대로입니다.

## 왜 하는가

회사에서는 사내 OpenAI 호환 LLM을 씁니다. 사용자가 말한 사정은 이렇습니다.

- 사내 모델 중에는 그림을 받지 못하는 모델이 있고, 추론은 그 모델이 더 좋습니다. 그래서 실행 전체는 그 모델이 이끌게 하고 싶습니다.
- 그림을 꼭 봐야 할 때만 비전 모델을 따로 부릅니다.
- 사내 API는 `openai` 파이썬 패키지를 그대로 쓰고, 연결 정보는 API 키, 모델 이름, 주소 세 가지입니다.

지금 코드는 이렇습니다.

- `OpenAIResponder`는 `OpenAI()`를 인자 없이 만듭니다. 그래서 `OPENAI_API_KEY`와 `OPENAI_BASE_URL`은 이미 env에서 읽힙니다.
- 모델 이름은 env가 아니라 명령줄, 작업 파일, `settings.local.yaml`, 코드 기본값(`gpt-6.1-terra`)에서 옵니다.
- 화면 그림은 모두 같은 모델의 대화에 들어갑니다. 모델이 그림을 못 받으면 `image_mode: off`로 그림을 아예 끄는 수밖에 없습니다. 그러면 `look`이 거절되고, 트리에 없는 대상은 찾을 수 없습니다.

## 용어

- **텍스트 모델:** 실행을 이끄는 모델입니다. 계획, 단계 판단, 도구 선택, 질문, 지식 등록 초안을 맡습니다. 지금의 "모델"과 같습니다.
- **비전 모델:** 그림 한 장과 질문 하나를 받아 글로 답하는 모델입니다. 도구를 부르지 않고 대화 기록도 갖지 않습니다.
- **한 모델 방식:** 비전 모델을 지정하지 않은 실행입니다. 지금과 똑같이 동작합니다.
- **나눈 방식:** 비전 모델을 지정한 실행입니다. 텍스트 모델에게는 그림을 한 장도 보내지 않습니다.

## 목표와 하지 않는 것

목표:

1. env에 키, 주소, 모델 이름 세 값만 넣으면 사내 모델로 실행됩니다.
2. env에 비전 모델 이름을 더 넣으면 나눈 방식이 됩니다. 비전 모델의 키와 주소는 따로 넣을 수도 있고, 비워 두면 텍스트 모델의 값을 씁니다.
3. 나눈 방식에서도 지금 그림으로 하던 일(트리에 없는 대상 찾기, 동작 결과 눈으로 확인하기, 그림을 완료 근거로 내기)을 모두 할 수 있습니다.
4. 비전 모델을 언제, 무엇을 묻느라 불렀는지 기록과 뷰어에 남습니다.

하지 않는 것:

- Chat Completions API 지원. 지금처럼 Responses API만 씁니다(사내 API가 지원한다고 사용자가 확인함). 비전 모델도 같은 API로 부릅니다.
- 텍스트 모델과 비전 모델 외의 세 번째 모델(예: 등록 초안 전용 모델).
- 실행 중에 모델을 바꾸는 것, 비전 모델이 실패하면 다른 모델로 넘기는 것.
- 사람이 보는 그림(뷰어, 실행 기록의 캡처)을 바꾸는 것. 사람은 지금처럼 모든 캡처를 봅니다.

## 1. 연결 정보

### env 이름

| env | 뜻 | 없을 때 |
| --- | --- | --- |
| `OPENAI_API_KEY` | 텍스트 모델의 키 | 실행 거절(지금과 같음) |
| `OPENAI_BASE_URL` | 텍스트 모델의 주소 | OpenAI 기본 주소 |
| `OPENAI_MODEL` | 텍스트 모델 이름 | 아래 우선순위의 다음 값 |
| `VISION_MODEL` | 비전 모델 이름. 있으면 나눈 방식 | 한 모델 방식 |
| `VISION_API_KEY` | 비전 모델의 키 | `OPENAI_API_KEY` |
| `VISION_BASE_URL` | 비전 모델의 주소 | `OPENAI_BASE_URL` |

- `.env`는 지금처럼 `run.py`, `view.py`, `check.py`가 읽습니다(`ENV_FILES`). env 이름은 `.env.example`과 README에 적습니다.
- `VISION_API_KEY`나 `VISION_BASE_URL`만 있고 `VISION_MODEL`이 없으면 설정 실수입니다. 실행을 거절하고 무엇이 빠졌는지 알립니다.

### 모델 이름의 우선순위

작업 파일 > 설정 파일 > env(`OPENAI_MODEL`) > 코드 기본값. `run.py`에는 `--model` 인자가 없고, 이번에도 만들지 않습니다.

- 오케스트레이터의 판단: 설정 파일의 원칙("PC마다 다른 값은 설정 파일")과 사용자가 원하는 "env만으로 동작"을 둘 다 지키려면, env를 코드 기본값 바로 위에 둡니다. 설정 파일에 `model`이 없으면 env가 씁니다.
- 저장소의 작업 파일 `tasks/footprint_open_settings.yaml`이 `model`을 적고 있습니다. 회사에서 이 작업을 돌리면 env보다 작업 파일이 이깁니다. 작업 파일의 `model` 줄은 지웁니다. 작업 파일의 `model`은 그 작업에 특정 모델이 필요할 때만 씁니다.
- 실행 시작 줄에 어떤 모델이 어디서 왔는지 출처만 찍습니다(예: `텍스트 모델: env · 비전 모델: env`). 모델 이름 자체는 찍지 않습니다(요약과 점검 출력의 규칙과 같음).
- 비전 모델 이름은 env에서만 받습니다. 설정 파일 키 `vision_model`도 추가해, 설정 파일이 있으면 env보다 앞서게 합니다. 작업 파일과 명령줄에는 넣지 않습니다.

### 추론 노력

사내 모델이 `reasoning` 인자를 받지 못할 수 있습니다.

- 텍스트 모델: 지금처럼 `reasoning_effort`, `plan_reasoning_effort`를 보냅니다. 값을 `omit`으로 적으면 `reasoning` 인자를 보내지 않습니다. `none`은 그 자체가 유효한 effort 값인 모델이 있어 표시로 쓰지 않습니다. 이 규칙은 텍스트 모델의 모든 호출(실행, 계획, 등록 초안, `check.py`)에 같습니다.
- 비전 모델: 기본으로 `reasoning` 인자를 보내지 않습니다. 설정 파일 키 `vision_reasoning_effort`가 있을 때만 보냅니다.

## 2. 모델 객체

`agent/llm.py`에 연결을 만드는 함수 하나를 둡니다. `run.py`, `view.py`, `check.py`가 각자 `OpenAIResponder`를 만들던 것을 이 함수로 모읍니다.

- 텍스트 쪽은 지금의 `OpenAIResponder`입니다. 키와 주소를 명시적으로 받아 `OpenAI(api_key=..., base_url=...)`를 만듭니다.
- 비전 쪽은 `VisionReader`입니다. `read(picture_path, question) -> VisionAnswer` 하나만 있습니다. 도구 없이 Responses API를 한 번 부르고, 입력은 사용자 메시지 하나(`input_text` 질문 + `input_image` 그림)입니다. `image_mode`는 비전 호출에 쓰지 않습니다. 비전 호출에는 도구 결과가 없어서 그림을 넣는 방식이 하나뿐입니다.
- 나눈 방식이 아니면 `VisionReader`는 없습니다(None). 코드는 "비전 모델이 있는가"로만 갈라집니다.
- 테스트는 지금처럼 가짜 client를 넣습니다. 실제 네트워크는 부르지 않습니다.

## 3. 나눈 방식에서 그림이 가는 곳

지금 그림이 텍스트 모델의 대화에 들어가는 곳은 다섯 곳입니다. 나눈 방식에서는 다섯 곳 모두 텍스트 모델에게 그림을 보내지 않습니다. 대신 아래처럼 바뀝니다.

| 지금 | 나눈 방식 |
| --- | --- |
| `look`: 사진에 번호 박스를 그려 모델에게 보냄 | 텍스트 모델이 `question`을 함께 보냄. 하니스가 사진을 찍고 비전 모델에게 묻고, 답을 `look` 결과의 `vision`에 넣음 |
| 동작 뒤 자동 캡처(불일치, `unconfirmed`) | 하니스가 정해진 질문으로 비전 모델에게 묻고, 답을 동작 결과의 `vision`에 넣음 |
| 질문하라는 정책 거절에 붙는 캡처 | 캡처는 찍어 기록에만 남기고 비전 모델은 부르지 않음. 필요하면 텍스트 모델이 `look`을 부름 |
| `click_point`: 모델이 사진에서 픽셀을 골라 누름 | 그대로. 픽셀은 비전 모델의 답에서 옴 |
| `stage_done`의 그림 근거(`capture`) | 그대로. 텍스트 모델은 비전 모델이 그 캡처에 대해 한 답을 보고 판단함 |

### `look`

- 나눈 방식에서는 `look`의 스키마에 `question`(필수, 글)이 붙습니다. 한 모델 방식의 스키마는 지금과 같습니다. 도구 정의는 실행이 시작될 때 방식에 따라 정해집니다.
- 질문은 텍스트 모델이 알고 싶은 것 하나입니다(예: "조회 버튼은 어느 번호인가", "WA0 옆 체크 표시가 켜져 있는가"). 막연한 화면 묘사 대신 질문에 답하게 해서 답을 짧고 정확하게 만듭니다.
- 결과는 지금의 `look` 결과(`capture`, `window_id`, `width`, `height`, `drawn`, `cropped`)에 `vision`을 더한 것입니다.

### 비전 모델의 답

비전 모델에게 아래 JSON 하나로 답하라고 지시합니다.

```json
{"answer": "질문에 대한 답(글)", "marks": [3], "points": [{"label": "조회 버튼", "x": 412, "y": 88}], "unsure": false}
```

- `marks`: 그림에 그려진 번호 박스 중 답에 해당하는 번호입니다. 번호로 가리킬 수 있으면 번호를 먼저 쓰라고 지시합니다. 텍스트 모델이 `click_part`로 누를 수 있어서 픽셀보다 안전합니다.
- `points`: 번호 박스가 없는 대상의 위치를 **그 캡처 이미지의 픽셀**로 줍니다. 텍스트 모델은 이 값을 `click_point`에 그대로 넣습니다. 픽셀로 고른 클릭에는 지금처럼 사람의 확인이 필요합니다(`agent/policy.py`). 이 규칙은 바꾸지 않습니다.
- `unsure`: 그림으로 판단할 수 없으면 true입니다.
- 하니스가 답을 검사합니다. `marks`는 그 캡처에 그려진 번호만, `points`는 이미지 안의 좌표만 남기고 나머지는 버립니다. 버린 것이 있으면 `vision.dropped`에 개수를 적습니다.
- JSON으로 읽히지 않으면 답 글 전체를 `answer`로 두고 `marks`와 `points`는 비웁니다. 실행을 멈추지 않습니다.
- 비전 호출이 실패하면(네트워크, 거절, 시간 초과) 도구 결과에 `vision: {"error": "<코드>"}`를 넣습니다. 캡처는 남습니다. 텍스트 모델은 다른 방법을 찾거나 사람에게 물을 수 있습니다.

### 좌표 규칙

비전 모델마다 좌표를 내는 방식이 다릅니다. 이미지 픽셀을 내는 모델도 있고, 0~1000으로 정규화한 값을 내는 모델도 있습니다. 또 API가 큰 그림을 내부에서 줄여 보면, 모델은 줄인 그림 기준의 픽셀을 냅니다.

- **보내기 전에 하니스가 줄입니다.** 캡처의 긴 변이 `vision_max_side`(설정 파일 키, 기본 1280)보다 크면 비율을 지켜 줄인 사본을 보내고, 이미지의 `detail`은 `high`로 보냅니다. 모델이 보는 픽셀과 하니스가 아는 픽셀이 같아지게 하려는 것입니다. 원본 캡처는 그대로 두고, 비전 모델이 낸 좌표는 줄인 비율만큼 되돌려 원본 캡처의 픽셀로 텍스트 모델에게 줍니다. `click_point`는 원본 캡처 픽셀을 받으므로 바뀌지 않습니다.
- 설정 파일 키 `vision_points`로 `pixel`(기본)과 `normalized_1000` 중 하나를 정합니다. 하니스가 `normalized_1000`을 보낸 그림의 픽셀로 바꾼 뒤 위처럼 되돌립니다.
- `check.py`의 비전 점검이 어느 값이 맞는지 알려 줍니다(5절). 하니스는 실행 중에 좌표가 맞는지 알 수 없습니다. 그래서 `points`로 고른 클릭은 지금처럼 항상 사람의 확인을 받습니다. 이것이 좌표가 틀렸을 때의 안전장치입니다.

### 자동 캡처에 붙는 질문

동작 뒤 불일치나 `unconfirmed`로 찍는 캡처는 텍스트 모델이 "눈으로 확인해야 하는" 경우입니다. 하니스가 동작의 대상과 기대(`expect`)로 질문을 만듭니다.

- 동작 뒤에는 다시 관찰하면서 번호가 새로 매겨지므로, 질문에 번호를 쓰지 않습니다. 대신 대상의 위치(동작 전에 알던 대상의 화면 영역)를 중심으로 잘라 보냅니다. 지금의 `look(mark)`처럼 `around`로 자르는 방식입니다. 대상 위치를 모르는 동작이면 창 전체를 보냅니다.
- 질문에는 기대의 종류와 대상의 역할, 이름(동작 전 관찰에서 읽은 값)을 넣습니다. 이 값은 실행 중에 텍스트 모델에게도 이미 가는 값이므로 비전 모델에게 보내도 됩니다.
- 질문의 틀(문장)은 `agent/`에 두고, 코드에는 앱 이름이나 화면 글을 넣지 않습니다(`tests/test_application_agnostic.py`).

### 텍스트 모델에게 주는 안내

시스템 프롬프트(`agent/loop.py`)에 나눈 방식일 때만 붙는 문단을 둡니다.

- 당신은 그림을 볼 수 없다. `look`의 `question`으로 비전 모델에게 묻고, 결과의 `vision`을 읽는다.
- 번호(`marks`)가 있으면 `click_part`, 픽셀(`points`)만 있으면 `click_point`를 쓴다.
- `vision.unsure`이거나 `vision.error`면 다시 묻거나 사람에게 묻는다. 비전 모델의 답만으로 확신할 수 없는 대상은 `ask`로 확인한다.

## 4. 호출 수와 토큰

- 단계별 호출 한도(`stage_call_limit`)는 텍스트 모델 호출만 셉니다. 비전 호출은 도구 안에서 일어나는 일입니다.
- 토큰 예산(`token_budget`)에는 비전 호출의 토큰도 더합니다. 비전 호출 때문에 실행이 무한히 길어지지 않게 하기 위해서입니다.
- `run.json`과 요약에 비전 호출 수와 비전 토큰을 따로 적습니다(수만).

## 5. 점검 (`check.py`)

- 지금의 LLM 항목(호출, 도구 호출, 그림 읽기)은 텍스트 모델을 점검합니다. 나눈 방식에서는 텍스트 모델의 그림 읽기 항목을 건너뜁니다(건너뛴 이유: 나눈 방식).
- 나눈 방식이면 비전 항목 두 개를 더합니다.
  - **비전 호출:** 그림 하나와 질문으로 한 번 부릅니다. 지금의 그림 읽기처럼 무작위 숫자를 그린 그림을 읽게 합니다.
  - **비전 좌표:** 알려진 위치에 표시를 그린 그림을 주고 위치를 묻습니다. 답이 픽셀로 맞으면 `pixel`, 0~1000으로 맞으면 `normalized_1000`을 권장 값으로 적고, 둘 다 아니면 실패로 둡니다.
- 출력에는 지금처럼 수와 코드, 출처(env 또는 설정 파일)만 넣습니다. 모델 이름, 주소, 키는 넣지 않습니다.

## 6. 기록과 뷰어

- 비전 호출마다 `events.jsonl`에 `vision` 이벤트를 하나 남깁니다: 캡처 id, 누가 물었는지(`look` 또는 자동 캡처의 이유), 질문, 답(`answer`, `marks`, `points`, `unsure`), 오류 코드, 걸린 시간, 토큰.
- 뷰어의 캡처 옆에 비전 모델의 질문과 답을 보여 줍니다. `points`는 캡처 위에 점으로 그립니다.
- 질문과 답의 글은 `events.jsonl`에만 둡니다. `run.json`과 요약에는 수만 넣습니다(단계 설계와 같은 규칙).

## 7. 바뀌지 않는 것

- 한 모델 방식(비전 모델 미지정)의 동작, 도구 스키마, 기록 형식.
- `image_mode`의 뜻. 한 모델 방식에서만 쓰입니다. 나눈 방식에서는 `image_mode`를 통째로 무시합니다. 그림을 못 받는 텍스트 모델 때문에 회사 설정에 이미 `off`가 들어 있을 가능성이 크고, 그 설정이 비전 모델까지 조용히 끄면 안 되기 때문입니다. 나눈 방식에서 그림을 쓰지 않으려면 `VISION_MODEL`을 지웁니다. `image_mode`가 무시됐으면 실행 시작 줄과 `check.py`에 그 사실을 한 줄로 알립니다.
- 정책과 묻기 규칙, 지식 파일 형식, 단계 실행.

## 오케스트레이터가 정한 것 (사용자가 말한 것이 아님)

- env 이름(`OPENAI_MODEL`, `VISION_MODEL`, `VISION_API_KEY`, `VISION_BASE_URL`)과 모델 이름의 우선순위에서 env의 자리.
- 비전 모델도 Responses API로 부른다는 것.
- 비전 모델의 답 형식(JSON의 `answer`, `marks`, `points`, `unsure`)과 번호를 픽셀보다 먼저 쓰게 하는 것.
- 질문하라는 정책 거절의 캡처에는 비전 모델을 부르지 않는 것.
- 비전 모델에 보내기 전에 하니스가 그림을 줄이고 좌표를 되돌리는 것(`vision_max_side`, 기본 1280, `detail: high`).
- 자동 캡처의 질문에 번호를 쓰지 않고 대상 주변을 잘라 보내는 것.
- 나눈 방식에서 `image_mode`를 무시하는 것.
- 추론 인자를 빼는 표시를 `none`이 아닌 `omit`으로 하는 것.
- 비전 토큰을 토큰 예산에 넣고, 단계 호출 한도에는 넣지 않는 것.
- 좌표 규칙 설정(`vision_points`)과 `check.py`의 비전 좌표 점검.
- 작업 파일 `tasks/footprint_open_settings.yaml`의 `model` 줄 삭제.

## 확인이 필요한 것

- 사내 비전 모델이 Responses API의 `input_image`를 받는지. 받지 않으면 비전 쪽만 Chat Completions로 불러야 합니다.
