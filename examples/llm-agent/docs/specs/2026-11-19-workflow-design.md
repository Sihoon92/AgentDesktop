# workflow 만들기와 파라미터 재실행 설계

- 날짜: 2026-11-19
- 상태: 사용자 승인(2026-11-19), 구현됨(실제 창 확인 전). 구현 계획: [2026-11-19-workflow](../plans/2026-11-19-workflow.md)
- 대상: `examples/llm-agent`의 계획 도구(`agent/tool_schemas.py`, `agent/loop.py`), 기록(`agent/recorder.py`), 실행 시작(`run.py`, `viewer/run_manager.py`, `viewer/server.py`, `viewer/static/`), 요약(`agent/summary.py`), 그리고 새로 만드는 workflow 모듈들. `agent-desktop` CLI는 고치지 않습니다.
- 앞선 설계: [관찰, 묻기, 배우기](2026-11-13-observe-ask-learn-design.md), [단계로 나눠 실행하기](2026-11-14-staged-run-design.md), [시스템 골라 띄우고 준비될 때까지 기다리기](2026-11-18-system-launch-ready-design.md). 배경은 [CUA 배경과 설계 기준](../cua-background.md)의 서비스 흐름 6과 7입니다.

## 왜 하는가

지금 에이전트는 지시를 받을 때마다 모델을 불러 화면을 읽고 조작합니다. 같은 조회를 값만 바꿔 되풀이하는 일에는 느리고 비쌉니다. 회사의 기존 RPA는 사람이 workflow를 손으로 적어야 해서 넓히지 못했습니다.

이 설계는 그 사이를 잇습니다. 사람이 자연어로 한 번 시키고 성공을 확인하면, 그 실행이 모델 없이 다시 도는 workflow가 됩니다. 그 뒤에는 workflow의 ID와 바뀌는 값(Shop, 기간, 저장 경로)만 주면 됩니다.

## 용어

- **workflow:** 모델 없이 다시 실행할 수 있게 적은 단계 목록입니다. 시스템 하나에 속하고 ID가 있습니다.
- **재실행:** workflow를 ID와 파라미터 값으로 실행하는 일입니다. 모델을 부르지 않습니다.
- **파라미터:** 재실행 때 바꿀 수 있는 값입니다. 이름과, 원래 실행에서 쓴 값(예시 값)이 있습니다.
- **대상 적기:** 단계가 누를 요소를 좌표 없이 적은 것입니다(창, 역할, 이름, 기준 글자와 순서).
- **확인 조건:** 단계를 실행한 뒤 화면에서 일어나야 하는 일입니다(창이 열림, 창이 닫힘, 내용이 바뀜).
- **미확인 / 확인됨:** workflow의 상태입니다. 만들어진 직후는 미확인이고, 모델 없는 재실행이 한 번 끝까지 통과하면 확인됨입니다.

## 목표와 하지 않는 것

목표:

1. 성공한 모델 실행(`verified`, `confirmed`)이 끝나면 workflow를 자동으로 만들어 저장하고 ID를 알려 줍니다.
2. workflow는 좌표가 아니라 요소로 대상을 적습니다. 해상도와 DPI가 달라도 다시 찾습니다.
3. 재실행은 모델을 한 번도 부르지 않습니다.
4. 여러 항목을 고르는 목록(Shop)은 "이것만 선택된 상태로 맞추기"로 재실행합니다. 원래 실행과 다른 조합도 됩니다.
5. 단계마다 확인 조건을 검사하고, 깨지면 그 단계에서 멈추고 이유를 코드로 남깁니다.
6. 재실행도 지금의 실행 기록으로 남아 뷰어에서 스텝별로 볼 수 있습니다.
7. 첫 버전은 가상 MES에서 메뉴 → 필터 → 조회 → 엑셀 아이콘 → 저장 → 파일 확인까지 재실행합니다. 아이콘이 트리에 요소로 보이는 설정(`--expose icon=ref`, 지금 이 PC의 `VirtualMes.args`)이 기준입니다.

하지 않는 것:

- **재실행 중 모델 사용.** 확인 조건이 깨져도 모델이 이어받지 않습니다(사용자 결정). 다시 만들려면 같은 지시를 모델 실행으로 돌립니다.
- **등록 전 자동 재실행.** 만들 때는 형식만 검사합니다. 조회와 파일 저장을 자동으로 한 번 더 하지 않습니다(사용자 결정).
- **그림뿐인 대상(사용자 결정).** 트리에 요소가 없어 캡처의 픽셀을 골라 누른 동작(`click_point`, `mouse_click`)은 workflow로 옮기지 않습니다. 그런 동작이 꼭 필요한 실행에서는 workflow를 만들지 않고 이유를 남깁니다(`PICTURE_TARGET`). 우클릭 원형 메뉴(사용자 결정으로 다음 차례)와, 트리에 보이지 않는 아이콘이 여기에 듭니다. 다음 버전에서 함께 설계합니다.
- **기존 RPA의 workflow 형식과 등록 API.** 맞추지 않습니다.
- **ID로 부르는 웹 API, 여러 사용자, 인증.** 첫 버전의 입구는 `run.py`와 뷰어입니다.
- **스크롤해야 보이는 대상.** 화면 밖(`offscreen`) 대상은 멈춥니다.
- **조건 분기와 반복.** workflow는 위에서 아래로 한 번 도는 목록입니다.
- **지난 workflow 고치기와 버전 관리.** 다시 만들면 새 ID가 됩니다.

실패로 보는 것(동작해도 실패):

- 재실행이 틀린 대상을 누르고도 성공으로 끝나는 것. 후보가 없거나 여럿이면 추측하지 않고 멈춥니다.
- 지시에 있던 값인데 workflow가 조작하지 않는 값을 파라미터로 받아 조용히 무시하는 것.
- `agent/`나 `viewer/` 코드에 앱 이름이나 화면의 글이 들어가는 것(`tests\test_application_agnostic.py`).

## 사용자가 정한 것

| 결정 | 고른 것 | 고르지 않은 것 |
| --- | --- | --- |
| 파라미터 수준 | "상태 맞추기" 단계를 둠 | 값 끼우기만 / 파라미터 단계만 모델 사용 |
| 등록 전 확인 | 형식 검사만 하고 미확인 ID를 냄. 첫 재실행 통과가 확인 | 같은 값으로 자동 재실행 / 다른 값으로 재실행해야 등록 |
| 확인 조건이 깨지면 | 그 단계에서 멈추고 보고 | 모델이 이어받음 / 사용자가 고르면 이어받음 |
| 첫 버전 범위 | 아이콘 엑셀 저장까지 | 조회까지 / 원형 메뉴까지 |
| 만드는 방식 | 모델은 묶고 이름 붙이고, 하니스가 대상을 채움 | 모델이 YAML 전체를 씀 / 하니스가 기록을 그대로 옮김 |
| 그림뿐인 대상 | 첫 버전에서 뺌. 아이콘이 요소로 보이는 설정에서 확인 | 첫 버전에 넣음 |

## 1. 전체 흐름

```
모델 실행(지금과 같음)
  └ plan에 파라미터 후보를 적음 ............................ 2절
  └ 성공(verified, confirmed)
       └ workflow 만들기 .................................... 3절
            1. 기록 폴더에서 재료를 읽음
            2. 모델을 한 번 불러 단계 초안을 받음(기록의 번호로 가리킴)
            3. 하니스가 대상 적기와 확인 조건을 기록에서 채움
            4. 형식 검사(기록에 다시 대 보기)
            5. workflows\<시스템>\<ID>.yaml 저장, 상태 "미확인"
재실행(모델 없음) ........................................... 5절
  run.py --workflow <ID> --param shop=WA0,WA1  또는 뷰어
  └ 준비 기다리기 → 단계마다 [대상 찾기 → 동작 → 확인] → 파일 확인
  └ 끝까지 통과하면 workflow 상태가 "확인됨"
```

## 2. 실행 중 파라미터 표시

`plan` 도구에 `params`를 더합니다. 모델은 지시에서 온 값 가운데 다음에 바뀔 수 있는 것을 이름과 함께 적습니다.

```json
{"stages": [...], "params": [{"name": "shop", "value": "WA0, WA1"}, {"name": "period", "value": "전일"}]}
```

- `name`은 영문 소문자로 시작하는 `[a-z][a-z0-9_]*`입니다. 명령줄에서 `--param shop=...`로 쓰는 이름입니다.
- `value`는 지시에 적힌 표현 그대로입니다(예: "조립"). 화면에서 실제로 누른 이름(예: `WA2`)과 다를 수 있습니다. 여러 값이어도 글 하나로 적고, 나누지 않습니다.
- 없으면 빈 배열입니다. 계획을 고칠 때는 지금 규칙대로 전체를 다시 줍니다.
- `plan` 이벤트에 그대로 남습니다. 글이므로 `events.jsonl`에만 두고 `run.json`과 요약에는 넣지 않습니다.

이 목록은 후보이고 쓰임은 둘입니다. workflow의 파라미터 이름이 되고, 조작하지 않은 값을 가려내는 기준이 됩니다(3절). 파라미터의 예시 값은 이 `value`가 아니라 기록에서 옵니다. 배경 문서의 "파라미터는 기록 시점에 구분"을 이렇게 채웁니다.

## 3. workflow 만들기

### 언제

- 모델 실행이 `verified`나 `confirmed`로 끝난 직후, 지식 등록과 따로 한 번 합니다. 사람에게 묻지 않습니다. 기록기가 실행을 닫기 전에 하므로(뷰어가 실행의 끝 이벤트보다 먼저 결과를 받음) 그때 `run.json`의 상태는 아직 `running`입니다. 그래서 성공 여부는 `run.json`이 아니라 실행의 결과 상태로 봅니다.
- 계획이 없는 실행이나 `claimed`, `stopped` 실행에서는 만들지 않습니다.
- 만들기가 실패해도 실행 결과는 바뀌지 않습니다. 이유를 코드로 남깁니다(7절).
- `python run.py --make-workflow <run_id|latest>`로 지난 실행에서 다시 만들 수 있습니다. 초안이 검사에 걸렸을 때 다시 시도하는 길입니다.

### 재료

만들기는 메모리의 상태가 아니라 **기록 폴더**(`runs\<id>\events.jsonl`)만 읽습니다. 그래야 저장해 둔 기록으로 시험하고 `--make-workflow`가 같은 코드를 씁니다.

기록에 세 가지를 더합니다. 이것이 없는 옛 기록에서는 만들지 않습니다(`RECORD_TOO_OLD`).

- **표시 번호:** 관찰 이벤트의 `elements` 항목마다 그 관찰의 표시 번호(`mark`)를 넣습니다. 지금은 순서로만 알 수 있고, 글자 요소가 400개를 넘어 잘리면 순서가 어긋납니다.
- **속한 창:** `elements` 항목마다, 트리에서 가장 가까운 조상 창 요소의 표시 번호(`scope`)를 넣습니다. 관찰한 창 바로 아래면 null입니다. 지금 기록의 `elements`는 평평한 목록이라 요소가 어느 창 안에 있는지 알 수 없습니다(4절의 "범위").
- **저장한 경로:** 모델이 `finish`에 알린 저장 경로를 이벤트로 남깁니다. 지금은 메모리에만 있습니다. 경로는 글이므로 `events.jsonl`에만 둡니다.

### 모델이 하는 일

모델을 한 번 부릅니다. 주는 것:

- 지시, 계획의 파라미터 후보, 단계(목표, 완료 근거, 끝낼 때의 메모)
- 전달된 동작의 목록. 동작마다 번호, 도구, 의도, 대상의 역할과 이름, 값 인자, 기대와 판정, 효과 요약(열리고 닫힌 창), 속한 단계
- 동작이 일어난 창의 관찰 글(표시 번호가 붙은 트리). 같은 창의 연속된 관찰은 마지막 것만 줍니다.

모델은 도구 하나(`propose_workflow`)로 답합니다. 대상을 글로 적지 않고 **기록의 번호로 가리킵니다.**

| 초안 단계 | 모델이 적는 것 | 뜻 |
| --- | --- | --- |
| `act` | 동작 번호, 파라미터 이름(없으면 null) | 그 동작을 그대로 다시 함. 파라미터가 있으면 대상의 이름이나 입력 글이 그 값으로 바뀜 |
| `select_only` | 묶을 동작 번호들, 한 관찰 안에서 "전체 선택" 요소의 표시 번호와 실행이 끝났을 때 선택되어 있던 항목들의 표시 번호, 파라미터 이름 | 그 동작들 대신 "이 목록에서 이 값들만 선택"을 함 |
| `check_file` | 파라미터 이름 | 그 경로에 파일이 생겼는지 확인 |

- 초안에 없는 동작은 버립니다(헛걸음, 다시 연 목록, `look`).
- 모델은 단계마다 목표 글 한 줄을 붙입니다. 재실행 기록과 멈춤 보고에 쓰입니다.
- 파라미터의 종류도 모델이 적습니다: `text`(글 하나), `list`(여러 개), `path`(저장 경로).
- 파라미터 이름은 계획의 후보에 있는 이름을 씁니다. 후보에 없던 값(지시에 없던 저장 경로 등)에는 새 이름을 붙일 수 있습니다.
- **예시 값은 모델이 글로 적지 않습니다.** 하니스가 기록에서 꺼냅니다. `act`는 그 동작의 대상 이름이나 입력한 글이고, `select_only`는 모델이 가리킨 항목들의 이름이며, `path`는 기록된 저장 경로입니다.

### 하니스가 하는 일

1. **대상 적기를 채웁니다(4절).** `act`의 대상은 그 동작의 기록에서, `select_only`의 "전체 선택" 요소는 가리킨 관찰에서 꺼냅니다.
2. **확인 조건을 채웁니다.** 그 동작의 기록된 효과에서 가져옵니다. 창이 열렸으면 "창이 열림", 닫혔으면 "그 창이 닫힘", 그 밖에는 기록된 기대(`content_changed`, `value_changed`)와 판정을 씁니다. 판정이 그림 변화뿐이었던 동작은 "대상 둘레의 그림이 바뀜"이 조건입니다.
3. **저절로 닫히는 창을 가려냅니다.** 동작이 연 창이, 그 창 안을 누르거나 그 창을 닫는 동작 없이 사라졌으면 저절로 닫히는 창입니다(조회의 진행 팝업). 이런 단계의 확인 조건은 "창이 열림"이 아닙니다. 조회가 빠르면 재실행이 그 창을 보지 못하기 때문입니다. 대신 "그런 창이 없어질 때까지 기다린 뒤, 내용이 바뀌었는지"로 적습니다(`settle`, 5절).
4. **범위를 잇습니다.** 대상이 팝업 창 안에 있으면, 그 창을 연 단계를 찾아 "N번 단계가 연 창"으로 적습니다. 창 id와 제목으로 적지 않습니다(같은 제목의 목록 창이 여럿입니다).
5. **쓰는 도구와 권한을 적습니다.** 단계는 기록된 도구(`click`, `click_part`, `type`, `press` 등)와 인자(부분, 클릭 종류, 키 조합)를 그대로 씁니다. workflow에는 원래 실행의 권한 단계를 적습니다.

### 형식 검사

하나라도 걸리면 저장하지 않습니다.

- **기록에 다시 대 보기:** 대상 적기를 그 동작 직전의 기록된 관찰에 적용하면 정확히 기록된 요소 하나가 나와야 합니다. 0개나 2개 이상이면 걸립니다(`LOCATOR_NOT_UNIQUE`).
- **번호:** 가리킨 동작과 관찰, 표시 번호가 기록에 있어야 하고, 전달되지 않았거나 거절된 동작을 가리키면 걸립니다.
- **파라미터:** `act`에 파라미터를 붙일 수 있는 것은 이름이 있는 대상을 누른 동작과 글을 넣은 동작뿐입니다. `select_only`가 가리킨 항목들은 "전체 선택" 요소와 같은 팝업 창 안에 있고, 서로 역할이 같고, 이름이 그 창 안에서 하나씩이어야 합니다. `path` 파라미터는 기록된 저장 경로가 있고 그 경로를 넣은 동작에 붙어 있어야 합니다. 어긋나면 걸립니다(`DRAFT_INVALID`).
- **순서:** 단계는 기록의 순서를 따릅니다. `select_only`가 묶는 동작은 같은 목록 창 안의 것이어야 합니다.
- **그림뿐인 대상:** 초안이 캡처의 픽셀을 누른 동작을 가리키면 걸립니다(`PICTURE_TARGET`).

### 조작하지 않은 값

계획의 파라미터 후보 가운데 어느 단계에도 쓰이지 않은 것이 있을 수 있습니다. 예: 지시에 "기간은 전일"이 있었지만 화면이 이미 전일이라 건드리지 않았습니다. 이런 값은 파라미터로 받지 않고 workflow의 `fixed`에 이름과 지시의 표현을 적습니다. 재실행에 그 이름을 주면 "이 workflow는 그 값을 바꾸지 못합니다"로 거절합니다(`PARAM_UNKNOWN`). 뷰어는 "바꿀 수 없는 값"으로 보여 줍니다.

## 4. 대상 적기

좌표는 저장하지 않습니다.

```yaml
target:
  scope: main             # 또는 {opened_by: 3}: 3번 단계가 연 창
  role: button
  name: 조회(F5)           # 있을 때만
  description: ...        # 있을 때만
  near: {name: Shop, relation: same_row, nth: 3}   # 위의 것만으로 하나가 안 될 때
```

- **읽는 트리:** 만들기의 검사와 재실행은 같은 읽기를 씁니다. 모델 실행이 읽던 그대로, 지금 창의 트리입니다. 가상 MES의 목록과 메뉴 팝업은 창 목록에도 나오지만, 본 창의 트리 안에 `window` 요소로 들어 있고 그 안에 항목들이 있습니다(실행 기록 `20261114-230056`의 관찰). 모델이 누른 것도 이 트리의 요소입니다.
- **범위(`scope`):** `main`은 관찰한 창 바로 아래, 곧 어떤 팝업 창 요소에도 들지 않은 요소들입니다. `{opened_by: N}`은 N번 단계의 실행으로 트리에 새로 생긴 창 요소의 안쪽입니다. 하니스는 그 단계의 앞뒤 관찰을 비교해 새로 생긴 창 요소를 찾습니다. 새 창 요소가 하나가 아니면 그 단계는 범위를 열지 못한 것입니다. 같은 글자가 본 창과 목록에 함께 있어도(필터 이름 "기간"과 목록의 "기간") 범위가 달라 섞이지 않습니다.
- **따로 읽는 창:** 팝업이 본 창의 트리에 들지 않고 따로 관찰되는 앱에서는, 기록의 관찰이 그 창을 읽은 것이므로 범위는 "N번 단계가 연, 따로 읽는 창"이 됩니다. 규칙은 같습니다: 기록이 읽은 트리와 재실행이 읽는 트리가 같아야 합니다. 표준 저장 대화상자가 어느 쪽인지는 실제 창 확인에서 봅니다.
- **역할과 이름:** 그 범위 안에서 역할, 이름, 설명이 같은 요소가 하나면 이것만 적습니다.
- **기준 글자와 순서(`near`):** 이름이 없거나 같은 요소가 여럿이면 가까운 글자를 기준으로 적습니다. 기준은 그 범위에서 이름이 하나뿐인 요소여야 합니다. `same_row`는 세로로 겹치는 줄, `same_column`은 가로로 겹치는 열이고, `nth`는 그 줄이나 열에서 기준 다음에 오는 같은 역할 요소의 순서입니다. 줄에서 먼저 찾고, 없으면 열에서 찾습니다. 정확한 규칙은 구현자가 정하되, 3절의 "기록에 다시 대 보기"를 통과해야 합니다.
- **바뀌는 글은 기준으로 쓰지 않습니다.** 대상에 가장 가까운 글자가 라벨이 아니라 칸의 값일 수 있습니다(줄이 라벨, 값, 이름 없는 버튼일 때). 값을 기준으로 삼으면 다음 실행에서 값이 달라 대상을 못 찾습니다. 그래서 같은 화면의 다른 관찰 가운데 하나라도 빠져 있는 이름(실행 중에 생기거나 사라진 글)과 파라미터의 예시 값은 기준에서 뺍니다. "같은 화면"은 같은 창을 읽었고 그 범위의 이름이 절반 이상 그대로인 관찰입니다. 실행 내내 바뀌지 않은 값(건드리지 않은 칸의 기본값, 날짜)은 여전히 기준이 될 수 있습니다.
- **앱이 준 고유 id는 쓰지 않습니다.** 앱을 다시 켜면 바뀌는 id가 있고(창 핸들에서 온 숫자), 기록만으로는 고정된 id인지 알 수 없습니다.
- **파라미터인 이름:** `name: $period`처럼 적습니다. 재실행 때 그 값과 이름이 같은 요소를 찾습니다.
- **요소의 부분:** `click_part`의 부분(가운데, 왼쪽, 오른쪽, 위, 아래)은 기록된 대로 씁니다.
- **그림뿐인 대상은 적지 않습니다.** 캡처에서 고른 픽셀을 누른 동작에는 요소가 없습니다. 하니스가 요소로 치는 것은 ref가 있거나 이름, 설명, 값이 있는 노드뿐이라(`agent/observe.py`), 이름 없는 그림 영역은 기록에 남지 않고 기준으로 삼을 것도 없습니다. 첫 버전은 이런 동작을 옮기지 않습니다(`PICTURE_TARGET`).

재실행 때의 찾기:

- 지금 창의 트리를 읽어 범위를 정하고 대상 적기를 적용합니다.
- 0개면 단계 제한 시간(기본 15초) 동안 다시 읽습니다. 끝까지 없으면 멈춥니다(`TARGET_NOT_FOUND`).
- 2개 이상이면 바로 멈춥니다(`TARGET_AMBIGUOUS`).
- 화면 밖이면 멈춥니다(`TARGET_OFFSCREEN`).
- ref가 있는 요소는 기록된 ref 도구로, 없는 요소는 위치의 부분을 실제 클릭으로 누릅니다. 지금 모델 실행과 같은 길입니다.

## 5. 재실행

### 입구

```powershell
python run.py --workflow w-20261119-001 --param shop=WA0,WA1 --param period=전주 --param save_path=C:\out\a.xlsx
python run.py --workflows                      # 이 시스템의 workflow 목록
python run.py --make-workflow latest           # 지난 실행에서 다시 만들기(모델 호출)
```

- `list` 파라미터는 쉼표로 나눕니다.
- 주지 않은 파라미터는 예시 값을 씁니다. `path`만 다릅니다: 주지 않으면 예시 경로의 폴더에 실행 ID를 붙인 새 이름을 씁니다.
- 시작 전에 걸러 냅니다: 모르는 이름(`PARAM_UNKNOWN`), 빈 `list`(`PARAM_INVALID`), 이미 있는 저장 경로(`FILE_EXISTS`), workflow의 시스템과 다른 시스템(`SYSTEM_MISMATCH`).
- 실행 파일은 지금 순서로 고릅니다(`--exe` > `--system` > 설정). workflow 파일에는 시스템 이름만 있고 경로는 없습니다.
- 뷰어: 9절.

### 실행기

모델 루프와 따로 둔 작은 실행기입니다(`--baseline`과 같은 자리). 앱 조작과 기록은 지금의 `Toolbox`와 `RunRecorder`를 그대로 씁니다. 실행기는 "요소를 찾고, 동작하고, 확인한다"에만 기대므로, 나중에 브라우저용 조작 계층을 같은 자리에 끼울 수 있습니다.

- **시작:** 준비 신호가 있으면 지금의 준비 기다리기를 합니다. 같은 시스템이 이미 떠 있으면 지금처럼 멈춥니다. 재실행은 항상 최초 화면에서 시작합니다.
- **단계마다:** 대상 찾기 → 동작 → 다시 읽기 → 확인 조건 검사. 동작과 관찰은 지금처럼 기록되어 뷰어 타임라인에 보입니다. 동작의 `intent`에는 단계의 목표 글이 들어갑니다.
- **확인 조건:** 지금의 효과 비교(`agent/effects.py`)와 그림 비교를 씁니다. 한 번 읽고 판정하지 않습니다. 가상 MES는 창 여는 일을 클릭 뒤로 미루므로, 채워질 때까지 단계 제한 시간(기본 15초) 동안 다시 읽습니다. 끝까지 채워지지 않으면 멈춥니다(`EXPECT_UNMET`).
- **저절로 닫히는 창(`settle`):** 이 표시가 있는 단계는 그 동작 전에 없던 창이 떠 있는 동안 계속 기다립니다. 창이 동작 직후가 아니라 조금 뒤에 떠도 같습니다. 동작 뒤 180초가 지나도 떠 있으면 멈춥니다(`WAIT_TIMEOUT`). 그런 창이 없을 때 확인 조건(내용이 바뀜)을 보고, 창이 마지막으로 사라진 뒤 15초 안에 채워지지 않으면 멈춥니다(`EXPECT_UNMET`). 창이 한 번도 보이지 않았어도(빠른 조회) 내용이 바뀌었으면 통과입니다. 이 단계에서 뜬 창은 모르는 창으로 세지 않으므로, 닫히지 않는 알림 창이 뜨면 180초 뒤 `WAIT_TIMEOUT`이 됩니다.
- **모르는 창:** 확인 조건이나 `settle`이 말하지 않은 창이 새로 뜨면 멈춥니다(`UNEXPECTED_WINDOW`). 덮어쓰기 확인, 오류 알림 같은 창입니다.
- **묻지 않습니다.** 질문 정책, 승인, 지식, 단계 호출 한도는 재실행에 적용하지 않습니다. 사람이 재실행을 시작한 것이 곧 승인입니다.
- **반복 동작 가드도 쓰지 않습니다.** 모델 실행에서는 같은 동작이 한 실행에서 3번을 넘으면 멈춥니다. 재실행은 목록마다 같은 이름의 요소("전체 선택", 닫기)를 누르므로 목록이 넷이면 이 가드에 걸립니다. 재실행은 정해진 단계를 한 번 도는 것이라 되풀이를 막을 까닭이 없습니다.
- **멈춤 신호:** 뷰어의 "실행 멈춤"은 단계 사이에서 듣습니다. 대상 앱은 닫지 않습니다.
- **권한:** workflow에 적힌 권한 단계로 돕니다.

### `select_only`: 이것만 선택

대상은 "N번 단계가 연 목록 창"이라는 범위와 파라미터 값들입니다.

1. 값마다 그 범위에서 이름이 같고 역할이 기록된 항목과 같은 요소를 찾습니다. 하나씩 있어야 합니다. 없거나 여럿이면 멈춥니다(`PARAM_VALUE_NOT_FOUND`). 아무것도 누르기 전입니다.
2. 항목 줄을 정합니다. 찾은 요소들과 역할이 같고 가로 위치가 같은 열에 있는 요소 전부입니다.
3. 체크 상태가 트리에 보이면(체크박스와 상태), 줄마다 상태를 읽어 다른 것만 `check`나 `uncheck`로 맞춥니다.
4. 보이지 않으면 "전체 선택" 요소를 누른 뒤, 값에 없는 줄을 하나씩 눌러 해제합니다. 처음 상태가 무엇이든 결과가 같습니다. 누를 때마다 그 줄 둘레의 그림이 바뀌었는지 봅니다. 바뀌지 않으면 멈춥니다.
5. 목록을 닫는 동작(예: "Select")은 이 단계에 넣지 않고 다음 `act` 단계로 둡니다.

**한계:** 4의 경우 최종 체크 상태를 글로 다시 읽지 못합니다. "전체 선택이 전부를 체크한다", "줄을 누르면 해제된다"는 원래 실행에서 본 동작에 기대고, 재실행은 그림이 바뀐 것만 확인합니다. 목록이 길어 스크롤해야 하는 경우는 멈춥니다.

### `check_file`

경로에 파일이 있고 이번 실행을 시작한 뒤에 쓰였는지 봅니다(`agent/completion.py`의 파일 확인). 아니면 멈춥니다(`FILE_NOT_SAVED`).

### 결과

- 모든 단계가 통과하면 `verified`로 끝나고 종료 코드는 0입니다. `started_by`가 `workflow`라서 모델 실행과 구분됩니다.
- 멈추면 `stopped`이고, 몇 번째 단계에서 어떤 코드로 멈췄는지 남깁니다.
- 통과하면 workflow 파일을 고칩니다: 상태를 확인됨으로, 통과 횟수를 하나 올리고, 예시와 다른 값으로 통과한 적이 있는지를 적습니다. 멈추면 실패 횟수만 올립니다. 상태를 내리지 않습니다.

## 6. workflow 파일

`workflows\<시스템>\<ID>.yaml`에 둡니다. 화면의 글이 들어 있으므로 지식 파일처럼 Git에서 제외합니다. 폴더는 설정의 `workflow_dir`이나 `--workflow-dir`로 바꿀 수 있습니다. ID는 `w-YYYYMMDD-NNN`입니다.

```yaml
format: 1
id: w-20261119-001
system: virtualmes
goal: 전공정 생산현황에서 Shop WA0, WA1을 고르고 조회해 엑셀로 저장
source: {run_id: 20261119-101500, date: '2026-11-19'}
status: unverified            # unverified | verified
passes: 0
failures: 0
verified_with_other_values: false
permission_level: 2
params:
  shop: {kind: list, example: [WA0, WA1]}
  save_path: {kind: path, example: 'C:\out\front.xlsx'}
fixed:
  - {name: period, value: 전일}
steps:
  - n: 1
    goal: 생산운영 메뉴 목록이 열림
    do: act
    tool: click
    target: {scope: main, role: button, name: 생산운영}
    expect: window_opened
  - n: 2
    goal: 전공정 생산현황 화면이 열림
    do: act
    tool: click
    target: {scope: {opened_by: 1}, role: button, name: 전공정 생산현황}
    expect: window_closed
    closes: 1
  - n: 3
    goal: Shop 셋째 칸의 목록이 열림
    do: act
    tool: click
    target: {scope: main, role: button, near: {name: Shop, relation: same_row, nth: 3}}
    expect: window_opened
  - n: 4
    goal: Shop이 고른 값만 선택됨
    do: select_only
    scope: {opened_by: 3}
    all: {role: statictext, name: All}
    item_role: statictext
    items: $shop
  - n: 5
    goal: 목록이 닫히고 선택이 적용됨
    do: act
    tool: click_part
    args: {part: center, action: click}
    target: {scope: {opened_by: 3}, role: statictext, name: Select}
    expect: window_closed
    closes: 3
  - n: 6
    goal: 조회가 끝나 표가 채워짐
    do: act
    tool: click
    target: {scope: main, role: button, name: 조회(F5)}
    settle: true
    expect: content_changed
  # 이어서: 엑셀 아이콘, 저장, 경로 입력(type, text: $save_path), 확인 키
  - n: 11
    goal: 파일이 저장됨
    do: check_file
    path: $save_path
```

읽을 때 형식을 다시 검사합니다. 모르는 키, 좌표처럼 보이는 값, 선언되지 않은 `$이름`이 있으면 실행하지 않습니다(`WORKFLOW_INVALID`).

| 때 | 코드 |
| --- | --- |
| 만들기 | `RUN_NOT_FOUND`, `RUN_NOT_SUCCESSFUL`, `NO_PLAN`, `RECORD_TOO_OLD`, `MODEL_NO_DRAFT`, `DRAFT_INVALID`, `LOCATOR_NOT_UNIQUE`, `PICTURE_TARGET` |
| 재실행 시작 전 | `WORKFLOW_NOT_FOUND`, `WORKFLOW_INVALID`, `SYSTEM_MISMATCH`, `PARAM_UNKNOWN`, `PARAM_INVALID`, `FILE_EXISTS`, 준비 기다리기의 `READY_*` |
| 재실행 중 | `APP_GONE`, `TARGET_NOT_FOUND`, `TARGET_AMBIGUOUS`, `TARGET_OFFSCREEN`, `ACTION_FAILED`, `EXPECT_UNMET`, `UNEXPECTED_WINDOW`, `PARAM_VALUE_NOT_FOUND`, `WAIT_TIMEOUT`, `FILE_NOT_SAVED`, `STOPPED_BY_USER` |

## 8. 기록과 요약

- **`events.jsonl`:** 모델 실행에는 만들기 결과를 `workflow` 이벤트로 남깁니다(만들었는지, ID, 단계 수, 파라미터 수, 못 만들었으면 코드). 재실행에는 단계마다 `workflow_step` 이벤트를 남깁니다(단계 번호, 종류, 통과했는지, 코드, 걸린 시간). 단계의 목표 글은 이 파일에만 있습니다.
- **`run.json`:** 모델 실행에는 `workflow: {created, id, code}`를, 재실행에는 `workflow_run: {id, steps, steps_done, code}`를 넣습니다. ID는 화면의 글이 아니므로 넣습니다. 파라미터의 이름과 값은 넣지 않습니다.
- **요약(`agent/summary.py`):** 위의 수와 코드, ID만 더합니다. 회사에서 "몇 번째 단계에서 어떤 코드로 멈췄다"를 말로 전할 수 있습니다.
- **실행 끝의 출력:** 모델 실행은 `workflow: w-20261119-001 (미확인, 단계 12, 파라미터 2)`나 `workflow를 만들지 못했습니다: LOCATOR_NOT_UNIQUE` 한 줄을 더합니다.

## 9. 뷰어

새 실행 화면 옆에 workflow 목록을 둡니다.

```
workflow (virtualmes)
┌──────────────────────────────────────────────────────────────┐
│ w-20261119-001  미확인   통과 0 / 실패 0                        │
│ 전공정 생산현황에서 Shop WA0, WA1을 고르고 조회해 엑셀로 저장        │
│   shop       [ WA0, WA1            ]  여러 개, 쉼표로 나눔       │
│   save_path  [                     ]  비우면 새 이름으로 저장    │
│   바꿀 수 없는 값: period = 전일                                 │
│                                              [ 재실행 ]        │
└──────────────────────────────────────────────────────────────┘
```

- 목록은 고른 시스템의 것만 보여 줍니다. 서버는 workflow 폴더를 읽어 ID, 지시, 상태, 횟수, 파라미터(이름, 종류, 예시 값), 바꿀 수 없는 값을 보냅니다.
- "재실행"은 `RunManager`로 재실행을 시작하고 그 실행의 타임라인으로 넘어갑니다. 한 번에 실행 하나라는 지금 규칙을 따릅니다.
- 재실행의 타임라인은 지금과 같고, 스텝마다 workflow 단계 번호와 목표를 보여 줍니다. 멈춘 실행은 멈춘 단계와 코드를 보여 줍니다.
- 모델 실행이 끝나면 만들어진 workflow의 ID와 상태, 또는 만들지 못한 코드를 보여 줍니다.
- 상태 표시는 "미확인", "확인됨(같은 값)", "확인됨(다른 값)" 셋입니다.

## 10. 시험과 확인

- 지금 관례대로 테스트를 먼저 쓰고, 테스트마다 구현을 되돌려 실패하는지 확인합니다.
- 만들기는 저장해 둔 기록 폴더와 가짜 모델로 시험합니다. 재실행기는 캡처한 CLI 응답을 재생하는 가짜 데스크톱으로 시험합니다. 앱을 띄우지 않습니다.
- 목표와 "실패로 보는 것"의 항목마다, 어겼을 때 실패하는 테스트가 적어도 하나 있어야 합니다.
- 새 모듈도 `tests\test_application_agnostic.py`의 검사를 받습니다.
- **실제 창 확인(사용자에게 확인받은 뒤):** 가상 MES 기본 프로파일(`mes-like`)에 `--expose icon=ref`를 더한 설정에서 합니다.
  1. 모델 실행으로 아이콘 엑셀 저장까지 성공시켜 workflow가 만들어지는지.
  2. 같은 값으로 재실행해 확인됨이 되는지.
  3. 다른 Shop 조합과 다른 저장 경로로 재실행해 통과하는지. 결과는 재실행의 판정이 아니라 가상 MES의 이벤트 기록(적용된 필터, 저장)과 저장된 파일로 확인합니다.
  4. 깨뜨려 보기: 목록에 없는 Shop 값과 다른 노출 방식(`--expose`)에서 틀린 동작 없이 코드와 함께 멈추는지. 조회 대기를 아주 짧게, 그리고 길게(`--delay-ms`) 바꿔도 통과하는지.
  5. 아이콘이 그림뿐인 설정(`--expose icon=pixel`)의 모델 실행에서 workflow가 만들어지지 않고 `PICTURE_TARGET`이 남는지.
- 창 크기나 배율을 바꾼 재실행도 3에서 한 번 확인합니다.

## 설계자가 정한 것 (사용자가 말한 것이 아님)

1. 파라미터 후보를 `plan`에 적게 합니다(사용자에게 제안했고 반대가 없었습니다).
2. 대상은 창, 역할, 이름, 기준 글자와 순서로 적고, 후보가 0개나 여럿이면 멈춥니다(같음).
3. 재실행기는 모델 루프와 따로 두고, 입구는 `run.py`와 뷰어, 저장은 `workflows\<시스템>\`입니다(같음).
4. 만들기는 기록 폴더만 읽고, `--make-workflow`로 지난 실행에서 다시 만들 수 있습니다.
5. 기록에 표시 번호, 속한 창, 저장한 경로를 더합니다. 옛 기록에서는 만들지 않습니다.
6. 앱이 준 고유 id는 대상 적기에 쓰지 않습니다.
7. 캡처의 픽셀을 누른 동작이 남은 실행에서는 일부만 옮기지 않고 workflow 전체를 만들지 않습니다(그림뿐인 대상을 첫 버전에서 빼는 것 자체는 사용자 결정).
8. 조작하지 않은 지시 값은 파라미터로 받지 않고 "바꿀 수 없는 값"으로 보여 줍니다.
15. 대상을 찾는 범위는 창 목록의 창이 아니라, 모델 실행이 읽던 트리 안의 창 요소입니다.
16. 파라미터의 예시 값은 계획의 글이 아니라 기록에서 꺼냅니다. `select_only`의 예시는 모델이 가리킨 항목들의 이름입니다.
17. 기다리기는 모델이 적지 않습니다. 저절로 닫히는 창을 하니스가 기록에서 가려내고, 확인 조건은 제한 시간까지 다시 읽습니다.
9. 주지 않은 파라미터는 예시 값을 쓰고, 저장 경로만 새 이름을 만듭니다. 이미 있는 경로는 시작 전에 거절합니다.
10. 모르는 창이 뜨면 멈춥니다.
11. 재실행의 성공 상태는 `verified`를 쓰고 `started_by`로 구분합니다.
12. 제한 시간 기본값: 단계 15초, 저절로 닫히는 창 기다리기 180초.
13. 체크 상태가 트리에 보이면 그것을 읽어 맞추고, 보이지 않을 때만 "전체 선택 뒤 해제"를 씁니다.
14. 멈춘 재실행은 workflow의 상태를 내리지 않고 실패 횟수만 올립니다.

## 확인이 필요한 것

1. **가상 MES에서 아이콘 저장까지 가는 모델 실행이 아직 없습니다.** 실제 창 확인 1에서 처음 봅니다.
2. **회사 MES의 엑셀 아이콘이 트리에 어떻게 보이는지 모릅니다.** 이름이나 ref가 있는 요소면 첫 버전으로 됩니다. 그림뿐이면 모델 실행은 캡처의 픽셀을 누르게 되고, workflow는 `PICTURE_TARGET`으로 만들어지지 않습니다. 회사에서 첫 실행의 요약에 이 코드가 나오는지로 알 수 있습니다.
6. **`select_only`의 예시 값은 모델의 판단입니다.** "실행이 끝났을 때 선택되어 있던 항목"을 모델이 틀리게 가리키면, 값을 주지 않은 재실행이 다른 조합을 고릅니다. 체크 상태가 그림뿐이면 하니스가 검증하지 못합니다. 만들어진 직후 출력과 뷰어가 예시 값을 보여 주므로 사람이 봅니다.
3. **회사 MES의 화살표 버튼이 이름 없는 버튼으로 보이는지는 가정입니다**(가상 MES README). 아예 보이지 않으면 칸의 오른쪽 끝을 누른 기록이 되고, 대상 적기는 그 칸과 부분으로 적힙니다.
4. **"전체 선택"이 켜고 끄는 방식이 아니라 항상 전부를 고르는지.** 사용자 설명과 가상 MES는 그렇습니다. 켜고 끄는 방식인 목록에서는 `select_only`가 틀린 상태를 만들 수 있고, 그림 변화만으로는 알아채지 못합니다.
5. **표준 저장 대화상자가 재실행에서도 같은 순서로 동작하는지.** 경로는 실제 키 입력으로 넣어야 한다는 것만 확인되어 있습니다.

## 방법 비교 (사용자가 고름)

1. **모델은 묶고 이름 붙이고, 하니스가 대상을 채움 (고름).** 모델은 기록의 번호로만 가리키므로 없는 대상을 지어낼 수 없고, 검사를 저장 전에 할 수 있습니다. 단계 종류와 가리키는 법을 미리 정해야 합니다.
2. **모델이 YAML 전체를 씀.** 구현이 가장 적지만, 이름을 조금만 틀려도 재실행에서야 드러납니다. 미확인으로 바로 등록하기로 했으므로 틀린 workflow가 그대로 등록됩니다.
3. **하니스가 기록을 그대로 옮김(모델 없음).** 결과가 항상 같지만 "두 항목을 해제했다"가 "나머지 두 항목만 선택한다"는 뜻임을 알 수 없어, 정한 파라미터 수준을 채우지 못합니다.
