# 화면 구조를 LLM이 스스로 파악하기 설계

- 날짜: 2026-11-27
- 상태: 1·2단계 구현됨(2026-11-27, 계획 `docs/plans/2026-11-27-screen-structure.md`). 구현에서 더한 것: 표 역할 안의 잎 `row` 요소도 칸(GridItem 패턴 없는 DataItem), `find_rows`의 `where`는 `[{column, value}]` 배열, 같은 열 이름에 ` (2)`. 3단계는 회사 확인 뒤 따로 계획

## 왜

회사 MES 첫 캡처 세션과 그 뒤의 확인에서 다음을 알게 되었다.

- **표의 칸이 관찰에 들어오지 않는다.** H14 `TABLE_ONLY`. Inspect로 본 표의 경로는 `창 > XtraLayoutControl > sc_Count > pn_Content > usSplitContainerControl1 > "" > "" > pn_Main > 표 > Data Panel > Row 1 > "양품수 row0"`이다. 칸은 창부터 12번째 단계다. CLI `snapshot`은 기본 `--max-depth 10`(창 아래 10단계, 창까지 세면 11번째)까지만 읽는다. 잘린 자리의 노드는 `children_count`만 남기고 스냅샷은 `complete: true`다. 가상 MES에서 깊이를 줄여 같은 모습(표 박스만 남고 `children_count: 200`)을 재현했다. 하니스(`agent/tools.py` `_snapshot`)도 캡처 세션(`agent/survey_capture.py`)도 `--max-depth`를 주지 않는다.
- **칸에는 구조와 값이 있다.** 칸 이름은 `<열 이름> row<번호>` 꼴이다. 칸의 `Value.Value`와 `LegacyIAccessible.Value`에 화면의 값이 나온다(사용자 확인). 그러므로 깊이만 풀리면 "공정이 극판이고 구분이 소계인 행의 양품수"를 그림 없이 트리로 찾을 수 있다.
- **모델은 구조를 보지 못한다.** 관찰 글(`agent/observe.py`)은 요소마다 번호를 붙인 줄을 트리 순서로 늘어놓는다. id만 있는 영역(패널)은 줄이 없어 모델은 소속을 모른다. 박스 좌표는 기본으로 보이지 않아 "Shop 필터의 3번째 칸"은 모델의 짐작이고, 그래서 매번 사람에게 묻는다. 표 칸 찾기(`agent/table.py` `find_cells`)는 화면 글자의 위치를 맞추는 방식이라 표의 구조와 칸 값을 쓰지 않는다.
- **사용자의 방향(2026-11-27):** 칸 위치를 사람이 넣어 주는 대신 LLM이 트리 구조를 보고 어디를 누를지 스스로 판단하게 한다. 사람이 넣는 정보와 LLM이 찾는 정보를 분명히 나눈다. **사람이 넣는 정보는 관리자가 시스템마다 한 번 등록한다.**

## 목표

1. 깊이 때문에 잘린 곳을 하니스가 알아채고 다시 읽는다. 캡처 세션도 잘린 곳을 세어 전달 블록에 남긴다.
2. 모델은 관찰에서 영역, 줄(왼쪽→오른쪽 순서), 표의 요약을 보고, 필요한 곳만 도구로 열어 본다. 표는 열과 행의 값으로 찾는다.
3. 모델이 알아낸 화면 구조를 **화면 지도 초안**으로 내면, 관리자가 등록 화면에서 확인하고 업무 용어의 뜻을 덧붙여 저장한다. 다음 실행은 승인된 지도를 근거로 탐색 없이 찾는다.
4. 정보를 셋으로 나눈다: LLM과 하니스가 찾는 것, 관리자가 등록하는 것, 실행 중 묻는 것.

## 하지 않는 것

- 앱이나 부품(DevExpress 등)에 맞춘 분기. 구조는 역할, 박스, 이름의 모양, 값으로만 판단한다. `tests/test_application_agnostic.py`가 지킨다.
- CLI(Rust) 수정. 깊이는 하니스가 `--max-depth`로 정한다. CLI의 기본값은 그대로 둔다.
- 그림으로 칸 찾기의 새 기능. 칸이 트리에 없는 시스템은 지금의 `look`과 `click_point`로 다룬다. 따로 다룬다.
- 관리자 승인 없이 지도를 쓰는 것. 초안은 실행에 영향을 주지 않는다.

## 실패로 보는 것(안티 목표)

- 같은 조건에 맞는 행이 여럿인데 하나를 골라 누르는 것. 여럿이면 묻거나 멈춘다.
- 관리자가 빈 양식을 처음부터 채워야 하는 등록. 관리자는 LLM이 찾은 것을 확인하고 업무의 뜻만 더한다.
- 표 전체를 매 관찰마다 모델에게 보내는 것(행 40 × 열 12 = 칸 480개).
- 행 번호(`row3`)로 기억하는 것. 조회 조건이 바뀌면 같은 행의 번호가 바뀐다.

## 제약

- 화면의 글, 요소 이름, id, 값은 `events.jsonl`, 프로파일, 지도 초안(모두 Git 제외)에만 둔다. `run.json`, 요약, `check.py` 출력, 전달 블록에는 수와 코드만 넣는다.
- 번호 매기기는 `render_marked`, `visible_elements`, `RunRecorder`가 같은 규칙을 공유한다(어긋나면 workflow 만들기가 조용히 틀린다). 이 설계는 번호를 바꾸지 않고, 표 안의 칸을 관찰 글에서 줄로 늘어놓지 않을 뿐이다. 칸의 번호는 그대로 있다.
- ID 규칙은 `agent/identity.py` 하나를 따른다(역할, id, 담긴 영역을 함께 맞춤).
- 가상 MES는 C# 5(문자열 보간, `nameof`, `?.` 금지).
- **진행 중인 다른 작업:** 다른 세션이 창 올리기(`docs/specs/2026-11-27-window-focus-design.md`)를 `agent/tools.py`, `loop.py`, `tool_schemas.py`에서 구현 중이다. 이 설계의 구현은 그 작업이 커밋된 뒤 시작한다. `mouse_click`을 모델 도구에서 빼는 일(사용자 결정)은 이 설계와 따로, 그 뒤에 먼저 한다.

## 접근 방법

- **A. 관찰 글 자체를 구조화.** 영역, 줄, 표 전체를 관찰마다 보여 준다. 한 번에 다 보이지만 큰 표에서 글이 너무 길다.
- **B. 요약 + 열어 보는 도구.** 관찰에는 요약만 두고 모델이 `expand`, `read_table`, `find_rows`로 필요한 곳을 본다. 글이 짧고 "어디를 볼지"를 LLM이 정한다. 호출이 몇 번 는다.
- **C. B + 관리자가 승인하는 화면 지도. (사용자 선택)** B로 알아낸 구조를 지도 초안으로 남기고 관리자가 승인한다. "LLM이 스스로 파악"(B)과 "관리자가 한 번 등록"(지도)을 둘 다 만족한다. 단계로 나눠 쌓는다: 1단계 깊이, 2단계 B, 3단계 지도.

## 정보 나눔

| 누가 | 무엇을 | 어디에 |
| --- | --- | --- |

## 설계

### 1단계: 깊이로 잘린 곳 다시 읽기

- **처음부터 깊게 읽는다.** 하니스의 관찰(`tools._snapshot`)은 언제나 `--max-depth 30`(상수 `DEEP_DEPTH`, 설정 `observe_deep_depth`로 바꿈)을 준다. "잘린 곳을 보면 다시 읽기"로 하지 않는 이유: Windows 어댑터는 ref의 신원을 증명하려고 깊이 옵션과 상관없이 창 전체를 50단계까지 훑고 출력만 자른다(`crates/core/src/snapshot/window_capture.rs`의 `WHOLE_WINDOW_DEPTH`). 그래서 다시 읽으면 같은 훑기를 두 번 한다. 깊게 읽을 때 늘어나는 것은 출력과 ref 지도(refmap)의 크기다.
- **크기 한도.** CLI는 refmap이 1MB를 넘으면 스냅샷 전체를 `INTERNAL`로 거절한다(`crates/core/src/refs/mod.rs` `MAX_REFMAP_BYTES`). 표의 칸은 역할이 `cell`이라 모두 ref를 받는다. 깊게 읽기가 이 한도나 시간 초과로 실패하면 기본 깊이로 한 번 다시 읽어 그 트리를 쓰고 이유 코드(`deep_read_too_large`, `deep_read_timeout`)를 남긴다. 관찰은 멈추지 않는다. (회사 표가 행을 모두 트리에 내는지는 아래 "사용자에게 확인할 것" 1.)
- 깊게 읽어도 잘린 곳(`children_count`)이 남으면 관찰 글의 그 줄에 지금처럼 `children=N`이 붙는다. 시스템 안내에 "children=N은 더 읽지 못한 자식이 있다는 뜻"을 한 줄 더한다.
- **다른 트리 읽기.** 등록 화면(`viewer/profile_editor.py`)과 `check.py`의 앱 관찰도 깊게 읽는다(관리자가 깊은 패널 안의 요소와 표를 등록하려면 필요). 준비 확인(`agent/ready.py`)은 0.5초마다 읽으므로 지금 깊이를 유지한다(내 판단).
- **기록:** `events.jsonl`의 관찰 기록에 쓴 깊이, 남은 잘린 곳 수, 크기·시간 때문에 얕게 돌아간 경우의 코드. 요약에는 얕게 돌아간 수와 남은 잘린 곳 수만.
- **캡처 세션:** `survey_capture.py`의 `snapshot`에 `--max-depth 30`을 주고 같은 대체 규칙을 쓴다. 캡처마다 잘린 곳 수와 얕게 돌아갔는지를 `facts.json`에 넣고, 전달 블록의 H11 값에 붙인다(예: `COMPLETE(2.5s/c0)`). 블록 버전을 v3으로 올리고 `--read-block`은 v2와 v3을 모두 읽는다(내 판단: 새 가설 줄을 만들지 않고 읽기 완전성 줄에 붙인다).

### 2단계: 구조 요약과 열어 보는 도구

새 모듈 `agent/structure.py`. 스냅샷 트리와 그 관찰의 번호(`visible_elements`)만 받는 순수 함수다.

**영역.** `identity.as_container`가 영역으로 치는 노드(id나 이름이 있는 노드) 가운데, 요소를 직접 담거나 영역을 둘 이상 담은 것만 이정표로 남긴다. 이름도 id도 없는 감싸개가 여러 겹이어도 이정표 하나로 접힌다. **표 안의 노드(행 `Row 1` 등)는 이름이 있어도 이정표가 되지 않는다.** 관찰마다 `A1`, `A2`… 핸들을 준다(번호 `[n]`과 다른 이름공간, 누르는 대상이 아님).

**줄.** 한 영역 안의 요소를 세로로 겹치는 정도(`agent/locator.py`의 같은 줄 판단과 같은 규칙)로 묶고 왼쪽→오른쪽으로 순서를 매긴다. 표 안의 칸은 줄로 묶지 않는다(표가 따로 다룬다).

**표.** 다음 중 하나면 표다.
- 역할이 `table`이나 `grid`인 노드
- 역할이 `cell`인 요소를 여러 줄에 걸쳐 담은 노드

행은 칸을 담은 자식 노드(예: `Row 1`) 단위로, 그런 노드가 없으면 칸 박스의 세로 위치로 나눈다. 열은 **열마다** 다음 순서로 이름을 정한다(한 표 안에서 열마다 다른 규칙이 쓰일 수 있다).
1. 같은 표의 머리글 요소(역할 `column` 등)가 그 열과 가로로 겹치면 그 이름
2. 없으면 칸 이름에서 행마다 달라지는 숫자 부분을 `#`로 바꾼 모양(예: `양품수 row0`, `양품수 row1` → `양품수 row#`)
3. 둘 다 아니면 `열1`, `열2`

칸의 값은 `value`, 없으면 이름이다. 화면 밖으로 스크롤된 칸(박스 없음, `offscreen`)도 행으로 센다.

하니스는 "행을 가르는 열의 후보"를 요약에 적는다. **숫자만 담긴 열은 후보에서 뺀다**(`agent/table.py`의 `NUMERIC`과 같은 판단). 양품수처럼 값이 매일 바뀌는 열이 우연히 겹치지 않아 열쇠가 되는 것을 막기 위해서다. 글자 열 가운데 값이 겹치지 않는 열, 또는 가장 적은 열의 조합을 적는다. 이것은 모델에게 주는 힌트일 뿐이고, 행을 정하는 것은 모델이 `find_rows`에 넘긴 조건이다. 표마다 `T1`, `T2`… 핸들을 준다.

**표의 신원.** 표에 id가 있고 프로파일의 `stable_ids`가 참이면 역할·id·담긴 영역(`agent/identity.py`)으로, 아니면 **담긴 영역 + 역할 + 열 이름의 집합**으로 알아본다. 지도와 workflow가 같은 규칙을 쓴다(내 판단).

**관찰 글.** 관찰 글 맨 앞에 구조 요약을 둔다. 표 안의 칸은 개별 줄로 늘어놓지 않는다(번호는 그대로 있다).

```
구조
  A1 영역 id="pn_Filter"  줄 1개
    줄1: [20] "Shop" → [21] · [22] · [23]
  A2 영역 id="pn_Main"
    T1 표 [40]  열 12개 · 행 40개 · 값 있음 · 행을 가르는 열: 공정+구분
      열: 공정 | 구분 | 양품수 row# | 불량수 row# | …
```

`wait_for_text`는 관찰 글에서 글자를 찾으므로(`tools.py`), 칸이 줄에서 빠지면 칸 값을 기다릴 수 없게 된다. `wait_for_text`는 관찰 글과 함께 그 관찰의 표 칸 값도 찾는다.

**새 도구(레벨 0, 앱을 바꾸지 않음, `READ_ONLY_TOOLS`).** `expand`는 이미 앱을 바꾸는 ref 동작의 이름이므로 쓰지 않는다.
- `open_area(area)`: 영역 하나 안의 줄과 요소를 번호와 함께 보여 준다.
- `read_table(table, columns, rows)`: 고른 열(없으면 전부), 행 범위(한 번에 최대 30행, 이어 읽기 가능)를 표 모양으로 보여 준다. 칸마다 번호와 값이 있다.
- `find_rows(table, where, columns)`: `where`는 `{열 이름: 값}`. 앞뒤 공백을 뺀 값이 같은 행만 고른다. 맞는 행마다 행 순서, 가르는 열의 값, 요청한 열의 칸 번호를 돌려준다. 0개면 이유 코드(`no_such_column`, `no_match`), 여럿이면 모두 돌려주고 하니스가 그 칸들을 "후보가 여럿"으로 알린다(`agent/asking.py`의 `_note_cells`가 `agent/policy.py`에 사각형을 넘기는 지금 길). 그래서 누르기 전에 묻게 된다. 하나면 묻지 않는다. 후보 가운데 화면 밖이라 박스가 없는 칸이 있으면, 지금의 사각형 판단으로는 막을 수 없으므로 **질문에 답하기 전에는 그 표의 어느 칸도 누를 수 없게** 막는다. 화면 밖 칸을 누르려면 먼저 스크롤해서 보이게 해야 한다(지금의 `scroll`).

`find_cells`는 표 구조가 없는 화면(글자만 그려진 표)을 위해 남긴다. 시스템 안내는 "표가 `T`로 보이면 `find_rows`, 아니면 `find_cells`"로 순서를 준다.

**workflow.** 표 칸을 누른 단계는 행 번호가 아니라 `표의 신원 + 열 이름 + 그 칸을 찾은 find_rows의 조건`으로 적는다(`agent/locator.py`, `agent/workflow_format.py`). 열쇠는 하니스가 계산한 후보가 아니라 모델이 실제로 넘긴 조건이다(내 판단). 재실행은 `find_rows`와 같은 규칙으로 찾고, 0개나 여럿이면 그 단계에서 코드와 함께 멈춘다. 조건의 값은 workflow 파라미터가 될 수 있다(예: 공정 이름). 칸을 `find_rows` 없이 눌렀으면 그 단계는 지금처럼 적는다.

**기록.** workflow 만들기와 지도 초안은 실행이 끝난 뒤 기록에서 일한다. 지금의 기록(`agent/recorder.py`)은 요소를 평평하게만 남겨 표의 신원과 열을 다시 계산할 수 없다. 그래서 관찰 이벤트마다 `structure` 기록(영역과 표의 신원, 열 이름, 행 수, 가르는 열 후보)을, `find_rows`마다 조건·맞은 행·돌려준 칸 번호를 `events.jsonl`에 남긴다. 트리 전체는 남기지 않는다(깊게 읽으면 크다).

### 3단계: 화면 지도

**지도 항목.** 지도는 화면 하나에 대한 항목 묶음이다.

| 항목 | 내용 | 누가 채움 |
| --- | --- | --- |
| `screen` | 이 화면을 알아보는 표시(영역·표의 역할, id, 담긴 영역. `ready` 신호와 같은 모양) | LLM 초안 |
| `table` | 표의 위치(영역·역할·id), 열 이름들, 가르는 열 | LLM 초안(하니스가 값 검사) |
| `line` | 영역과 줄의 칸 순서, 칸마다 뜻 | 칸 순서는 초안, 뜻은 관리자 |
| `term` | 업무 용어 → 표·열·조건, 또는 줄의 몇 번째 칸 | 관리자(초안은 실행의 지시와 누른 칸에서 후보만 제안) |

**초안 만들기.** 성공한 모델 실행의 끝에, workflow 만들기와 같은 자리에서 한 번 부른다. 모델은 실행 기록의 관찰과 도구 결과 번호만 가리키고(`agent/workflow_author.py`와 같은 방식), 하니스가 위치와 열 이름을 적은 뒤 그 관찰에 다시 대 본다. 맞지 않는 항목은 버리고 수를 센다. 초안은 `profiles/<시스템>.draft.yaml`에 쌓인다. 실행은 초안을 읽지 않는다.

**승인.** 뷰어의 등록 화면(`viewer/profile_editor.py`)에 "화면 지도" 부분을 더한다. 관리자는 초안 항목을 확인하고 `term`과 `line`의 뜻을 적어 승인한다. 승인된 항목은 프로파일의 새 최상위 키 `screens`로 옮겨진다(프로파일 `format` 2, 1도 계속 읽음). 등록 화면은 앱을 조작하지 않는다(지금 규칙).

**실행 때 쓰기.** 관찰마다 승인된 `screen` 표시를 트리에 대 보고(`identity.fits`), 맞는 화면의 지도를 관찰 글 구조 요약 아래에 붙인다.

```
등록된 지도: 화면 S1
  "극판 양품수" → T1에서 공정=극판, 구분=소계 행의 양품수 row#
  "Shop 3번째 칸" → A1 줄1의 3번째 = 공정 필터
```

지도를 근거로 누른 클릭은 묻지 않는다(도구 인자 `map_id`). **단, 지금의 `knowledge_id`와 달리 후보가 여럿인 상황은 건너뛰지 않는다.** 지도의 용어가 여러 행에 맞으면(예: 여러 Shop 아래의 극판 소계) 묻는다. 지도의 표나 열이 트리에 없으면 `map_mismatch` 이벤트와 코드가 남고, 모델에게 "지도가 맞지 않음, 탐색하라"가 가고, 요약과 등록 화면에 그 수가 보인다.

### 가상 MES

- 노출 방식 `rows`를 `grid` 영역에 더한다. 회사 표와 같은 모양이다: 표 > `Data Panel` > `Row n` > 이름이 `<열 이름> row<k>`이고 값(Value 패턴)이 화면 글자인 칸. 칸 클릭은 지금의 `cell_clicked` 이벤트를 남긴다.
- 옵션 `--nest <N>`(0~12, 기본 0): 화면 패널을 이름 없는 패널과 id만 있는 패널 N겹으로 감싸 칸이 10단계 밖으로 나가게 한다. 회사의 깊이 잘림을 재현한다.
- 둘 다 기본은 꺼져 있어 지금의 시험은 그대로다.

### 기록과 요약

- `events.jsonl`: `deep_read`, `structure`(영역·표·행 수), `find_rows`(조건과 결과 수), `map_match`, `map_mismatch`, `map_draft`(항목 수, 버린 수).
- 요약과 `run.json`: 다시 읽은 수, 남은 잘린 곳 수, `find_rows` 호출·0개·여럿 수, 지도 맞음·안 맞음 수, 초안 항목 수. 글과 값은 넣지 않는다.

## 검증

- 캡처한 CLI 응답을 재생하는 시험: 관찰이 언제나 `--max-depth 30`을 주는 것, refmap 한도·시간 초과면 기본 깊이로 돌아가 코드를 남기는 것, 등록 화면과 `check.py`도 깊게 읽는 것, 준비 확인은 그대로인 것.
- `wait_for_text`가 줄에 없는 표 칸 값도 찾는 것.
- `structure.py` 단위 시험: 감싸개 접기, 줄의 왼→오 순서, 머리글이 있는 표와 없는 표의 열 이름, 숫자 부분 바꾸기, 가르는 열 계산, 표 안의 칸이 줄에서 빠지는 것, 번호가 바뀌지 않는 것.
- 도구 시험: `find_rows` 0개·1개·여럿, 여럿일 때 정책이 묻게 하는 것, `read_table` 이어 읽기.
- workflow: 칸 단계가 가르는 열의 값으로 적히고 재실행에서 다른 행 번호로도 찾는 것.
- 지도: 초안 만들기, 맞지 않는 항목 버리기, 승인, 실행 때 맞음·안 맞음, 지도를 근거로 한 클릭이 묻지 않는 것.
- 캡처 세션: v3 블록 쓰기와 v2·v3 읽기.
- 가상 MES: 새 옵션 해석 시험(창 없음). 실제 창 시험(`--nest`로 잘림 재현 → 다시 읽기 → `find_rows`로 극판 소계 양품수 → `cell_clicked`의 행이 맞음)은 사용자 확인 뒤.
- 단계마다 회사 확인: 1단계 뒤 캡처 세션 블록의 잘린 곳 수가 0인지, 2단계 뒤 실제 실행에서 `find_rows`로 칸을 찾는지.

## 사용자에게 확인할 것

1. 회사 표가 행을 모두 트리에 내는지, 화면에 보이는 행만 내는지. 한 번에 보통 몇 행인지.
2. 소계 행과 병합된 칸이 트리에서 어떻게 보이는지(소계 행도 `Row n`인지, 병합된 공정 칸이 행마다 값을 갖는지).

## 구현자에게 맡기는 것

- `DEEP_DEPTH`의 값(30은 내 판단. 회사 경로가 12단계이고 raw view의 중간 노드를 감안함). 깊게 읽기에 걸린 시간을 재서 조정해도 된다.
- 감싸개를 이정표로 남길지 접을지의 세부 기준, 핸들 이름(`A`, `T`, `S`)의 모양.
- `read_table`의 한 번 행 수(30은 내 판단).
- 가르는 열이 하나도 없는 표(모든 열 조합이 겹침)의 표시 방법. 단, 그런 표에서 `find_rows`가 여럿을 찾으면 반드시 묻는다.
- 등록 화면의 화면 지도 부분의 배치.
