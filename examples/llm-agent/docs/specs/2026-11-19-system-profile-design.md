# 시스템 프로파일: 준비 신호와 요소 ID를 등록하고, 준비 확인을 재서 빠르게 하기

- 날짜: 2026-11-19
- 상태: 사용자 승인(2026-11-19), 구현 끝. 가상 MES의 실제 창과 실제 모델로 8절의 다섯 가지를 확인함(2026-11-19). 회사 시스템에서는 아직 돌리지 않음. 구현 계획: [시스템 프로파일 구현 계획](../plans/2026-11-19-system-profile.md)
- 대상: `examples/llm-agent`의 준비 기다리기(`agent/ready.py`), 관찰 글과 요소(`agent/observe.py`), 대상 적기(`agent/locator.py`, `agent/workflow_format.py`, `agent/workflow_author.py`, `agent/workflow_run.py`), 설정(`agent/settings.py`, `agent/systems.py`, `agent/task.py`), 점검(`check.py`, `agent/checks.py`), 기록과 요약(`agent/recorder.py`, `agent/summary.py`), 뷰어(`viewer/`), 가상 MES(`virtual-mes/`), 그리고 새로 만드는 프로파일 모듈. `agent-desktop` CLI는 고치지 않습니다.
- 앞선 설계: [시스템 골라 띄우고 준비될 때까지 기다리기](2026-11-18-system-launch-ready-design.md), [workflow 만들기와 파라미터 재실행](2026-11-19-workflow-design.md). 배경은 [CUA 배경과 설계 기준](../cua-background.md)의 "공통부와 시스템 프로파일을 나눕니다"입니다.

## 왜 하는가

개발하는 쪽은 회사의 시스템 화면을 볼 수 없습니다. 시스템마다 다른 것은 회사에서 관리자가 직접 알려 줘야 하는데, 지금은 그 길이 설정 파일을 손으로 고치는 것뿐입니다. 사용자가 회사에서 겪은 문제는 둘입니다.

1. **MES의 준비 기다리기가 느립니다.** 메인 화면이 눈에 다 보인 뒤에도 한참 있다가 실행이 시작됩니다. 준비 신호는 글자 하나뿐이고 모든 시스템이 같이 씁니다. 메인 화면의 고정 글자 여러 개로 판정하고 싶고, 그 글자를 쉽게 등록하고 싶습니다.
2. **GSCM은 메뉴의 글자가 그림입니다.** 이름이 없어 하니스도 모델도 무슨 메뉴인지 모릅니다. 다만 메뉴 항목마다 AutomationId가 있고(예: "Shipment Plan"은 `56`, "Execution Plan"은 `60`), 이 값은 바뀌지 않습니다. 사용자는 Inspect로 이것을 확인했습니다. Inspect는 가리켜 보여 주기만 하고 저장하지 못합니다.

지금 코드는 이렇습니다.

- 준비 확인 한 번은 후보 창마다 트리 전체를 위치까지 통째로 읽습니다(`snapshot --compact --include-bounds`, 창마다 최대 8초). 그 뒤에 1초를 쉽니다. 읽기가 실패해도 조용히 다음으로 넘어가고, 몇 번 읽었고 얼마나 걸렸는지는 요약에 남지 않습니다.
- 하니스는 스냅샷의 `native_id`(Windows의 AutomationId)를 읽지만 반복 동작 가드와 요소 수 세기에만 씁니다. 모델에게 가는 관찰 글에는 넣지 않습니다.
- 하니스가 요소로 치는 것은 ref가 있거나 이름, 설명, 값이 있는 노드뿐입니다(`agent/observe.py`). ID만 있고 이름도 ref도 없는 노드는 표시 번호도 박스도 없습니다.
- workflow의 대상 적기는 ID를 쓰지 않습니다. 어제 설계에서 "앱을 다시 켜면 바뀌는 ID가 있다"는 이유로 뺐습니다.

## 용어

- **시스템 프로파일:** 시스템 하나에 대해 관리자가 등록한 것을 담은 파일입니다. 준비 신호와 요소 이름이 들어 있습니다.
- **준비 신호:** 메인 화면이 다 떴다고 볼 수 있는 요소 하나입니다. 이름으로 적거나 ID로 적습니다. 시스템마다 여러 개를 둘 수 있습니다.
- **등록 이름:** 화면에 글자가 그림으로만 그려져 이름이 없는 요소에, 관리자가 ID를 열쇠로 붙인 이름입니다.
- **등록 화면:** 뷰어에서 대상 앱의 지금 화면을 읽어, 박스와 표로 준비 신호와 등록 이름을 고르는 화면입니다.
- **읽는 방식:** 준비 확인이 화면을 읽는 두 가지 방법입니다. `snapshot`은 트리를 통째로 읽고, `find`는 "이 이름(또는 이 ID)의 요소가 있는가"만 CLI에 묻습니다.

## 목표와 하지 않는 것

목표:

1. 준비 확인이 얼마나 걸리는지 수로 볼 수 있습니다. 회사에서 말로 전할 수 있는 형태입니다.
2. 준비 확인의 쉬는 시간이 짧고, 시스템마다 재 본 수로 더 빠른 읽는 방식을 고를 수 있습니다.
3. 시스템마다 준비 신호를 여러 개 둘 수 있고, 이름으로도 ID로도 적을 수 있습니다.
4. 모델이 읽는 관찰 글에 요소의 ID와 등록 이름이 보입니다. 그림뿐인 메뉴가 모델에게 이름 있는 요소처럼 보입니다.
5. ID만 있는 요소도 하니스가 요소로 쳐서, 번호가 붙고 누를 수 있습니다.
6. 관리자가 뷰어의 등록 화면에서 화면을 읽고, 박스를 눌러 준비 신호를 고르고, 표에서 ID에 이름을 한꺼번에 붙입니다. 파일을 손으로 고치지 않아도 됩니다.
7. ID가 바뀌지 않는다고 표시한 시스템에서는 workflow의 대상 적기가 ID를 씁니다.
8. 집에서 가상 MES로 이 흐름을 재현하고 시험할 수 있습니다.

하지 않는 것:

- **실제 앱 위에 정보를 띄워 가리켜 고르는 도구.** 사용자가 고르지 않았습니다. 가리켜 보는 일은 Inspect가 합니다.
- **등록 이름을 자동으로 채우기**(그림을 모델이나 OCR로 읽어 제안). 필요해지면 나중에 더합니다.
- **등록 화면에서 앱을 조작하기.** 등록 화면은 읽기만 합니다. 메뉴를 여는 일은 관리자가 직접 합니다.
- **준비 판정의 다른 방식**(화면이 멈추면 준비, 그림으로 판정).
- **프로파일에 메뉴 구조, 용어집, 로그인 같은 다른 시스템 고유 값을 넣기.** 파일의 자리는 만들지만 이번에는 준비 신호와 요소 이름만 넣습니다.
- **프로파일을 여러 PC가 나눠 쓰기.** 파일을 복사하면 됩니다.

실패로 보는 것(동작해도 실패):

- 프로파일의 글(준비 신호, 등록 이름)이나 ID가 `run.json`, 요약, `check.py` 출력에 나오는 것.
- 한 창에서 여럿이 같이 쓰는 ID를 등록해, 다른 요소가 그 이름으로 보이는 것.
- `agent/`나 `viewer/` 코드에 앱 이름이나 화면의 글이 들어가는 것(`tests\test_application_agnostic.py`).
- 프로파일이 없는 시스템의 동작이 지금과 달라지는 것(아래 2절과 3절에서 밝힌 것은 예외).

## 사용자가 정한 것

| 결정 | 고른 것 | 고르지 않은 것 |
| --- | --- | --- |
| 등록 도구 | 뷰어의 한 화면: 캡처한 화면의 박스(B)와 한꺼번에 등록하는 표(C) | 실제 앱 위에서 가리켜 고르기(A) |
| 모델과 ID | 모델이 ID도 읽으며 동작한다 | ID를 하니스만 쓰기 |
| ID의 안정성 | 이 시스템들의 AutomationId는 있으면 바뀌지 않는다(사용자가 확인) | — |
| ID의 쓰임 | ID는 **추가 정보**다. ID 하나만으로 요소를 판정하지 않는다. 다른 화면의 다른 요소가 같은 ID를 쓰는지 모르기 때문이다 | ID만으로 요소를 알아보기 |
| 준비 판정 | 메인 화면의 고정 글자 여러 개 | 글자 하나 |

사용자가 알려 준 사실: GSCM은 설치형 앱이다. GSCM의 메뉴 항목은 Inspect에서 `ControlType`은 있고 `IsInvokePatternAvailable`은 `false`다.

### ID를 추가 정보로 쓴다는 것

이 설계의 모든 곳에서 ID는 홀로 열쇠가 되지 않습니다. 항상 다른 것과 **함께** 맞아야 합니다.

- **역할:** ID는 늘 역할과 짝으로 봅니다(`(role, id)`).
- **담긴 영역(`in`):** 그 요소의 조상 가운데 가장 가까운, ID나 이름이 있는 요소입니다(역할과 그 ID나 이름). 메뉴 항목이라면 그것들을 담은 메뉴 줄입니다. 등록 화면이 등록할 때 자동으로 함께 적습니다. 다른 화면의 다른 영역에 같은 ID가 있어도 담긴 영역이 다르면 같은 요소로 보지 않습니다.
- **이름과 설명:** 요소에 이름이나 설명이 있으면 ID는 그것을 대신하지 않고 더해집니다. 둘 다 맞아야 합니다.
- **하나뿐일 것:** 위가 모두 맞는 요소가 그 범위에서 하나여야 합니다. 둘 이상이면 어느 것도 그 요소로 보지 않습니다.
- **모델에게는 참고로:** 관찰 글의 `id`와 `alias`는 모델이 화면을 읽는 데 더해지는 정보입니다. 화면에서 본 것과 `alias`가 어긋나 보이면 `alias`를 믿지 말고 확인하거나 물으라고 지시문에 적습니다.

## 1. 시스템 프로파일 파일

`profiles\<시스템>.yaml`에 둡니다. 화면의 글이 들어 있으므로 Git에서 제외합니다. 폴더는 `--profile-dir` > 설정의 `profile_dir` > 환경변수 `AGENT_PROFILE_DIR` > 기본 폴더 순서로 정합니다. 시스템 이름의 규칙은 지식 폴더와 같습니다.

`--profile`과 `AGENT_PROFILE`은 이미 `.env.<이름>`을 고르는 데 쓰고 있어 이름이 겹칩니다. 그래서 이 파일을 가리키는 인자와 설정 키는 모두 "시스템 프로파일"이라는 뜻으로 `profile_dir`만 쓰고, 파일을 고르는 열쇠는 지금의 시스템 이름입니다.

```yaml
format: 1
system: GSCM
stable_ids: true
ready_read: snapshot
ready:
  - {name: Order Management}
  - {id: '56', role: image, in: {role: toolbar, id: '12'}}
elements:
  - {id: '56', role: image, in: {role: toolbar, id: '12'}, name: Shipment Plan}
  - {id: '60', role: image, in: {role: toolbar, id: '12'}, name: Execution Plan}
```

| 키 | 값 | 뜻 |
| --- | --- | --- |
| `ready` | 준비 신호의 목록(없으면 빈 목록) | **모두** 보여야 준비입니다. 항목은 이름 신호(`name`, 더 좁힐 때 `role`)이거나 ID 신호(`id`와 `role`, 있으면 `in`)입니다 |
| `elements` | 등록 이름의 목록(없으면 빈 목록) | `id`, `role`, `name`은 꼭 있고 `in`은 등록할 때 담긴 영역이 있었으면 적습니다. 같은 `(role, id, in)`은 한 번만 |
| `in` | `{role, id}` 또는 `{role, name}` | 담긴 영역: 조상 가운데 가장 가까운, ID나 이름이 있는 요소. 뿌리 창은 치지 않습니다. 그런 조상이 없으면 적지 않습니다 |
| `stable_ids` | 참 또는 거짓(기본 거짓) | 이 시스템의 ID가 앱을 다시 켜도 같다고 관리자가 표시한 것. workflow를 만들 때 대상 적기가 ID를 써도 되는지를 정합니다(4절) |
| `ready_read` | `snapshot` 또는 `find`(기본 `snapshot`) | 준비 확인이 화면을 읽는 방식(2절) |

- 읽을 때 형식을 검사합니다. 모르는 키, 빈 글, 겹친 항목이 있으면 그 프로파일을 쓰지 않고 실행을 시작하지 않습니다. 오류 글에는 몇 번째 항목의 어느 키인지만 넣고 값은 넣지 않습니다.
- 쓰기는 임시 파일에 쓰고 바꿔치기합니다. 손으로 고쳐도 됩니다.
- 프로파일이 없는 시스템은 빈 프로파일과 같습니다.
- **지금의 `ready_text`와의 관계:** 설정의 `ready_text`는 그대로 둡니다. 그 시스템의 프로파일에 `ready`가 하나라도 있으면 프로파일이 앞서고, 없으면 `ready_text`가 이름 하나짜리 신호로 쓰입니다. `ready_timeout_s`는 지금처럼 설정에 둡니다.
- 프로파일의 `ready`도 설정의 `ready_text`처럼 설정 파일에서 고른 앱에만 적용합니다(지금의 `apply_ready` 규칙). 작업 파일이 `ready_text`를 직접 적으면 그것이 가장 앞섭니다.

## 2. 준비 확인: 재고, 읽는 방식을 고르기

### 재기

화면이 다 보인 뒤에도 늦는 까닭은 여기서 알 수 없습니다. 후보는 셋입니다: 트리가 커서 한 번 읽는 데 오래 걸린다, 화면이 보인 직후 앱이 바빠 읽기가 시간 초과로 실패한다, 관계없는 새 창까지 읽는다. 그래서 수를 남깁니다.

- **`ready` 끝 이벤트**에 더합니다: 확인한 바퀴 수(지금도 있음), 읽기 호출 수, 실패한 읽기 수, 시간 초과 수, 읽기 하나의 가장 긴 시간(ms), 마지막 바퀴의 후보 창 수, 읽는 방식.
- **요약의 `준비:` 줄**에 더합니다: `준비: ready · 95초 · snapshot · 확인 12바퀴 · 읽기 31회(실패 4, 시간 초과 0, 최대 7.9초) · 대상 바뀜`. 수와 방식 이름뿐입니다.
- **`check.py`의 준비 항목**은 한 바퀴씩 무엇이 얼마나 걸렸는지를 수로 출력합니다: 창 목록 읽기 ms, 후보 창 수, 신호마다 찾았는지와 걸린 ms, 실패 코드. 신호의 글과 ID는 출력하지 않고 "신호 1", "신호 2"로 부릅니다. 준비된 뒤에는 그 화면에서 두 방식의 시간을 재서 나란히 출력합니다(아래).

회사에서 이 수를 불러 주면 어디가 느린지 갈립니다.

### 읽는 방식 둘, 고르는 것은 잰 수로

어느 쪽이 빠른지는 시스템마다 다르고 여기서는 알 수 없습니다. 그래서 두 방식을 모두 두고, 재 본 수로 시스템마다 고릅니다. 비전 모델의 좌표 방식을 `check.py`가 재서 권하는 지금의 방식과 같습니다.

| 방식 | 하는 일 | 빠른 경우 | 느린 경우 |
| --- | --- | --- | --- |
| `snapshot`(기본, 지금 방식) | 후보 창의 트리를 깊이 10까지 통째로 읽고, 그 안에서 신호를 모두 찾음 | 트리가 작거나 신호가 여럿일 때(한 번 읽어 모두 판정) | 트리가 클 때 |
| `find` | 신호마다 `find --window-id <창> --name <이름> --exact --first`(또는 `--native-id <ID>`)로 물음 | 신호가 이미 떠 있을 때(첫 일치에서 멈춤) | 신호가 아직 없을 때. 없다고 답하려면 트리를 끝까지(깊이 50까지) 읽어야 하고, 큰 트리에서는 제한 시간에 걸림 |

- 프로파일의 `ready_read`가 방식을 정합니다(`snapshot` 또는 `find`, 없으면 `snapshot`).
- **`check.py`와 등록 화면의 "지금 확인"이 두 방식을 모두 재서 보여 줍니다**: 신호가 떠 있는 지금 화면에서 방식마다 걸린 ms. `check.py`는 빠른 쪽을 권합니다. 신호가 아직 없는 동안의 비용은 준비 기다리기의 수(위의 "재기")로 봅니다.
- **맞추는 규칙은 두 방식이 같습니다.** 이름은 앞뒤 공백만 무시하고 똑같아야 합니다(지금 규칙). `find --exact`는 대소문자를 무시하고 안쪽의 연속 공백을 하나로 줄이므로, `find`가 돌려준 요소의 이름을 이 규칙으로 한 번 더 봅니다. 느슨하게만 맞는 것은 찾지 못한 것으로 칩니다. ID는 글자 그대로 같아야 합니다.
- **창의 제목은 신호가 아닙니다**(지금 규칙). `find` 방식에서 후보 창의 제목이 이름 신호와 같으면, `--first`가 뿌리 창 자신을 돌려줄 수 있으므로 그 창은 그 바퀴에 `snapshot`으로 판정합니다.
- **`find`의 시간 초과는 "아직 없음"입니다.** 실패로 세지 않고 따로 셉니다(시간 초과 수). 그 밖의 오류만 실패한 읽기입니다. 그래야 실패 수가 "앱이 바빠서 못 읽음"을 가리킵니다.
- 한 창에서 신호가 **모두** 찾아지면 그 창이 준비된 창입니다. 신호 하나가 안 찾아지면 그 창의 나머지 신호는 보지 않고 다음 창으로 갑니다.
- `find` 방식으로 준비된 창을 찾으면 **그때 한 번만** 트리 전체를 읽어 준비된 창의 관찰로 기록합니다. `snapshot` 방식은 지금처럼 판정에 쓴 그 읽기를 기록합니다.
- 후보 창은 지금과 같습니다(`launch`가 돌려준 프로세스의 창, 실행 전에 없던 창).

### 방식과 상관없이 바뀌는 것

- 바퀴 사이에 쉬는 시간을 1초에서 0.3초로 줄입니다(코드의 상수).
- 신호를 여러 개 둘 수 있고, ID로도 적을 수 있습니다. ID 신호는 역할과 ID, 적혀 있으면 담긴 영역(`in`)까지 맞아야 합니다. `snapshot` 방식은 트리에서 셋을 모두 봅니다. `find` 방식은 역할과 ID만 묻고 담긴 영역은 보지 못하므로, `in`이 적힌 ID 신호가 있는 프로파일에서는 `find`가 그 신호를 찾은 뒤 준비된 창을 기록하려고 읽는 트리에서 담긴 영역을 한 번 더 확인합니다. 어긋나면 준비가 아닙니다.
- **ID 신호만으로 준비를 정하지 않기를 권합니다.** 등록 화면은 준비 신호가 ID 신호 하나뿐이면 "이름 신호나 다른 ID 신호를 함께 두세요"라고 알립니다(저장은 됩니다). 화면에 이름이 하나도 없는 시스템도 있기 때문에 막지는 않습니다.
- 읽기 수, 실패 수, 시간 초과 수, 가장 긴 읽기를 셉니다.

**어느 방식이 회사 MES에서 빠른지는 모릅니다.** 느린 까닭이 읽는 시간이면 방식을 바꿔 빨라질 수 있고, 화면이 보인 직후 앱이 바빠 읽기가 실패하는 것이면 어느 방식도 덜 빨라집니다. 회사에서 `check.py`와 요약의 수를 보고 정합니다. 구현할 때 집의 가상 MES에서도 두 방식을 재 보지만(창을 띄우므로 사용자에게 확인받은 뒤), 가상 MES의 트리는 작아서 회사의 답을 대신하지 못합니다.

### 프로파일이 없는 시스템

`ready_text`만 있는 지금의 설정은 이름 하나짜리 신호, `snapshot` 방식으로 돕니다. 판정 규칙은 그대로이고, 쉬는 시간이 줄고 수를 세는 것만 달라집니다.

## 3. 모델이 ID를 읽기

### 창 핸들인 ID는 ID가 아닙니다

실제 창 확인(2026-11-19)에서 더한 규칙입니다. 이름을 붙이지 않은 WinForms 컨트롤의 AutomationId는 그 컨트롤 자신의 창 핸들을 10진수로 적은 값이라 앱을 켤 때마다 바뀝니다. 가상 MES에서 재 보니 ID 13개 가운데 바뀌는 둘이 정확히 자식 창의 핸들이었고, 나머지는 핸들이 아니었습니다. 이런 ID를 그대로 두면 세 가지가 깨집니다.

- 담긴 영역에 핸들이 적힙니다. ID가 고정인 버튼이라도 핸들 ID 패널 안에 있으면, `stable_ids`인 시스템의 workflow가 그 영역까지 대상에 적어 앱을 다시 켠 뒤에는 대상을 찾지 못합니다(`TARGET_NOT_FOUND`).
- 등록 화면이 `in`에 핸들을 적으면 다음 날 등록 이름도 ID 준비 신호도 맞지 않습니다.
- 핸들 ID만 있는 빈 패널이 "ID만 있는 요소"로 관찰 글과 등록 화면의 표에 나옵니다.

그래서 하니스는 CLI에서 스냅숏을 받는 자리(`agent/desktop.py`)에서, **값이 그 창과 같은 프로세스에 속한 창 핸들과 글자 그대로 같은 native id를 뗍니다.** 그 뒤의 준비 확인, 관찰, 기록, 대상 적기, 등록 화면, 점검은 그 노드를 ID가 없는 노드로 봅니다. 앱의 이름이나 화면의 글이 아니라 플랫폼의 사실로만 가립니다. 창 핸들은 Win32로 직접 읽고(`agent/handles.py`), 읽지 못하면 아무것도 떼지 않습니다. CLI는 고치지 않습니다.

이 규칙이 가리는 것은 창 핸들에서 온 ID뿐입니다. 다른 까닭으로 바뀌는 ID(예: 만들 때마다 번호를 새로 매기는 앱)는 가리지 못하므로, `check.py`의 `id 유지`와 `stable_ids` 표시는 그대로 필요합니다.

### 요소의 범위

ID만 있는 노드(ref도 이름도 설명도 값도 없음)도 요소가 될 수 있습니다. 요소가 되면 표시 번호가 붙고, 뷰어에 박스가 그려지고, `click_part`로 누를 수 있습니다. 지금은 이런 노드가 하니스에 보이지 않습니다.

모든 ID 노드를 요소로 치지는 않습니다. 컨테이너마다 ID가 있는 툴킷(WinForms는 컨트롤 이름이 AutomationId가 됩니다)에서는 관찰 글이 크게 늘고, 이름 없는 `window` 노드가 요소가 되면 새 범위를 열어 그 아래 요소가 위쪽 범위에서 모두 빠지기 때문입니다. 규칙은 이렇습니다.

- **프로파일에 등록된 요소와 맞는 노드는 요소입니다**(`role`, `id`, 적혀 있으면 `in`까지 맞음). 자식이 있어도 됩니다. 관리자가 가리킨 것이기 때문입니다.
- **등록되지 않은 ID만 있는 노드는 자식이 없을 때만 요소입니다.**
- **역할이 `window`인 노드는 ID만으로는 요소가 되지 않습니다.** 범위를 여는 것은 지금처럼 이름이나 ref가 있는 창 요소뿐입니다.
- 둘째 규칙은 프로파일이 없는 실행에도 적용됩니다. ID만 있는 잎 노드가 있는 앱에서는 관찰의 요소 수와 표시 번호가 달라집니다.
- 요소의 종류는 지금의 `control`(ref 있음), `text`(이름·설명·값 있음)에 `id`(ID만 있음)를 더합니다.
- 등록 화면의 표는 이 규칙과 따로, 읽은 화면의 ID만 있는 노드를 자식이 있든 없든 모두 보여 줍니다(`window`는 빼고). 자식이 있는 노드는 그렇게 표시합니다.

### 관찰 글

```
[12] button "조회(F5)" @s1:e4 actions=Click
[13] image id="60" alias="Execution Plan"
[14] image id="56" alias="Shipment Plan"
[15] group id="71"
```

13번과 14번은 프로파일에 등록된 요소이고, 15번은 등록되지 않은 ID만 있는 잎 노드입니다. 셋 다 ref가 없으므로 모델은 표시 번호로 누릅니다(`click_part`, 실제 클릭).

- **`id`:** 이름이 없는 요소에 ID가 있으면 보여 줍니다. 이름이 있는 요소에는 붙이지 않습니다. 이름이 이미 그 요소를 가리키고, ID까지 붙이면 글이 길어지기 때문입니다.
- **`alias`:** 그 요소가 프로파일의 `elements` 항목과 맞으면 등록 이름을 보여 줍니다. 맞는다는 것은 `role`과 `id`가 같고, 항목에 `in`이 적혀 있으면 그 요소의 담긴 영역도 같은 것입니다. 한 관찰 안에서 한 항목에 맞는 요소가 둘 이상이면 어느 것에도 `alias`를 붙이지 않습니다.
- **담긴 영역:** 하니스는 ID가 있는 요소마다 담긴 영역(위의 `in`과 같은 것)을 함께 구합니다. 담긴 영역이 쓰이는 곳은 모두 ID와 함께이기 때문입니다. 관찰 글에는 넣지 않고, 요소 dict와 기록에만 둡니다.
- `alias`는 요소의 `name`을 바꾸지 않습니다. 화면에 실제로 보이는 글과 관리자가 붙인 이름을 섞지 않기 위해서입니다. 요소 dict에는 `native_id`와 `alias`가 따로 실립니다. 지금 `native_id`는 Toolbox의 표시 번호 맵에만 있고 기록이 쓰는 요소 목록(`visible_elements`)에는 없으므로, 거기에도 넣습니다.
- 모델에게 주는 지시문에 더합니다: `id`는 앱이 준 값이고, `alias`는 글자가 그림으로 그려진 요소에 관리자가 붙인 이름이니 그 요소의 이름으로 읽되, 화면에서 본 것과 어긋나 보이면 믿지 말고 `look`으로 확인하거나 물으라는 것.
- **GSCM의 메뉴는 실제 클릭으로 눌립니다.** `IsInvokePatternAvailable`이 거짓이라 헤드리스로 누를 길이 없습니다. 모델은 `click_part`로 그 자리를 실제 마우스로 누르고, 그러려면 권한 단계 2 이상이 필요하며, 실행하는 동안 커서가 움직입니다. 요소에 ref가 붙어 있더라도 `click`이 실패하면 모델은 지금처럼 `click_part`로 넘어갑니다.
- 모델은 지금처럼 ref나 표시 번호로 누릅니다. ID로 직접 누르는 도구는 만들지 않습니다.

### 그 밖에 따라 바뀌는 것

- **뷰어:** 박스에 마우스를 올리면 ID와 등록 이름도 나옵니다.
- **기록:** 관찰의 요소에 `native_id`, 담긴 영역, `alias`가 남습니다. `events.jsonl`에만 둡니다. workflow 만들기는 기록만 읽으므로 ID가 기록에 있어야 4절이 됩니다. 기록은 글자 요소를 관찰 하나에 400개에서 자르는데, 새 `id` 종류의 요소는 `control`처럼 자르지 않고 모두 남깁니다.
- **지식:** 지식 항목의 글에 `id="60"` 같은 표현을 쓸 수 있습니다. 좌표나 표시 번호와 달리 다음 실행에서도 같은 요소를 가리킵니다.
- **기대와 결과의 비교(`agent/effects.py`):** 요소를 `(종류, 역할, 이름, 설명)`으로 견줍니다. 이름 없는 요소 여럿이 ID로만 갈리는 화면에서는 ID도 열쇠에 넣어야 "무엇이 바뀌었나"가 맞습니다. 열쇠에 `native_id`를 더합니다.

## 4. workflow의 대상 적기에 ID 쓰기

어제 설계는 "앱이 준 고유 id는 쓰지 않습니다"였습니다. 이유는 앱을 다시 켜면 바뀌는 ID가 있다는 것이었습니다. 사용자가 이 시스템들의 ID는 바뀌지 않는다고 확인했으므로, **프로파일에 `stable_ids: true`가 있는 시스템에서만** ID를 씁니다.

- **ID는 더해지는 조건입니다.** 대상 적기의 바탕은 지금처럼 역할, 이름, 설명입니다. 대상 요소에 ID가 있으면 `id`를 더하고, 담긴 영역이 있으면 `in`도 더합니다. 이름이 있는 요소는 이름과 ID가 둘 다 맞아야 하고, 이름이 없는 요소는 역할, ID, 담긴 영역이 맞아야 합니다.
- **만들 때:** 그렇게 적은 것이 그 범위에서 대상 하나만 가리키면 거기서 끝냅니다. 여럿이면 지금처럼 가까운 글자와 순서(`near`)를 더합니다. 그래도 하나가 안 되면 만들지 않습니다(`LOCATOR_NOT_UNIQUE`).
- **이름이 파라미터인 대상에는 ID를 적지 않습니다.** 누른 요소의 이름을 파라미터로 삼은 단계(예: 목록에서 고른 항목)는 재실행 때 그 값의 이름을 가진 다른 요소를 눌러야 합니다. 기록 때 누른 요소의 ID를 함께 적으면 다른 값을 줬을 때 맞는 요소가 없어집니다. 이런 대상은 지금 규칙(`name: $이름`)으로만 적습니다. `select_only`의 항목도 지금처럼 이름으로 찾고, "전체 선택" 요소에는 ID를 더할 수 있습니다.
- **재실행 때:** 대상 적기에 적힌 것이 모두 맞는 요소를 그 범위에서 찾습니다. 0개와 여럿의 처리는 지금과 같습니다. 재실행은 대상을 찾을 때 `stable_ids`를 따지지 않습니다(준비 신호와 요소의 범위는 다른 실행처럼 프로파일에서 옵니다). `id`를 적은 workflow는 나중에 `stable_ids`를 끄거나 프로파일을 지워도 그대로 찾고, ID가 달라졌으면 대상을 못 찾아 멈춥니다(`TARGET_NOT_FOUND`).
- workflow 파일의 형식은 대상 적기에 `id`와 `in` 키를 받습니다. `in`은 `id`가 있을 때만 적습니다.
- `stable_ids`가 거짓이거나 프로파일이 없는 시스템에서 만드는 workflow는 지금과 똑같습니다.
- 그림뿐인 메뉴는 이름도, 기준으로 삼을 가까운 글자도 없어서 지금 규칙으로는 대상 적기를 만들지 못합니다(`LOCATOR_NOT_UNIQUE`). ID가 있어야 이런 화면의 workflow가 만들어집니다.


### 흐름

1. **시스템 고르기.** 설정의 시스템 목록에서 고릅니다. 그 시스템의 프로파일을 읽어 지금 등록된 것을 보여 줍니다.
2. **앱 띄우기.** 하니스가 그 시스템의 exe를 띄우고, `launch`가 돌려준 프로세스의 창과 띄운 뒤 새로 생긴 창을 목록으로 보여 줍니다(준비 기다리기의 후보 창과 같은 규칙). 같은 exe의 프로세스가 하나 떠 있으면 `launch`가 거기에 붙으므로 떠 있는 앱을 그대로 씁니다. 창이 목록에 나오지 않으면 시스템을 닫고 다시 누릅니다. 실행기가 메인 화면을 다른 프로세스로 띄우는 시스템이 이미 떠 있거나, 같은 exe가 여럿 떠 있어 `launch`가 실패하는 경우입니다. 이때 화면에 "시스템을 닫고 다시 띄워 주세요"를 보여 줍니다. PC의 다른 앱 창은 목록에 넣지 않습니다(다른 앱의 제목이 뷰어에 나오지 않게).
3. **화면 읽기.** 고른 창의 트리 전체와 스크린샷을 읽습니다. "3초 뒤 읽기"는 누르고 3초 뒤에 읽습니다. 브라우저로 넘어오면 앱의 메뉴가 닫히므로, 누른 뒤 앱으로 가서 메뉴를 열어 두는 용도입니다. 남은 초를 화면에 보여 줍니다.
4. **박스.** 지금 뷰어처럼 요소마다 박스를 그립니다. 박스를 누르면 오른쪽에 역할, 이름, ID, 담긴 영역이 나옵니다. "준비 신호로"를 누르면 이름이 있는 요소는 이름으로, 이름이 없고 ID가 있는 요소는 역할·ID·담긴 영역으로 준비 신호 목록에 들어갑니다. 둘 다 없는 요소는 준비 신호가 될 수 없습니다.
5. **표.** 읽은 화면에서 이름이 없고 ID가 있는 요소를 모두 줄로 보여 줍니다. 줄마다 그 요소를 스크린샷에서 잘라 낸 그림, 역할, ID, 담긴 영역, 이름 칸이 있습니다. 담긴 영역은 관리자가 적지 않습니다. 읽은 트리에서 하니스가 구해 함께 저장합니다. 이미 등록된 이름은 칸에 채워져 있습니다. 이름을 적으면 등록, 비우면 등록하지 않음(이미 있던 것은 지움)입니다. 줄에 마우스를 올리면 왼쪽의 그 박스가 강조됩니다.
6. **지금 확인.** 등록하려는 준비 신호로 지금 떠 있는 창에 준비 확인을 한 바퀴씩, 두 방식(`snapshot`, `find`)으로 돌립니다. 신호마다 찾았는지와, 방식마다 걸린 ms를 보여 줍니다. 저장하기 전에 신호가 실제로 잡히는지 보고, 빠른 방식을 "읽는 방식" 칸에서 고릅니다(프로파일의 `ready_read`).
7. **저장.** 프로파일 파일을 씁니다.

### 검사

저장하기 전에 읽은 화면으로 검사하고, 걸리면 무엇이 문제인지 그 줄에 보여 줍니다.

- 등록 이름의 `(role, id, in)`이 읽은 창에서 둘 이상의 요소와 맞으면 저장하지 않습니다. `56` 같은 작은 숫자는 한 창의 여러 요소가 같이 쓸 수 있습니다. 담긴 영역이 달라 갈리는 경우는 저장됩니다.
- ID 준비 신호도 같습니다.
- 이름 준비 신호가 읽은 창에 하나도 없으면 저장하지 않습니다(다른 화면에서 읽어 등록하려는 실수).
- 준비 신호가 창의 제목과만 같으면 저장하지 않습니다.

여러 화면에 걸쳐 등록할 수 있습니다. 메뉴를 바꿔 가며 "화면 읽기"를 되풀이하면 표의 줄이 그 화면의 것으로 바뀌고, 이미 등록한 다른 화면의 이름은 프로파일에 그대로 남습니다.

### 지키는 것

- 등록 화면은 앱을 조작하지 않습니다. 하는 일은 띄우기, 창 목록, 트리 읽기(`snapshot`, `find`), 스크린샷뿐입니다.
- 모델을 부르지 않습니다.
- 실행 중에는 쓸 수 없고, 등록 화면이 화면을 읽는 동안에는 실행을 시작할 수 없습니다(지금의 한 번에 하나 규칙).
- 서버는 읽은 화면(트리, 스크린샷)을 메모리와 임시 폴더에만 두고 실행 기록(`runs\`)에 남기지 않습니다. 뷰어를 끄면 지웁니다.
- 화면의 글은 `textContent`로만 넣습니다.
- 서버 응답에 시스템의 exe 경로를 넣지 않습니다.

## 6. 점검 (`check.py`)

- 설정 항목에 `시스템 프로파일: 준비 신호 2 · 등록 이름 14 · ID 고정 예 · 읽는 방식 snapshot`처럼 수와 방식 이름만 출력합니다. 프로파일이 깨졌으면 그 사실과 몇 번째 항목인지를 출력합니다.
- 앱 관찰 항목의 준비 줄은 2절의 "재기"대로 바퀴마다의 수를 출력합니다. 준비된 뒤에는 두 방식의 시간을 `읽는 방식: snapshot 4.2초 · find 0.3초 · 권장 find`처럼 출력합니다.
- 앱 관찰 항목의 요소 수에 "ID만 있는 요소" 수를 더합니다.
- `check.py`에는 앱을 다시 켠 뒤 ID가 같은지 비교하는 항목이 이미 있습니다(`agent/survey.py`의 `id_keys`). 그대로 두고, 그 결과 줄에 "같으면 등록 화면에서 'ID는 다시 켜도 같음'을 켜도 됩니다"라는 안내를 붙입니다. `stable_ids`를 켜기 전에 확인하는 수단입니다.

## 7. 가상 MES

그림뿐이면서 ID가 있는 메뉴를 집에서 재현합니다.

- `menu` 영역이 `bare`(이름 없는 `button`, ref와 고정된 숫자 `AutomationId`)를 받게 합니다. 지금 `bare`는 `arrow`만 받습니다.
- `menu`에 새 노출 방식 `idonly`를 더합니다: 이름도 ref도 없고 `AutomationId`만 있는 요소. 회사 GSCM의 메뉴가 어느 쪽인지 모르므로 둘 다 시험합니다.
- 메뉴 항목의 `AutomationId`는 화면이 달라도, 앱을 다시 켜도 같습니다.
- 메뉴 항목들을 담은 영역에도 `AutomationId`가 있습니다(담긴 영역을 시험). 이것을 없애는 옵션도 둡니다(담긴 영역이 없는 경우).
- 같은 `AutomationId`를 두 요소가 쓰는 경우를 만드는 옵션을 둡니다: 같은 영역 안의 두 요소(등록 화면이 막아야 함)와, 다른 영역의 두 요소(담긴 영역으로 갈려야 함).

## 8. 시험과 확인

- 지금 관례대로 테스트를 먼저 쓰고, 테스트마다 구현을 되돌려 실패하는지 확인합니다.
- 준비 확인은 지금의 가짜 데스크톱(`tests/ready_support.py`)에 `find` 응답을 더해 시험합니다. 등록 화면의 서버 쪽은 가짜 데스크톱으로, 화면 쪽은 지금 뷰어 테스트의 방식으로 시험합니다.
- 목표와 "실패로 보는 것"의 항목마다, 어겼을 때 실패하는 테스트가 적어도 하나 있어야 합니다.
- **실제 창 확인(사용자에게 확인받은 뒤):**
  1. 가상 MES에서 두 읽는 방식의 시간을 `check.py`로 잽니다. 가상 MES의 트리는 작으므로 도구가 도는지를 보는 것이고, 회사의 답을 대신하지 않습니다.
  2. 가상 MES를 `--expose menu=bare`와 `menu=idonly`로 띄우고, 등록 화면에서 화면을 읽어 메뉴에 이름을 붙이고 준비 신호를 등록합니다.
  3. 그 프로파일로 모델 실행을 해서, 모델이 등록 이름을 보고 메뉴를 누르는지 봅니다.
  4. `stable_ids`를 켜고 workflow를 만들어 재실행합니다.
  5. "3초 뒤 읽기"로 열린 메뉴 안의 항목이 잡히는지 봅니다.

## 설계자가 정한 것 (사용자가 말한 것이 아님)

1. 준비 신호는 모두 보여야 준비입니다(하나만 보여도 준비가 아님).
2. 시스템마다 프로파일 파일 하나를 두고, 폴더를 가리키는 이름은 `profile_dir`입니다. `.env`를 고르는 `--profile`과 구분합니다.
3. 설정의 `ready_text`는 남기고, 프로파일의 `ready`가 있으면 그것이 앞섭니다.
4. 준비 확인의 쉬는 시간 0.3초.
5. 읽는 방식을 둘 다 두고(`snapshot`, `find`), 시스템마다 프로파일의 `ready_read`로 고릅니다. 기본은 지금 방식인 `snapshot`입니다. `check.py`와 등록 화면이 두 방식을 재서 보여 줍니다. 처음 초안의 "`find`로 바꾼다"를 검토에서 고쳤습니다: `find`는 신호가 아직 없을 때 트리를 끝까지 읽어야 답하므로, 기다리는 동안에는 오히려 느릴 수 있습니다.
6. 맞추는 규칙은 두 방식이 같습니다(앞뒤 공백만 무시). `find`의 시간 초과는 "아직 없음"으로 치고 실패와 따로 셉니다.
7. ID만 있는 노드는 프로파일에 등록됐거나 자식이 없을 때만 요소로 칩니다. `window` 역할은 ID만으로는 요소가 되지 않습니다. 자식이 없는 경우는 프로파일이 없는 실행에도 적용됩니다.
8. 이름이 파라미터인 대상은 ID가 있어도 이름으로 적습니다. 재실행은 대상을 찾을 때 `stable_ids`를 따지지 않습니다.
9. 등록 화면의 창 목록에는 하니스가 띄운(붙은) 프로세스의 창과 그 뒤 새로 생긴 창만 넣습니다. 안 나오면 시스템을 닫고 다시 띄웁니다.
10. 기록의 요소에 `native_id`를 넣고, `id` 종류의 요소는 자르지 않습니다.
11. 관찰 글의 `id`는 이름이 없는 요소에만 붙입니다.
12. 등록 이름은 `alias`로 따로 보여 주고 요소의 `name`을 바꾸지 않습니다.
13. 모델에게 ID로 직접 누르는 도구는 주지 않습니다.
14. workflow가 ID를 쓰는 것은 `stable_ids: true`인 시스템에서만입니다. 등록 화면의 체크 칸으로 켭니다. ID는 이름을 대신하지 않고 더해집니다.
15. 등록 화면은 앱을 조작하지 않고, 읽은 화면을 기록으로 남기지 않습니다.
16. 등록 화면에 "지금 확인"을 둡니다.
17. ID에 더하는 정보는 역할과 "담긴 영역"(가장 가까운, ID나 이름이 있는 조상)입니다. 사용자가 정한 "ID는 추가 정보"를 이렇게 채웠습니다. 셋이 모두 맞는 요소가 한 창에 둘 이상이면 등록하지 못하고, 실행 중에 둘 이상이면 `alias`를 붙이지 않습니다.
18. 모델에게 `alias`는 참고로 주고, 화면과 어긋나 보이면 확인하거나 물으라고 지시합니다.
19. 준비 신호가 ID 신호 하나뿐이면 등록 화면이 알리되 막지는 않습니다.
20. 가상 MES에 `menu=bare`와 `menu=idonly`를 더합니다.
21. 창 핸들인 ID는 ID로 치지 않습니다(3절). 실제 창 확인에서 드러난 문제를 보고 더했습니다.
22. 등록 화면의 "지금 확인"은 잰 시간과 권장 방식을 보여 주기만 하고 "읽는 방식"의 선택을 바꾸지 않습니다. 저장하지 않고 적어 둔 이름은 화면을 다시 읽어도 남습니다. 읽은 창의 그림에는 그 위에 겹친 같은 프로세스의 창(열린 메뉴 목록 등)도 붙입니다. 실제 브라우저 확인에서 고쳤습니다.

## 구현자에게 맡기는 것

- 새 모듈의 이름과 나누는 방식, 프로파일을 `Task`와 `Toolbox`에 싣는 방법.
- `ready` 이벤트와 요약 줄의 정확한 키와 문구(수와 코드만이라는 조건 안에서).
- 등록 화면의 배치와 문구, 서버의 주소 이름, 잘라 낸 그림을 만드는 방법(서버에서 자르기, 브라우저에서 자르기).
- 표의 줄이 많을 때의 처리(스크롤, 걸러 보기).
- 두 읽는 방식의 읽기 하나에 주는 제한 시간(지금 `snapshot`은 8초).

## 확인이 필요한 것

1. **회사 MES에서 어느 읽는 방식이 빠른지.** `check.py`의 `읽는 방식:` 줄로 봅니다.
2. **회사 MES에서 느린 까닭.** 읽기 시간인지, 앱이 바빠 읽기가 실패하는 것인지. 요약의 새 `준비:` 줄로 압니다. 실패 수가 많으면 앱이 바쁜 것이고, 그때는 읽는 방식을 바꿔도 덜 빨라집니다. 그 수를 보고 다음 수(읽기 제한 시간 줄이기, 후보 창 줄이기)를 정합니다.
3. **GSCM의 메뉴 항목이 자식을 가진 노드인지.** `IsInvokePatternAvailable`이 거짓이라는 것은 사용자가 확인했고, 그래서 실제 클릭으로 누릅니다. 자식을 가진 노드면 등록하기 전에는 모델에게 보이지 않고(3절의 잎 규칙), 등록 화면의 표에는 나옵니다. 등록 화면에서 처음 읽을 때 드러납니다.
4. **GSCM의 메뉴 항목에 담긴 영역이 있는지.** 메뉴 항목들을 담은 영역에 ID도 이름도 없으면 `in`을 적지 못하고, 그때 ID에 더해지는 정보는 역할과 "한 창에 하나뿐"만 남습니다. 등록 화면의 표에서 담긴 영역 칸이 비어 있는지로 압니다.
5. **`56` 같은 ID가 화면마다 겹치는지.** 사용자도 모릅니다. 그래서 ID를 홀로 쓰지 않습니다. 그래도 다른 화면의 요소가 역할, ID, 담긴 영역까지 같으면 그 요소도 같은 등록 이름으로 보입니다. 모델에게는 `alias`가 화면과 어긋나 보이면 확인하라고 지시하고, 이런 경우가 실제로 있는지는 회사에서 등록하며 봅니다.

## 방법 비교 (사용자가 고름)

등록 도구:

1. **뷰어의 한 화면에 박스와 표 (고름).** 박스 그리기와 서버가 이미 있고, 가짜 화면으로 집에서 시험할 수 있고, 하니스가 보는 그대로를 보여 줍니다. 메뉴 스무 개를 그림을 보며 한 번에 적습니다. 브라우저로 넘어가면 메뉴가 닫히는 문제는 "3초 뒤 읽기"로 풉니다.
2. **실제 앱 위에서 가리켜 고르기.** 가장 직관적이고 포커스를 뺏지 않습니다. 화면 위에 투명 창을 띄우고 전역 단축키를 받는 Windows 전용 GUI 코드가 필요하고, 자동 시험이 어렵고, 요소를 하나씩 가리켜야 합니다. 가리켜 보는 일은 Inspect가 이미 합니다.
3. **파일을 손으로 고치기(지금).** 만들 것이 없지만 ID와 화면의 요소를 눈으로 맞춰야 하고, 겹치는 ID를 알아채지 못합니다.
